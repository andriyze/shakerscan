# ShakerScan 2.13.0

**Status:** integration candidate on `release/2.13.0`; it follows 2.12.2.
The client for this release is `shakerscan` 0.13.0 (`secrets` commands and `api` paths accept a
URL).

2.13.0 carries the fixes prepared as 2.12.3 (never published), Scans that close what they
re-checked and keep listing what they saw, signed-in access-control reads in a standard Scan, an
archive that holds what sqlmap and Dalfox sent, a rebuilt sidebar, a first pass over every page of
the web UI, and a contract that lets a managed deployment place its own pages in the UI.

**Upgrade.** Upgrade in place from 2.12.2 (or any 2.12 release). The first start creates the
`finding_scan_observations` table and a trigger on `findings` in the always-run migration path and
fills the table once from the Scan columns of existing findings; installs one definition of
`update_target_stats()` and repairs, once, a target whose stored latest result came from a
discovery run; and recomputes the root domain of a target on a wildcard-DNS service. Nothing else
existing is rewritten. **Worker start-up changes:** a worker whose image identity does not match
its release manifest no longer starts (see Known limits). A rollback restores the pre-upgrade
database dump, as for every release (`docs/upgrade-and-rollback.md`).

## Scans and findings

- **A Scan keeps listing every finding it observed.** A finding is one record per target and
  fingerprint, and it pointed at the latest Scan that saw it. A later Scan that saw the finding
  again removed it from the earlier Scan's list, while that Scan's count and report still included
  it. `finding_scan_observations` now records one row per Scan and finding; `GET
  /findings?scan_id=`, the Scan detail and the release gate's report links read it.
- **A discovery run does not decide a target's latest result.** A discovery run maps hosts and
  endpoints with active testing off. It no longer sets the target's grade, score, last-scanned time
  or Scan count, is not the dashboard's latest result or the exposure inventory's latest scan, and
  is labelled "Discovery run". `GET /scans` returns `hidden_internal`, and the Scans list names the
  runs it leaves out with a control that shows them.
- **A signed-in standard Scan reads access control, read-only.** A standard active Scan that
  carries a credential profile also selects `authz_surface`: GETs to routes the Scan discovered,
  anonymous and signed in, no id enumeration. The family is medium risk, and a profile that lets
  the crawl use its session lets this batch use it too.
- **Password hashes in a signed-in API response are reported.** A bcrypt or argon2 value under any
  key, or a hash-shaped value under a key naming the account password, is a finding: the signed-in
  user's own hash is medium, another account's hash is high. Only keyed digests of the hashes leave
  the probe, and distinct hashes are counted across the whole Scan.
- **A proven SQL injection and a listed directory are reported once.** A SQL injection candidate
  for the proven route, method and input is folded into the proof as corroborating evidence, and
  one directory-listing finding is kept per directory (`/ftp` and `/ftp/`).
- **A Hunt proof of an exposure the Scan proved links to the Scan's finding** instead of becoming a
  second finding.
- **A live provider credential is critical in any exposed file.** A private key, cloud access key,
  live Stripe key, GitHub, Slack, npm or SendGrid token makes the exposure critical whatever file
  class holds it; a configuration password alone keeps the class severity.
- **A distribution build's upstream advisories do not rate its listener.** A candidate left
  unresolved because the distribution may have backported the fix no longer sets the listener's
  severity; the Services view labels such candidates probable.
- **A short credential value no longer corrupts scanner output.** A one-character session cookie
  turned every such character in URLs and ports into `***`, and the Scan failed at finalization.
  Pieces shorter than six characters are no longer masked on their own.
- **Dalfox is skipped where no input reflects.** Before Dalfox runs on a candidate the batch sends
  one request with an inert canary in every input; when it comes back nowhere the candidate settles
  negative for reflected XSS. The request is counted, sent once per candidate and taken from the
  candidate's own allowance. The credential profile's own sign-in endpoint is not pre-checked.
- **Every template window attempt keeps its planned rate and is retried when cut off.**
- **A web Scan's release decision uses its target's environment** when the run names no policy
  profile, and says what selected the profile (`policy_profile_basis`).
- **The deployment decision reads each exception's compensating controls.** It reported every
  exception as missing them.
- **Accept risk works without a configured policy profile.** A fresh install has none; the
  exception then applies under the built-in release policy. Once a profile exists, a new effective
  exception must name it. An unknown exception status answers 422, and an update locks its row.
- **A scope deny rule survives a DNS failure.**
- **A TLS port that refuses a plain request is recorded as an https origin**, not as a second,
  unencrypted web address on the same port.
- **A host that holds a scanned web application is not counted as a second asset** in the exposure
  inventory.
- **`POST /targets` names the stored name when it reuses a target.**

## Retest

- **Exposure and missing-header findings are retested with their own check.** They were refused as
  "retest by rescan only". A retest sends the recorded GET again and judges the answer with the
  same check; an unavailable service is inconclusive.
- **A later Scan that no longer sees a passive finding on its own URL verifies it fixed.** The Scan
  records what it re-checked (`check_coverage`, `scan-check-coverage/v1`) and one completed
  verification (`verification_mode` `scan_rescan`, `likely_fixed`) for each open exposure or
  missing-header finding it read again and no longer found. The engine does not change the
  finding's status. `GET /retests?verification_mode=scan_rescan&since=` lists them. An unread URL,
  an error page or another principal is not evidence.

## Evidence and coverage

- **The Scan archive holds what sqlmap and Dalfox sent.** Over HTTPS their requests were one
  `CONNECT` row per run. The worker now reads each tool's own log and archives its transactions to
  the tested origin (at most 2,000 per run, request bodies cut at 16 KiB, response bodies at
  4 KiB), sealed and masked on export like the engine's own requests. A Dalfox run stopped at its
  wall keeps every complete entry; a body the tool did not log is marked as not logged, not empty.
- **A tunnel row names the request the tool was given to test.**
- **A slice its continuation finished is not a coverage gap.** The report and the Scan page leave
  it out of the gaps, and the family row says how many actions were continued and why they stopped
  (`continued_actions`).
- **A selected discovery family has a row in the family coverage.**

## Scope and the CT monitor

- **A wildcard-DNS service is a public suffix.** `sslip.io`, `nip.io`, `xip.io` and `traefik.me`
  answer for any name that carries an address. A target on one got the service as its root domain,
  and with the CT monitor on, every certificate issued under the service became a new target. A
  root, wildcard or discovery apex on such a service is now refused, the monitor skips it, and a
  name below one is its own registrable domain.
- **The dashboard's CT monitor control is a labelled switch.** It shows on or off, says
  "starting…" or "stopping…" while a change is applied, and for a session that may not change it
  shows a lock and the reason (`ct_monitor.toggle` in `docs/session-capabilities.md`).
- **The switch acts on its own stack only.** `POST /gungnir/start` and `/gungnir/stop` took the
  first container named gungnir on the host; with two installations on one host, one could start
  or stop the other's monitor. An idle monitor now stops at once.

## Interface

- **The sidebar is rebuilt.** New Scan sits under the logo. The less used pages wait behind a
  "More" row that ends the menu and says how many pages it holds. The foot is a Settings row and
  one line with the edition, the version and two icon links (website, source code). In a short
  window only the list of pages scrolls.
- **A managed deployment can place its own pages in the UI** (`docs/ui-extensions.md`,
  `ui-extensions/v1`): sidebar entries and sections, pages at `/ext/<id>`, panels in named places
  and an account row at the foot of the sidebar that opens a panel with the deployment's links,
  Sign out and the version. Every declared value is validated, paths are same-origin only, and an
  entry that fails a check is dropped. `/api/build-identity` lists the contract in `ui_contracts`.
  A standalone UI is unchanged by it.
- **Detail pages say "not found" for an id that does not exist**, with a link back to the list, and
  an address that matches no page gets a page in the product's style.
- **Four pages finish in the browser what they left to a terminal:** a "What changed" card on the
  target page, the status control from Interpretations, Upload on Request Collections, and a plain
  host-task notice for Model Intake.
- **New Scan** does not ask again for authorization on a target that has a standing one, opens
  prefilled for a target with several web addresses, says when default-login templates will not
  run, and shows minimum attempts by check label. Web and API credentials are created on a web
  application, not its host.
- **The Scan page relates its finding totals in one line**, its coverage tab names steps in plain
  words and folds plan identifiers, and a step that did not apply is not marked for attention.
- **Lists read the same as the pages they lead to:** the Scans list and the dashboard show the
  grade as the Scan page does, a Targets row shows the whole host name and counts informational
  findings, the dashboard's latest results carry their examination strength, and a finished event
  no longer says "Queued".
- **Smaller corrections:** a skip-to-content link; the Docs page loads no remote images; the
  deletion preview names record kinds; Create Exception stays off until every field is filled; the
  posture tab shows DNS answers as fields; empty Evidence and Coverage pages say what fills them;
  Exposure uses the shared page header and does not scroll sideways on a phone; Add device names
  service policies in words; an authorization notice names a person.

## Client 0.13.0

- **`shakerscan secrets` commands accept a target URL as well as its id.**
- **`shakerscan api` accepts a URL as a query value** (`/targets/lookup?url=https://…`).
- **`shakerscan scan --endpoint` explains its format.**
- The help text no longer lists an `update` subcommand that does not exist.

## Fixes prepared as 2.12.3

2.12.3 was never published. Its changes ship here and are listed in [`2.12.3.md`](2.12.3.md):
four names used without an import on live paths (deleting a finding with an approved preview
answered 500), Hunt action accounting that lost partial results at a deadline, two writes a
refusal rolled back, input a target controls that failed a whole action, and a static gate that
rejects undefined names.

## Known limits

- The observation record of a finding seen before the upgrade holds its first and its last Scan;
  Scans in between left no record.
- The SQL injection fold covers a query or body input. A proven injection in a path segment can
  still be listed with its candidate.
- Targets the CT monitor already added under a wildcard-DNS service stay until they are deleted.
  Names below a wildcard-DNS host are not discovered.
- The engine records a rescan verification; it does not close the finding.
- The worker's identity check fails when the deployment names a version or revision
  (`SCANNER_EXPECTED_VERSION`, `SCANNER_EXPECTED_REVISION`; the release Compose file sets the
  version) that the image does not carry, or when the image's release manifest is unreadable. A
  worker left on another release's image after a partial upgrade exits at start instead of taking
  work; finish the upgrade with the documented route.
- The UI extension contract places pages and reads none of their content; what a deployment's page
  may do is decided by the server that serves it.
