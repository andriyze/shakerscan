# ShakerScan 2.3.6

Three new surfaces arrive gated or read-only — authenticated-scan assurance, AI application
boundary verification, and Service Intelligence — alongside correctness work on scan
accounting, proof reporting and the remote client. Upgrade in place from 2.3.5; 0.8.18 remains
the oldest directly certified upgrade base. No change to the deterministic proof boundary.

## Changes

### An external verifier spends what it reserved (#152)

- A nuclei batch attempt is paced to its reservation, as every other batched tool already was.
  Its argv fixed `-rate-limit 10` regardless of the hold, so a 45-second attempt holding 120
  requests planned about 450. Each attempt tripped the wire ceiling, was charged its whole
  reservation, and reported the catch-all `adapter_failed`. The same attempt now plans 90
  requests against its 120 hold.
- A failed action names its cause. The public receipt carried only identifiers, timestamps,
  parser version and provenance, so an operator saw "The capability adapter failed" and had
  nowhere to go while the cause sat in the stored receipt. It now carries a bounded diagnostic:
  the normalised error class, the error count, whether execution started, and the attempted and
  unattempted counts. Only the class travels, never the tool's own text.
- The operator log no longer masks that cause. A batch prepends `adapter_failed` before its real
  per-attempt errors, and the classifier returned on the first unrecognised token, so every
  batch failure read as `unclassified_adapter_error`.

### Missing evidence is not evidence of safety (#136)

- A proof batch whose manifest slice is empty because its producer was truncated or timed out
  now reports `dependency_incomplete` rather than `not_applicable`. The finalizer counted
  `not_applicable` as a clean, complete escalation, so an upstream timeout was laundered into
  good-looking coverage. An empty slice from a complete producer still reports `not_applicable`.

### Continuous ASM stops hammering a host that cannot resolve (#135)

- A dispatch failure is recorded like every other dispatcher decision, with a `next_eligible_at`
  backoff, and a target inside that backoff is skipped. Previously only the success path stamped
  `asm_last_test_at`, so an unresolvable target was retried, and logged, on every tick forever.

### Attack surface: Service Intelligence (#150, #153)

- Service Intelligence relates a domain to its targets, listeners, service and version identity,
  candidate weaknesses and investigation activities, with scoped Hunt investigation.
- Its services table leads with the listener and service rather than with an absent address,
  orders rows by consequence so linked findings and candidate weaknesses come first, shows counts
  only above zero, reports real time since last seen, and states the active findings that could
  not be tied to a listener instead of leaving them a footnote.

### AI application boundary verification (#149)

- Deterministic verification of a configured AI application boundary, with its own proof types
  joining the deterministic set. Ordinary web DAST does not select it.

### Authenticated-scan profile and assurance preview (#137)

- Reviewed profile metadata pinned to a credential version, explicit one-shot read-only
  validation, deterministic content-free evaluation, and an action-level credential gate that
  surfaces blocked work as `authentication_uncertain`. Gated off by default behind
  `SHAKERSCAN_AUTHENTICATED_ASSURANCE`; its own guide lists the remaining release gates.

### The remote client (#143, #144, #146)

- An authenticated request is never followed through a redirect. The https guard only ever
  examined the URL the operator supplied, so a redirect re-sent the bearer token to another
  origin or to plain HTTP.
- A saved token is bound to its origin: it is inherited only when the effective scheme, host and
  effective port match the saved ones. An explicit credential remains a deliberate override.
- `doctor` exits non-zero when the health probe fails. A reachable tool catalogue does not
  establish engine health, and onboarding runs this as a readiness check.
- The published 0.3.0 client is reconciled into this line, and a release tag that is not an
  ancestor of the supported line is refused.
- The Hunt page no longer demands an approval receipt an operator cannot create, where the
  deployment records target authorization itself. Credential use still requires its own receipt,
  and a standalone deployment is unchanged.
