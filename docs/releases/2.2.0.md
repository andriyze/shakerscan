# ShakerScan 2.2.0

**Candidate prepared 2026-09-04; not yet published.** Trustworthy upgrades, the fifth image handled
everywhere, and DAST depth restored on the 2.1.0 platform. Upgrade in place from 2.1.0; 0.8.18 is the
oldest directly certified upgrade base. One additive schema change (Scan plan revisions may now hold
up to nine rounds); no capability-authority change.

## Changes

### Upgrades that cannot eat an install

- Startup ensures the operator, session, and signer secrets before the datastore rotation, whose
  `compose up` interpolates every required secret; the misleading
  `MODEL_INTAKE_SIGNER_DATABASE_PASSWORD is required` failure on a 2.1.0 upgrade is gone.
- A data volume with no recorded password belongs to another install directory: startup refuses to
  rotate it away unless `SHAKERSCAN_ADOPT_EXISTING_DATA=1`, and the hosted installer refuses a new
  directory when another directory owns the Compose project, printing the `SHAKERSCAN_HOME=` command.
- The installer records prebuilt mode inside the atomic candidate tree and starts with `--prebuilt`;
  `scanner.sh` reads `release-image-lock.env` itself, so an installer run over a source checkout no
  longer rebuilds the scanner image from source, and `--image-tag` still wins deliberately.
- The Model Intake signer init waits, bounded, for authenticated PostgreSQL instead of failing
  `compose up` on the `pg_isready` race.
- Certification proves stateful upgrade and rollback from both the previous stable and
  `install/OLDEST_SUPPORTED_UPGRADE_BASE` (0.8.18), with all four runtime images, and a new
  installer-driven upgrade smoke covers the in-place, foreign-directory, and source-checkout cases.

### Five images, everywhere

- `install/release-images.json` is the one inventory the launcher, installer, smokes, release
  workflows, ledger, certifier, and waiver validator derive the image set from.
- `MODEL_INTAKE_IMAGE` follows the selected tag; pull, cached-image fallback, status, rebuild, and
  reload cover the Model Intake worker. Fleet overlays carry no Model Intake service.
- `/health.model_intake_worker` and `/workers.pools` report each execution pool (Web DAST, agent
  tools, devices, Model Intake) as fresh, build-current, and tool-complete; startup waits for the
  Model Intake pool; a new Worker Pools page shows them. Busy workers heartbeat their identity.
- Model Intake submissions cannot carry a fleet placement; the enqueue boundary strips one.
- The Model Intake image is vulnerability-scanned in full: the toolchain directory exclusion is
  gone, the waiver validator refuses directory exclusions, and the image ships no `pip` or
  `setuptools` in its tool environments, so the release carries no vulnerability waivers.
- Trivy's database refreshes at Model Intake worker start when egress exists and falls back to the
  baked copy; every static-analysis evidence manifest records `trivy_db_updated_at`.
- The API image is built from the Playwright runtime without the scanner toolset, runs as a distinct
  non-root user (10002; the sandbox keeps 10001), and reaches the Docker socket through the group the
  socket carries inside a container, resolved at start.

### DAST depth

- Profiles: fast 30 min / 5,000 requests, balanced 60 min / 20,000, thorough 180 min / 60,000, and an
  opt-in `deep` at 360 min / 150,000. Tool wall never exceeds wall. Old scans keep their labels.
- Every verifier candidate holds the time its tool was measured to need (200 s for an XSS candidate,
  180 s for SQLi, 420 s for a request-body attempt), and larger profiles fund more candidates per
  slice at that cost rather than less time per candidate. One lane never holds more than a quarter
  of the wall in a single compile, and the first proof slice of every family is funded before any
  extra breadth, so a Scan no longer buys coverage it cannot prove anything with.
- Scans keep spending: up to eight append-only continuation rounds re-plan every lane from its next
  unplanned candidate against the reconciled residual, and the finalizer is its own terminal
  revision, so a Scan ends when the work or the ceiling is exhausted, not after one round.
- The headless crawl carries the credential's browser state: a bearer token seeded into
  `localStorage` (new `browser_storage_key` on bearer profiles) or the cookie header, in a private
  worker-owned Chromium profile, so token-in-localStorage applications crawl authenticated.
- Installed CLI Hunt acceptance (H-10/H-11) and the Model Intake trust-anchor lifecycle (MI-6) are
  hard gates again.

### Release engineering

- The candidate reuses the attested image set `build-on-main` built for the exact SHA and builds
  only when none exists; `build-on-main` skips changes that cannot alter an image.

## Upgrade

- Re-run the installer, or `shakerscan restart --prebuilt` in place. See
  [`docs/upgrade-and-rollback.md`](../upgrade-and-rollback.md). Installs older than 0.8.18 must
  upgrade to 0.8.18 first.
- Existing release installs gain `api-storage-init`, which hands `results/` to the API's runtime
  identity once at start.
