# ShakerScan 2.6.0

This release moves the database to PostgreSQL 18, redesigns how scan results and findings read,
lets one credential serve several targets, and fixes the defects found by an end-to-end check of
every install channel and an audit of main against 2.5.6. It ships with client 0.7.5.

Upgrade in place from 2.5.6. The first start migrates PostgreSQL 16 data to PostgreSQL 18 (see
Upgrading). No change to the deterministic proof boundary.

## Upgrading

- The first start of 2.6.0 copies the PostgreSQL 16 data into a PostgreSQL 18 cluster volume,
  verifies the copy (row counts, sequences, databases and roles), and keeps the 16 data for
  rolling back. A failed or unverifiable copy leaves the 16 data in place and does not start the
  stack. (#266, #286)
- The rollback data is deleted automatically 30 days after the upgrade, announced on every start
  in the last week; set `SHAKERSCAN_POSTGRES_LEGACY_RETENTION_DAYS=0` to keep it. Data a rollback
  wrote to after the copy, and any directory a container still uses as its PostgreSQL data, is
  never deleted automatically. (#269, #274, #286)
- Installing as root now finishes. The installer builds the install directory with mode 0700,
  and a root install runs the API as uid/gid 10002, which could not read it: `/health` failed and
  the installer gave up waiting. The launcher now gives the API's group read access on every
  start, so an existing root install recovers on its next start or upgrade. (#283)

## Scan results and findings

- The scan report opens with its verdict and splits the rest into tabs (findings, posture,
  coverage, release gate, activity); the findings list groups repeated findings; and a finding
  page leads with its evidence and how to fix it. (#278)
- Proven findings show as proven on the scan page. The page projects proof with the same rules as
  the findings list and matches report findings to stored rows by the identity persistence uses,
  so a finding proven at scan time no longer shows as suspected there. (#277, #285)
- The findings list filters by several severities at once and by proof (proven, suspected,
  unverified). A proof filter that includes suspected also lists open Hunt leads, which are
  always suspected. (#279, #284)
- Nine in ten findings show how to fix them, matched by the tool and finding type that produced
  them rather than by words in the title. (#279, #280, #284)
- Target filters scope every list consistently, including Hunt findings filed by source, scans
  of one target, and domains (`example.com` no longer matches `notexample.com`), and the selected
  target is kept across pages, reloads and Back. (#281)

## Credentials

- One credential can be shared with other targets by an explicit, revocable grant. A share makes
  it selectable there; Scans and Hunts on that target still need its own authorization, and the
  credential is only sent to that target. Credentials with active capabilities need the receiving
  target's approval. The credentials page has a library of all credentials. (#282)
- New Scans and Hunts start with the target's credentials selected (never SSH identities); the
  Scan form shows which identities it will run as. (#282)
- A Hunt, or a Scan's interactive login, starts from a live login an earlier Hunt made on the same
  target with the same credential version, instead of logging in again. A login is never reused on
  another target and stops being reused when the credential is rotated, deactivated or unshared.
  (#282)

## Client, launcher and agents

- The MCP findings tool (`shakerscan_findings`) and the exposure graph command no longer fail with
  HTTP 500 on every call. (#283)
- `shakerscan version` works on an installed engine; the launcher help is tidied. (#283)
- Client 0.7.5 ships the current agent guide (credential sharing and login reuse rules). (client
  0.7.5)

## Security, dependencies and delivery

- Dependency and image vulnerability fixes, including PyJWT token-forgery advisories, urllib3 and
  Alpine OpenSSL, and raised fastapi, lxml and pytest floors; Redis 8.10.2; the UI moves to
  Tailwind CSS 4.3 with no intended visual change. (#264, #265, #267, #270, #273, #246)
- The installer hands a pinned older version over to that release's own installer. (#271)
- Release certification now upgrades a real installed stable release; a failed GitHub Actions
  cache export no longer fails an image that was built and pushed. (#275, #284)
- Untrusted-input parsers in the public posture check are property-tested. (#276)

## Known limits

- Filtering findings by proof reads at most 20,000 matching findings; a broader view answers
  HTTP 422 and asks to narrow the list.
- A Scan's login is not kept after the scan, so a Hunt cannot start from it (Hunt-to-Hunt and
  Hunt-to-Scan reuse work).
- Merging duplicate targets does not move their credentials.
- SQLi verification on remote, high-latency targets can still time out within a batch slice.

## Validation

Release-candidate certification, published-version smoke, and stable-channel promotion are required
before 2.6.0 is public.
