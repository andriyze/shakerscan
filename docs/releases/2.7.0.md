# ShakerScan 2.7.0

**Status:** candidate prepared 2026-10-04. Publication and stable-channel promotion are pending.

This candidate brings the changes since 2.5.6 into one release: unified domain and network targets,
more capable operator-driven Hunts, direct SSH investigations, saved target instructions and
actions, PostgreSQL 18, clearer reports, and repairs to proof, request fidelity and secret storage.
The prepared 2.6.0 candidate was not published; its changes are included here.

## Targets and Hunt

- Domains, IP addresses and connected hosts share the target inventory. The Targets page retains
  domain/subdomain grouping and subdomain discovery, with web and network filters. Connected
  Devices shows discovered services and ports and starts network scans on the same asset.
- Startup includes a dedicated network worker with Nmap and Naabu. Operators can opt out with
  `SHAKERSCAN_NETWORK_WORKER_ENABLED=false` or `shakerscan devices stop`, and re-enable it with
  `shakerscan devices start`. Source checkouts use `./scanner.sh` for these lifecycle commands.
- A target's standing authorization is recorded once and reused by Scans and Hunts. Hunt can
  combine authorized web checks, port/service discovery and remote SSH work through its shared
  capability runtime. Network tools retain destination, authority and budget checks.
- Each target can hold one custom skill for authentication guidance, testing priorities and
  exclusions. Hunt loads it at startup and supports delegated instruction CRUD with revision
  checks. Advisory learned knowledge is separate from the operator's saved instructions.
- Saved target actions can be reused and edited with explicit operator control. The Hunt UI brings
  objectives, requests, actions and investigation history together; target and collection pickers
  are searchable. The methodology library includes network discovery and TV, camera, router and
  SSH guidance alongside web methodologies.
- Authorized identities can be reused across HTTP/HTTPS services on the same frozen asset,
  including nonstandard ports and untrusted target certificates. Service-specific evidence keeps
  scheme, port and principal identity; credential grants remain explicit across different targets.
- An unfinished Hunt can receive an explicit budget amendment and resume with the same history.
  Reservations, actual usage, cancellation and paused device work remain distinct; a planner does
  not increase its own authority or budgets.
- Authenticated requests already admitted on another service of the same asset retain their
  reservation if concurrent work exhausts the Hunt budget. Completed or cancelled Hunts and
  revoked authorization still stop credential use.

Hunt remains driven by an active external planner. Saved skills and actions do not run an
investigation in the background. Findings become verified only through deterministic proof.

## SSH investigations

- Hunt sends direct commands through `ssh.exec` when the selected stored SSH credential has an
  explicit command grant. It reuses sessions, supports operator-selected ports, and streams output
  through the live console, API, CLI and MCP adapter.
- SSH logs and diagnostics can run alongside external web or network checks within one Hunt.
  Commands support cancellation and transport closure; remote process termination is reported
  separately and may remain uncertain. Finalized Hunts release idle transports, including Hunts
  finalized after budget exhaustion. Legacy exact-command plans remain available for delegated
  command access.
- SSH authentication settings, console URL handling and saved-action edits survive their normal
  read/edit/save flows. SSH keys and reusable credentials remain encrypted; planner requests carry
  opaque selections rather than raw secrets.

## Scans, findings and evidence

- Scan reports lead with the verdict and separate findings, posture, coverage, release gates and
  activity. Findings support multiple severity filters, server proof states, grouped repetitions
  and guidance matched to the producing check. Target filters persist across navigation.
- Finding identities distinguish checks sharing a CWE and services on different schemes or ports.
  Legacy row adoption and policy-exception migration retain exact matches without granting an
  exception to a different finding. Concurrent saves preserve trustworthy partial output.
- SQLi, XSS, authentication and access-control proof contracts reject incomplete challenges and
  misleading success signals. Completed authentication challenges retain their supported proof
  path. Protected/shared objects and unproven candidates do not become verified findings.
- Managed login and refresh honor explicit failed or unfinished authentication verdicts for JSON,
  header and cookie identities. Valid token aliases, completed MFA and unrelated account metadata
  retain their supported login paths.
- Recorded and imported requests retain their bodies, array mutations, service identity and
  principals through replay and proof. DOM discovery and verification use the deployed module
  layout. TLS checks sharing a CWE keep distinct finding rows.
- Idle workers pick up new scans promptly; starved template endpoints remain eligible for later
  examination. Selected work that was not examined remains a coverage gap.
- Recorded raw HTTP headers and bodies are encrypted at rest, including archive backfills. Large
  archived payloads are hydrated for export, and normal JSON exports redact secrets. Verbatim HAR
  includes captured credentials: it defaults on for loopback publication, requires explicit
  deployment opt-in beyond loopback, and can be disabled with `SHAKERSCAN_HTTP_ARCHIVE_RAW_HAR=0`.
  A reverse proxy or tunnel must be accounted for by the operator; the API cannot detect it from
  its configured publish address.
- Credential profiles may be shared through explicit, revocable target grants. Runs can reuse a
  live login for the same target, principal, credential version and service; rotation, deactivation
  or revoked grants invalidate reuse. MCP and installed-client helper modules are shipped together.

## Upgrade, storage and deletion

- Upgrading from 2.5.6 migrates PostgreSQL 16 into a verified PostgreSQL 18 copy. A failed or stale
  copy does not replace the source data. The rollback copy is retained for 30 days by default, with
  advance notice; active or subsequently used rollback data is protected from automatic removal.
- Startup prepares the credential-encryption key before workers run and reports initialization
  failures. Keep `results/.credential_enc.key` separately: a lost key cannot decrypt saved secrets.
  Root installs refuse API identities belonging to host accounts/groups, normalize numeric IDs,
  persist the operator's selected free identity (`SHAKERSCAN_ROOT_API_UID`) across starts, and move
  the previous identity's files under `results/` to a newly chosen one.
- Backups omit the encryption key by default, including configured aliases, hard links and
  duplicate key files, and also on hosts without python3, where tar excludes the key by name and
  content. `shakerscan backup --include-key` explicitly includes it. Backups still hold `.env`
  (datastore passwords, service tokens, an `AI_API_KEY` saved there) and all evidence, so store
  them as carefully as the host. The newest five
  complete backups are retained by default, and backup listing/deletion handles historical backups
  and `--yes` consistently.
- Target, scan, Hunt, AI-target and Model Intake deletion workflows remove their associated records
  and files, including worker-written artifacts. Deleting live records does not erase independently
  retained backups. AI-provider key migration also compacts Redis persistence.
- AI-target template secrets are masked in headers, parameters and nested lists. Saving unchanged
  masked lists preserves the original secrets and classifications instead of replacing them with
  mask text.

## Delivery and validation

- Candidate E2E, DAST and fault receipts bind the exact source and inspected running image digests.
  Source-checkout diagnostics and caller assertions cannot certify release images.
- Stable promotion checks all five version tags against the accepted image lock before moving any
  `latest` alias, and uses the locked digest references for the move.
- Dependency updates include Redis 8.10.2, Tailwind CSS 4.3 and fixes to image/Python dependencies.
  Release image and dependency checks still run on the final candidate.

This note records the prepared scope, not a completed release certification. Exact-candidate
certification, immutable version publication, public installer smoke and the stable-channel PR
must succeed before the hosted installer advances. Deterministic Model Intake checks are mandatory
in the current certification process; physical KVM/Hugging Face acceptance remains optional.

Known boundaries remain: target/service authorization does not grant another asset's credentials;
SSH execution needs its stored command grant; AI Gate and physical infrastructure support retain
their documented preview/opt-in boundaries; and incomplete scan/Hunt coverage is not a clean bill
of health. Benchmark expectations and declared gaps remain visible rather than being replaced with
claims of universal detection.
