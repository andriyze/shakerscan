# ShakerScan 2.11.1

**Status:** in development on the `release/2.11.1` integration branch.
The client for this release is `shakerscan` 0.11.1.

A patch release: security and correctness fixes, longer time budgets for `thorough` and `deep`
Scans and `thorough` Hunts, and dependency updates. No new features, no schema changes.

## Security

- **`shakerscan record` never follows a redirect with the API token** (client 0.11.1). The
  recorder's HTTP client followed 301, 302 and 303 answers and re-sent `Authorization` to the
  `Location` host, including another origin and from HTTPS to HTTP. It now refuses every redirect,
  like the other client commands, and names the refused origin.
- **Copyable commands pass every target-chosen value as one shell word.** The reproduce, verify,
  replay and check commands on finding pages could carry an unquoted URL, parameter or payload
  chosen by the target, which a shell would expand when pasted. Replay commands stored before the
  upgrade are rebuilt from their stored inputs when read.
- **Capture replay withholds credentials carried in URL paths.** Magic-login, share, invite and
  reset links, cookieless session ids, long random tokens and userinfo in a captured URL are no
  longer replayed, and copies of the page URL in `Referer`, `Origin`, `HX-Current-URL`,
  `Next-Url`, query values and bodies lose the credential. Captures recorded before the upgrade
  are treated the same way when replayed. The display mask used elsewhere is unchanged.
- **Session headers stay on the target's origin across redirects.** A Scan authenticated with
  an API-key or other custom session header sent that header to whatever origin a redirect
  named: curl, httpx, aiohttp, sqlmap, dalfox and nuclei drop only `Authorization` and `Cookie`
  on a cross-host redirect, and an inline `-b` cookie string goes everywhere. A request that
  carries such material now follows a redirect only to the same scheme, host and port, or to the
  same host upgraded from `http` on port 80 to `https` on 443; on that origin it follows exactly
  as `curl -L` does (output, request bodies, cookie jar, `--max-redirs`). `Authorization`,
  `Cookie`, `-u` and `--oauth2-bearer` keep curl's own behaviour, since curl 7.83 and later strip
  them itself. Trade-off: sqlmap, dalfox and nuclei runs that carry the session do not follow
  redirects at all, and a curl request with a custom session header stops at a redirect to
  another origin, so a check whose proof sits behind such a redirect is not reached in a
  custom-header session.
- **Browser sessions send their headers to the target's origin only.** Playwright's extra
  headers went with every request a page made, including images and scripts from other origins
  and redirect hops to another origin, which no route handler sees. A browser context that
  carries session headers (the XSS browser proof, the authenticated browser crawl, the
  interactive browser session once a header is set, the AI widget target) is now confined at the
  network layer: all of its traffic goes through a local proxy that admits only its bound
  origins (scheme, host and port, or the same host upgraded from http on port 80 to https on
  443) and refuses every other connection before it is made. The headers stay the context's own,
  so Chromium keeps its streaming, CORS, cookie and size behaviour; an HTTPS connection elsewhere
  is refused before any byte of the request is sent, and a plain-HTTP one reaches only the local
  proxy. The cost: such a context loads nothing from another origin (a CDN, a third-party
  script, a redirect to another site). Each refusal is listed in the Scan's coverage, the
  browser crawl's and XSS proof's results, the interactive session's action result and the AI
  widget's evidence, without changing a family's status: `session_cross_origin_refused`, and
  `session_navigation_redirect_refused` for a navigation a bound origin redirected elsewhere.
  These confined contexts are granted Chromium's Local Network Access, so an internal
  application on private addresses loads; `private_network_subresource_blocked` is listed where
  Chromium still refuses one. A refused connection is closed unanswered, so the page sees a
  network error (never a response that would read as the other origin's), and WebRTC is
  disabled in these contexts, since it sends UDP outside any proxy. A context that carries only
  cookies is not confined. A custom session header makes a cross-origin request between two bound
  origins non-simple, so Chromium preflights it, as it did before. When an interactive (Hunt or
  AI verification) browser session is given a session header, it moves to a confined context
  that keeps its cookies, localStorage and current URL, but not its sessionStorage or any other
  page the user had open in that session.
- **Scan and Hunt browser actions keep trusted headers on the bound origin.** The browser
  capability's pinned proxy admitted the target's own address written as a host, so a redirect
  to that address as another origin received the trusted headers Chromium carries into redirect
  hops. The pinned proxy of a hostname target now refuses that address as a destination and
  counts it on its receipt (`address_literal_destinations_refused`); every scanner on that path
  (sqlmap, katana, nuclei, dalfox, httpx, ffuf) addresses it by hostname. The browser's tunnel
  also admits only its bound origin's scheme (a TLS record for https, plaintext for http), so an
  https origin's redirect to http on the same port is refused (`scheme_mismatch_refused`), and
  WebRTC is disabled in that browser. The action's result
  and the Scan's coverage list `session_cross_origin_refused` and
  `session_navigation_redirect_refused` when the proxy refused a connection.
- **Dalfox does not use its headless browser with a session.** Its headless verifier and
  `--deep-domxss` run a Chromium outside any proxy that adds the session headers to every
  request a page makes. A session-carrying run now passes `--skip-headless` and no
  `--deep-domxss`, and the Scan's coverage lists `session_header_withheld_from_headless`.
- **Known limit of browser sessions.** A Scan or Hunt browser XSS proof that sends its payload
  in a request body follows a 307 or 308 redirect the way the browser does for the page's own
  navigation, so the redirected request is a GET without the body.
- **A refused-redirect hint names only a plain origin** (client 0.11.1). The suggested
  `shakerscan connect <origin>` / `--url <origin>` used the `Location` host as sent, so a
  crafted `Location` produced a command that ran shell syntax when pasted. The origin is rebuilt
  from a validated host and port and quoted, or the hint says `<origin>`.
- **Path-segment SQL injection replay commands are quoted like the others.** Replay commands for
  a marked path segment (`/products/1*`) passed the stored URL to the shell with control
  characters and a backslash-quote intact.
- **A token used as a bare query name is masked.** A URL carrying a credential as a query key
  without a value (`?<token>`) showed it in capture request lists, replay plans and receipts.
- **Copy commands stored by earlier releases are rebuilt or shown as text only.** A finding's
  stored manual verification commands are rebuilt from the evidence's URL and path when read; a
  stored command that cannot be rebuilt or checked is shown as recorded text without a copy
  button.
- **The client shows server text without terminal control characters** (client 0.11.1). Public
  check results, instance health answers and error messages could carry escape sequences or a
  carriage return that rewrote the terminal; they are shown as visible text now.
- **aiohttp 3.14.5** in the scanner image, for CVE-2026-111064 (GHSA-2g87-pp6c-29x5, high),
  published after 2.11.0 (fixed in 3.14.4).
- **certifi 2026.10.19** in every Python image and tool lock, for GHSA-6q48-6c7w-9gw2 (critical):
  2026.7.22 bundles emSign root certificates that were compromised. The image vulnerability gate
  refused the older version. pip 26.2.2 in the Model Intake image's pip-audit environment, whose
  vendored copy of certifi carries the same fix.

## Fixes

- **A pre-2.6 install is refused instead of starting on a new, empty database.** An install that
  still holds PostgreSQL 16 data in `postgres-data` and has no migrated `postgres-cluster` no
  longer passes the start checks; the refusal names the backups to restore from. This corrects
  2.11.0, whose notes said such a start refuses. `redis reset` refuses in that state before it
  changes anything.
- **A pre-upgrade backup is taken when the release record does not name the running API's
  image** (running or stopped), or when that container cannot be inspected.
- TLS legacy-protocol probes run only when the action's reservation pays for them.
- An open-redirect probe that got no answer stays inconclusive and is probed again on resume,
  instead of counting as examined.
- Exposure service pages give a device and its host target, which share an id, their own
  inventories.
- Opening a browser capture by an IPv6 target URL finds the target.
- A credentials link with `?target=<url>` reads search pages until it finds the origin; a failed
  read is reported as such, not as a missing target.

## Finding accuracy

- **Reflected XSS is browser-proven again.** The Scan's browser proof declared an adapter identity
  the capability registry did not accept, so every proof was rejected before it ran and no
  "Verified cross-site scripting" finding could be produced. A proof that breaks now leaves its
  family partial and the grade provisional, instead of complete.
- **A CORS policy that reflects any origin is detected.** The receipt redactor rewrote the echoed
  `Access-Control-Allow-Origin` before the check compared it with the probe origin.
- **Reproduce and check commands work from masked evidence.** Engine-authored probe values (the
  open-redirect target, the GraphQL introspection document) are kept; a stored URL whose query
  the scanner masked is not replayed as stored.
- **Active Nuclei templates run against the scanned URL, not a discovered endpoint's path**, on
  every profile, so host-level templates such as exposed-service checks match. Each active-template
  attempt now targets the directory of the URL the Scan targets (`/app/login.php` runs at
  `/app/`), and then the root of every other origin the Scan discovered; plans, holds and attempts
  are unchanged, only the URL each attempt targets. A host with more endpoints than template
  windows no longer repeats a window at the same URL. A finding a 2.11.0 Scan matched at a
  discovered subpath with a template that asks only its base URL (108 of the permitted templates)
  may not be reproduced by 2.11.1 and then reads as fixed: those templates now run at the Scan's
  base and the other origins' roots, not at discovered subpaths.
- **Active-template coverage counts every origin.** `nuclei_active.template_windows` counts
  (origin, template window) pairs and lists each origin's run and total, so a second origin that
  ran 11 of 39 windows no longer reads as 39 of 39. A thorough or deep Scan whose active templates
  did not all run at one of its allowed origins reads partial, with the reason
  `template_windows_incomplete_on_origin`. Each parallel scan part starts its template windows at its
  own offset, so alone it runs as many windows as before and the parts together run at least as
  many; the merged coverage counts each (origin, window) pair once and says how many pairs two
  parts both ran (`repeated_pairs`);
  an attempt resumed from before the upgrade is kept and never sent again, and a window it ran at
  a discovered endpoint's path is listed apart (`legacy_windows_run`), not counted at an origin.
- **Known limit:** a thorough or deep host whose endpoints span more than one origin and whose plan
  has fewer than 39 positions per origin reads partial on active templates
  (`template_windows_incomplete_on_origin`): 2.11.1 does not change the plan, and a later release
  will plan the windows per origin.
- **Active Nuclei never runs a template that requests a heap dump**, on any profile. A test checks
  the bundled template set, so a template update cannot bring one back.
- **A SQLi point sqlmap marked in a URL path segment** (`/products/1*`, `#1*`): the brief and replay
  commands use the unmarked URL with the payload in that segment, the database name comes from
  sqlmap's summary line, and a retest declines (inconclusive, nothing sent) because the retest
  prover injects only query and form parameters.
- **TLS:** a weak signature or key no longer also raises "chain is not trusted"; the certificates the
  server sent are read correctly on Python 3.12; weak-cipher evidence comes from the weak handshake;
  reproduce commands show the weakness.
- **Finding pages:** a page titled "Directory listing" is no longer a verified listing without a
  real listing; GraphQL findings get GraphQL commands and advice; JDK 9+ stack frames are
  recognized; non-secret key names are not masked; weak-CSP advice never loosens framing; Tomcat's
  Apache-Coyote is not reported as Apache httpd; DNS posture findings use the target's origin; the
  coverage page and the stored grade agree.

## Authenticated scans and Hunts

- **A credential profile left with no capability list now covers the crawl.** On an HTTP identity
  it grants every read-only capability that uses the identity (probe, crawl, browser crawl,
  content discovery, spec ingest, passive templates, safe collection replay, browser navigation);
  sign-in kinds also keep their session capabilities. Active verifiers are never a default and
  still need an approved elevation. Profiles saved with a list keep it. New Scan says when the
  attached profile leaves the crawl or a selected verifier running anonymously.
- **A crawl or content discovery that carries a session leaves action links alone:** sign-out,
  delete, disable, reset and similar paths and query actions are not requested with the session.
- **XSS and SQLi verifiers no longer fail with zero requests** when a replayed collection request
  and a declared endpoint share a route.
- **A signed-in crawl starts where the signed-in area is.** A crawl or browser crawl that carries
  the session also starts at the page the sign-in landed on and at the GET seed endpoints on its
  origin (pages before API routes, at most 20), so an area linked from nowhere the target's root
  reaches (a `/hub/` behind `/hub/login`) is crawled with the session. The target keeps its whole
  time box: the static crawl runs its inputs side by side under its one rate limiter and request
  ceiling, and the browser crawl adds only its first seed, so the target keeps half of that box.
  Action paths (also percent-encoded), route templates and the profile's own sign-in page are
  never a seed, and a seed the crawler cannot take is left out instead of failing the crawl.
- **The credential profile's own sign-in endpoint is tested at a lockout-safe pace.** An
  authenticated balanced scan of a test application sent about 1,460 injection requests to the
  sign-in form it used. On that one endpoint (a request with a body to the sign-in path, its
  routing query included, or to the form's action) the SQLi and XSS verifiers keep their full
  payloads (sqlmap level 2 / risk 2, Dalfox's own payloads for the body), send at most 20 requests
  a minute, one attempt at a time, and share one probe set per verifier across every candidate
  and round of the scan: sqlmap's whole level-2 ladder (473 requests per tested field, at most
  four fields) and 64 Dalfox requests per field, Dalfox stopping at its first verified finding.
  A check the probe set leaves without a verdict is inconclusive, never negative, and its family
  reads partial with the reason `auth_endpoint_probe_limited`. A GET to the sign-in page and
  every other endpoint keep their full holds, and plans are unchanged. In a scan split across
  parallel parts each part paces the endpoint by the number of parts and holds its own probe set.
- **A credentialed scan admitted on the target's standing authorization records a credential-tier
  receipt**, as New Scan does, whether or not the request named that authorization: the scan is
  bound to a receipt derived from it (same scope and approver, a seven-day bound, the scan and the
  source named in it), which covers the scan's credentials and the source's tier only and
  authorizes nothing else. It ends with its source: every revocation path revokes it (also one
  filed under an application service from its host's authorization), and the running-scan check
  and the worker's credential check, the only check a passive credentialed scan has, refuse it
  once the source no longer stands. Who may start the scan is unchanged.
- A browser session the session store refuses ends the Hunt action with its reason.
- A scan refused at admission leaves no target behind and keeps its blocked audit record.
- **ASM:** a completed recon fills the target's endpoint inventory from what the scan observed,
  without probing the target again; a target without an inventory can be opened from the ASM page;
  the continuous-testing controls are hidden where the deployment does not offer them. Several web
  apps on one host (different ports) are each listed in their domain group, so every target with
  an inventory appears on the Coverage page. `GET /targets/grouped` therefore lists a domain's
  other root targets, such as other ports of one host, in `subdomains` and counts them in
  `subdomain_count`, `total_count`, `total_findings` and `total_targets`; `best_score` and
  `latest_scan` remain the group root's own values (the root is the last root target in URL
  order). Only an ASM batch or recon scan is labelled as hidden from the Scans list, in the
  view and in the 409 an ASM action gets while a scan runs.
- **Client 0.11.1:** `shakerscan scan help` prints the options instead of submitting a scan, under
  its own name (`usage: shakerscan scan`); `hunt call` exits 2 when the action was refused; a
  certificate the client does not trust names `SSL_CERT_FILE`, once per line; a state-changing
  scan from the terminal relies on the target's standing authorization; a submitted scan prints
  the families it runs and, on `fast` or `balanced` without them, how to add active templates
  (`--include-family nuclei_active`); `hunt start --credential-ref` takes the short slot names
  (`primary=`, `secondary=`, ...). The Hunt page keeps decided permission requests visible.

## Time budgets on `thorough` and `deep`

`fast` and `balanced` Scans plan exactly as in 2.11.0; a test fixture generated on 2.11.0 pins
them.

- **Active Nuclei runs every template window.** Each endpoint attempt runs one window of 30
  templates. 2.11.0 ran as many windows as a host had endpoints, so a small host ran 1-6 of the 39
  windows of the active set. `thorough` and `deep` direct Scans that include active templates
  now run all 39. Coverage shows `nuclei_active.template_windows` (windows run of total) on every
  profile, and so does the scan page; a sweep whose every (origin, window) pair ran is complete
  in the report and on the page, not partial for endpoints the plan left without a position
  (the templates run at the origins, not at each endpoint).
- **The standard active set runs the active templates on `thorough` and `deep`.** The
  `standard_active` preset (New Scan's "Standard active", and `--active-testing` in the terminal)
  now adds `nuclei_active` on those two profiles; `fast` and `balanced` resolve and plan exactly
  as before. A scan whose request or mutation ceiling was lowered below the profile's keeps the
  earlier set, since the sweep's admission hold would not fit; `--include-family nuclei_active`
  still adds it, and `--exclude-family nuclei_active` removes it on any profile. The scan
  contract states the addition (`family_preset_profile_additions`).
- **SQLi extensions are sized to the techniques left.** 2.11.0 gave an extension the lane's whole
  time share and paced its requests to fill it (6.25 s per request on `thorough`). Extensions now
  hold what the remaining techniques need, at about 0.5 s per request.
- **Later rounds step down to a slice the remaining budget affords** instead of planning one the
  allocator refuses.
- **Request-body candidates get at least one attempt** when the Scan may send state-changing
  requests, through a floor in the first slice or a floor extension.
- **A lowered `max_duration_seconds` also lowers the tool wall** when no tool wall is given.
- **`thorough` Hunts:** `sqli.verify` reserves 900 requests / 540 s and `xss.verify` 1,800 requests
  / 480 s, so a call can finish; a call the Hunt cannot fund steps down to the registry hold.

Expect `thorough` Scans of small hosts to take about 25 minutes instead of about 4.

## Upgrade notes

- No database schema changes and no new settings.
- `thorough` and `deep` Scans run longer and send more requests to each host than on 2.11.0 (for
  the active template windows, about 2,200-2,600 requests per small host at the unchanged 2
  requests per second). Their standard active set now includes the active templates, so a
  `thorough` or `deep` scan with active testing runs them unless it excludes `nuclei_active`.
