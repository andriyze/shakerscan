# ShakerScan 2.11.1

**Status:** in development on the `release/2.11.1` integration branch.
The client for this release is `shakerscan` 0.11.1.

A patch release: security and correctness fixes, longer time budgets for `thorough` and `deep`
Scans and `thorough` Hunts, and dependency updates. No new features, no schema changes.

## Security

- **`shakerscan record` never follows a redirect with the API token** (client 0.11.1). The
  recorder's HTTP client followed 301, 302 and 303 answers and re-sent `Authorization` to the
  `Location` host, including another origin and from HTTPS to HTTP. It now refuses every redirect,
  like the other client commands, and names the refused origin.
- **Copyable commands pass every target-chosen value as one shell word.** The reproduce, verify,
  replay and check commands on finding pages could carry an unquoted URL, parameter or payload
  chosen by the target, which a shell would expand when pasted. Replay commands stored before the
  upgrade are rebuilt from their stored inputs when read.
- **Capture replay withholds credentials carried in URL paths.** Magic-login, share, invite and
  reset links, cookieless session ids, long random tokens and userinfo in a captured URL are no
  longer replayed, and copies of the page URL in `Referer`, `Origin`, `HX-Current-URL`,
  `Next-Url`, query values and bodies lose the credential. Captures recorded before the upgrade
  are treated the same way when replayed. The display mask used elsewhere is unchanged.
- **Session headers stay on the target's origin across redirects.** A Scan authenticated with
  an API-key or other custom session header sent that header to whatever origin a redirect
  named: curl, httpx, aiohttp, sqlmap, dalfox and nuclei drop only `Authorization` and `Cookie`
  on a cross-host redirect, and an inline `-b` cookie string goes everywhere. A request that
  carries such material now follows a redirect only to the same scheme, host and port, or to the
  same host upgraded from `http` on port 80 to `https` on 443; on that origin it follows exactly
  as `curl -L` does (output, request bodies, cookie jar, `--max-redirs`). `Authorization`,
  `Cookie`, `-u` and `--oauth2-bearer` keep curl's own behaviour, since curl 7.83 and later strip
  them itself. Trade-off: sqlmap, dalfox and nuclei runs that carry the session do not follow
  redirects at all, and a curl request with a custom session header stops at a redirect to
  another origin, so a check whose proof sits behind such a redirect is not reached in a
  custom-header session.
- **Browser sessions send their headers to the target's origin only.** Playwright's extra
  headers went with every request a page made, including images and scripts from other origins
  and redirect hops to another origin. The XSS browser proof, the authenticated browser crawl,
  the interactive browser session and the AI widget target now add session headers only to
  requests to the target's scheme, host and port; requests elsewhere are sent untouched, and
  cookies keep their own domain scoping. Two effects to know: when a target page redirects a
  navigation within its origin, the next page is requested with the session cookies but without
  the session header, and a target page delivered this way is treated by Chromium as public, so
  it cannot load resources from another origin on a private or loopback address.
- **A refused-redirect hint names only a plain origin** (client 0.11.1). The suggested
  `shakerscan connect <origin>` / `--url <origin>` used the `Location` host as sent, so a
  crafted `Location` produced a command that ran shell syntax when pasted. The origin is rebuilt
  from a validated host and port and quoted, or the hint says `<origin>`.
- **Path-segment SQL injection replay commands are quoted like the others.** Replay commands for
  a marked path segment (`/products/1*`) passed the stored URL to the shell with control
  characters and a backslash-quote intact.
- **A token used as a bare query name is masked.** A URL carrying a credential as a query key
  without a value (`?<token>`) showed it in capture request lists, replay plans and receipts.
- **Copy commands stored by earlier releases are rebuilt or shown as text only.** A finding's
  stored manual verification commands are rebuilt from the evidence's URL and path when read; a
  stored command that cannot be rebuilt or checked is shown as recorded text without a copy
  button.
- **The client shows server text without terminal control characters** (client 0.11.1). Public
  check results, instance health answers and error messages could carry escape sequences or a
  carriage return that rewrote the terminal; they are shown as visible text now.
- **aiohttp 3.14.5** in the scanner image, for CVE-2026-111064 (GHSA-2g87-pp6c-29x5, high),
  published after 2.11.0 (fixed in 3.14.4).

## Fixes

- **A pre-2.6 install is refused instead of starting on a new, empty database.** An install that
  still holds PostgreSQL 16 data in `postgres-data` and has no migrated `postgres-cluster` no
  longer passes the start checks; the refusal names the backups to restore from. This corrects
  2.11.0, whose notes said such a start refuses. `redis reset` refuses in that state before it
  changes anything.
- **A pre-upgrade backup is taken when the release record does not name the running API's
  image** (running or stopped), or when that container cannot be inspected.
- TLS legacy-protocol probes run only when the action's reservation pays for them.
- An open-redirect probe that got no answer stays inconclusive and is probed again on resume,
  instead of counting as examined.
- Exposure service pages give a device and its host target, which share an id, their own
  inventories.
- Opening a browser capture by an IPv6 target URL finds the target.
- A credentials link with `?target=<url>` reads search pages until it finds the origin; a failed
  read is reported as such, not as a missing target.

## Finding accuracy

- **Reflected XSS is browser-proven again.** The Scan's browser proof declared an adapter identity
  the capability registry did not accept, so every proof was rejected before it ran and no
  "Verified cross-site scripting" finding could be produced. A proof that breaks now leaves its
  family partial and the grade provisional, instead of complete.
- **A CORS policy that reflects any origin is detected.** The receipt redactor rewrote the echoed
  `Access-Control-Allow-Origin` before the check compared it with the probe origin.
- **Reproduce and check commands work from masked evidence.** Engine-authored probe values (the
  open-redirect target, the GraphQL introspection document) are kept; a stored URL whose query
  the scanner masked is not replayed as stored.
- **Active Nuclei never runs a template that requests a heap dump**, on any profile. A test checks
  the bundled template set, so a template update cannot bring one back.
- **A SQLi point sqlmap marked in a URL path segment** (`/products/1*`, `#1*`): the brief and replay
  commands use the unmarked URL with the payload in that segment, the database name comes from
  sqlmap's summary line, and a retest declines (inconclusive, nothing sent) because the retest
  prover injects only query and form parameters.
- **TLS:** a weak signature or key no longer also raises "chain is not trusted"; the certificates the
  server sent are read correctly on Python 3.12; weak-cipher evidence comes from the weak handshake;
  reproduce commands show the weakness.
- **Finding pages:** a page titled "Directory listing" is no longer a verified listing without a
  real listing; GraphQL findings get GraphQL commands and advice; JDK 9+ stack frames are
  recognized; non-secret key names are not masked; weak-CSP advice never loosens framing; Tomcat's
  Apache-Coyote is not reported as Apache httpd; DNS posture findings use the target's origin; the
  coverage page and the stored grade agree.

## Authenticated scans and Hunts

- **A credential profile left with no capability list now covers the crawl.** On an HTTP identity
  it grants every read-only capability that uses the identity (probe, crawl, browser crawl,
  content discovery, spec ingest, passive templates, safe collection replay, browser navigation);
  sign-in kinds also keep their session capabilities. Active verifiers are never a default and
  still need an approved elevation. Profiles saved with a list keep it. New Scan says when the
  attached profile leaves the crawl or a selected verifier running anonymously.
- **A crawl or content discovery that carries a session leaves action links alone:** sign-out,
  delete, disable, reset and similar paths and query actions are not requested with the session.
- **XSS and SQLi verifiers no longer fail with zero requests** when a replayed collection request
  and a declared endpoint share a route.
- A browser session the session store refuses ends the Hunt action with its reason.
- A scan refused at admission leaves no target behind and keeps its blocked audit record.
- **ASM:** a completed recon fills the target's endpoint inventory from what the scan observed,
  without probing the target again; a target without an inventory can be opened from the ASM page;
  the continuous-testing controls are hidden where the deployment does not offer them.
- **Client 0.11.1:** `shakerscan scan help` prints the options instead of submitting a scan;
  `hunt call` exits 2 when the action was refused; a certificate the client does not trust names
  `SSL_CERT_FILE`; a state-changing scan from the terminal relies on the target's standing
  authorization. The Hunt page keeps decided permission requests visible.

## Time budgets on `thorough` and `deep`

`fast` and `balanced` Scans plan exactly as in 2.11.0; a test fixture generated on 2.11.0 pins
them.

- **Active Nuclei runs every template window.** Each endpoint attempt runs one window of 30
  templates. 2.11.0 ran as many windows as a host had endpoints, so a small host ran 1-6 of the 39
  windows of the active set. `thorough` and `deep` direct Scans now run all 39. Coverage shows
  `nuclei_active.template_windows` (windows run of total) on every profile.
- **SQLi extensions are sized to the techniques left.** 2.11.0 gave an extension the lane's whole
  time share and paced its requests to fill it (6.25 s per request on `thorough`). Extensions now
  hold what the remaining techniques need, at about 0.5 s per request.
- **Later rounds step down to a slice the remaining budget affords** instead of planning one the
  allocator refuses.
- **Request-body candidates get at least one attempt** when the Scan may send state-changing
  requests, through a floor in the first slice or a floor extension.
- **A lowered `max_duration_seconds` also lowers the tool wall** when no tool wall is given.
- **`thorough` Hunts:** `sqli.verify` reserves 900 requests / 540 s and `xss.verify` 1,800 requests
  / 480 s, so a call can finish; a call the Hunt cannot fund steps down to the registry hold.

Expect `thorough` Scans of small hosts to take about 25 minutes instead of about 4.
