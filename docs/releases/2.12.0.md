# ShakerScan 2.12.0

**Status:** integration candidate on `release/2.12.0`; it follows 2.11.4.
The client for this release is `shakerscan` 0.12.0 (`shakerscan agent --target`, saved logins for
Hunts, handoff ids).

2.12.0 carries the Hunt work prepared as 2.11.5 (never published), the fixes to it, saved logins
for Hunt sign-in, network and web recon that identify services by what they answer instead of by
their port, target liveness, and Targets pages that stay fast at thousands of targets.

**Upgrade.** Upgrade in place from 2.11.4 (or any 2.11 release). The first start creates the
`target_liveness` table and a trigger on `scans` in the always-run migration path; nothing existing
is rewritten. Service and exposure records kept by earlier releases gain their components when
read. A `sqli.verify` call that 2.11.1 to 2.11.4 queued runs after the upgrade; a queued scanner
call whose hold this release cannot match is released and settled instead of staying reserved. A
rollback restores the pre-upgrade database dump, as for every release (`docs/upgrade-and-rollback.md`).

## Hunt

- **A Hunt can log in and reuse its own session.** A response capture of `Set-Cookie` reads any
  response that carries it, a 302/303 login answer included, and holds the cookies as
  `name=value` pairs for a later request's `Cookie` header (`request_bindings`). The value stays in
  the worker; the planner gets a reference. A captured cookie is sent back only to the origin
  (scheme, host and port) that set it. A capture the response does not carry no longer fails the
  request: it is listed in `captures_missing`. The answer shows the response's cookie names and
  security attributes (`set_cookie_metadata`), never their values, and the exact
  `request_bindings` entry that sends the session.
- **Saved logins.** A person attaches a saved login of the target (a form or JSON login profile)
  to a Hunt at start (`saved_logins` on `POST /hunts`, `shakerscan hunt start --saved-login
  PROFILE_ID[=LOGINS]`) or approves the planner's `login.use` permission request; `shakerscan agent
  --allow login.use:<saved-login-id>` pre-authorizes it, and a `login.use` launch bound attaches it
  when the Hunt starts. The planner binds it by reference in the login's own POST, and an answer
  that shows a sign-in form carries the ready request. The worker fills the values after
  rechecking the grant, the profile version and the login URL, only on the Hunt's own host. The
  login needs active testing, not state-changing permission, and counts against the attachment's
  login count. Its answer is reduced to its status and cookie names. The secret is masked wherever
  a later answer echoes it (the body sample, the page outline, the response headers shown, a
  redirect's Location and cookie names, verbatim or HTML-, JSON-, URL- or base64-encoded) and is
  never given a `withheld://` reference. See `docs/hunt-saved-logins.md`.
- **The planner sees the page.** An HTML answer carries `html`: title, links, forms (method,
  action, field names and types) and visible text without `<style>`/`<script>`, built from the page
  as the body sample's masking left it, so a value withheld there (a `textarea name=password`, an
  element `id="api_key"`, a password column) is withheld in the outline too. A repeated attribute
  reads the first one, as browsers do.
- **`artifact.inspect` reads a signed-in page** with `session_ref`, `as_principal` or a captured
  session cookie, under the rules of `http.request`.
- **Scanners and verifiers run signed in.** `web.crawl`, `web.content_discover`, `templates.scan`,
  `xss.verify` and `sqli.verify` take `as_principal`, `session_ref` or the Hunt's captured login
  and send that identity on every request, under the Hunt's approval receipt and credential
  allowance. A signed-in header value carrying a scanner's own marker (ffuf `FUZZ`, sqlmap `*`,
  nuclei `{{`) is refused, and signed-in sqlmap skips the session's cookies. `xss.verify` on a URL
  with a server query and an anchor (`/search?q=1#results`) runs signed in with Dalfox.
- **Body tests.** `sqli.verify` and `xss.verify` test POST, PUT and PATCH bodies (`method`,
  `body_field_names`, `injection_field`, optional `content_type`) with the Hunt's state-changing
  permission. Their requests are held and settled in a ceiling of their own,
  `max_verifier_write_requests` (fast 7,200, balanced 36,000, thorough 144,000), shown beside the
  state-changing ceiling, which keeps bounding the planner's own writes.
- **A verified `sqli.verify` becomes a finding.** When sqlmap reports a vulnerable parameter the
  call named, the same action runs the Scan's deterministic SQL injection proof against the same
  request, signed in as the call was. A proof that holds becomes a verified critical finding
  (CWE-89); sqlmap's report alone stays a candidate. The proof is the action's second phase under
  one deadline: no proof request starts after it, a cancellation or timeout becomes the action's
  outcome, and the finish time is taken after the last phase.
- **One secrecy boundary.** Every observation and job result a Hunt scanner action publishes passes
  one sanitizer before the receipt, the record, endpoint knowledge or a finding sees it: every value
  the action's identity sent (each cookie value, an `Authorization` credential, Basic user and
  password, a JWT and its parts) in any encoding the target may echo it in, and labelled secrets in
  target text. The SQL injection proof's excerpt is masked with the request's own header values
  before it is shortened, so an error page that echoes `Cookie:` or an `HTTP_COOKIE` row shows no
  session. Only a captured cookie value shaped like a session secret is withheld for the rest of the
  Hunt, so a target cannot blind the planner with ordinary cookie text.
- **Signed-in evidence and retests.** A finding or candidate proved signed in records
  `evidence_principals`. It is not queued for an anonymous retest; its detail says to run a new
  signed-in Hunt (or a new signed-in Scan for a signed-in Scan's finding).
- **Handoffs.** A Hunt start may carry a handoff id (`GET /hunts?handoff_id=`, `shakerscan hunt list
  --handoff-id`); a start a person's decision holds tells the agent to continue with the Hunt its
  handoff id names, never the newest Hunt of the target. Every recovery command a person is told
  to run names the instance it came from with `--url`.
- **Queue lanes.** Short Hunt calls have their own lane, so a backlog of long actions never stops
  them being leased. A Hunt may have two long actions in flight per live agent-tool worker (at
  most 16).
- Smaller capability answers over MCP: the compact view drops the duplicate
  `result.receipt.observations`.

## Recon and services

- **Services are named by what they answer, never by their port.** Native read-only protocol
  adapters identify SSH, FTP, SMTP (with STARTTLS), POP3, IMAP, Telnet, MySQL/MariaDB, PostgreSQL,
  Redis/Valkey, MongoDB, Elasticsearch/OpenSearch, Memcached, SMB2, RDP, VNC, PPTP, OpenVPN, MQTT,
  AMQP, and DNS, NTP, IKE and OpenVPN over UDP. Product, upstream version and the exact reported
  string (with its build suffix) are separate fields. Nmap's "unknown" stays unknown with an
  explicit `port_hint`; VPN types are no longer named from the port number.
- **A handshake is not access.** A MongoDB `isMaster`, a Redis answer, an Elasticsearch
  `cluster_name` or a Memcached `STAT` banner no longer reports "Unauthenticated access".
  Authentication stays "not tested" unless a bounded read-only command ran without credentials,
  named as the finding's proof; an identified database without one is "exposed".
- **Every address of a host.** A device or server scan of a hostname with several A/AAAA records
  scans one pinned child per admitted address (up to 8); services merge per transport and port, a
  port that answers differently per address claims neither identity, and the scan is complete only
  when every child was. A new `server` device class prioritises administration, mail, VPN,
  database, cache, broker and container control-plane ports. Each address records its coverage;
  ranges left incomplete run first next time.
- **CDN edges.** A Cloudflare edge address is examined only on the web ports the edge proxies and is
  labelled "application assessed through the CDN; origin network not assessed". A device scan's
  `server_name` examines an explicitly authorized origin address under the application's Host/SNI.
- **Large domains resolve fully.** Subdomain discovery resolved only the first 300 names of an apex
  and added at most 100 as targets. Every name is now resolved and every name with an address
  becomes a target, up to a 10,000-name bound; the Scan's DNS deadline grows with the number of
  names (at most 30 minutes).
- **Product recipes (`web.identify`).** A Scan with recon sends a few fixed read-only GETs per
  product to identify the components behind an origin: Jenkins, Grafana, GitLab, Nexus, Keycloak,
  WordPress and its plugins, Kibana, phpMyAdmin, Tomcat Manager, Webmin, and the FortiGate,
  GlobalProtect, Ivanti, Citrix and Cisco ASA gateways. Every base path gets a negative control, so
  a site that answers every path alike produces no match; versions come only from fields the
  product uses to state them.
- **Several components per listener.** The service inventory keeps the edge, web server,
  application and plugins of a listener as separate components, each with product status, version
  status (reported / inferred range / unknown), provenance and per-field freshness. Advisory
  applicability is "affected" only for an identified product with a reported version inside an exact
  range and no distribution package marker; otherwise it is "unresolved" with the missing evidence
  named. The service view has a Components tab.

## Targets

- **Target liveness.** Each target records DNS (resolves / no record / resolver error), reachable,
  live, the addresses and ports tried, the last check and why it is not live. Checks are passive
  (at most one `GET /` per web port, no body or credentials, redirects not followed; at most 4
  ports, 8 connections and 15 s), run on add, before a Scan, every 12 hours and on demand
  (`POST /targets/{id}/liveness`, "Check now"). Blocked scopes and archived targets are never
  contacted. See `docs/target-liveness.md`.
- **Targets list at scale.** The list loads 25 domain groups of at most 20 targets; a larger group
  opens as its own keyset list of 50 per page (`GET /targets/inventory?domain=`). A Liveness column
  and a server-side Liveness filter with counts (`liveness=`), and a Liveness card on the target
  page. Measured at 500 and 2,000 targets on PostgreSQL; the Findings list already pages on the
  server.
- **Retests on private origins.** A retest that reaches a finding's private origin and does not
  reproduce it reads likely fixed; one that cannot reach it stays inconclusive and says why.
- **Browser retests** wait for a quiet spell after the last request before reading the marker, and
  tell requests apart by their query names (`?public=1` from `?private=1`).
- `GET /targets/lookup` answers which registered target a URL names; `shakerscan targets
  unauthorize` uses it, so a URL with a path that `authorize` registered is found again. A target
  named by an IPv6 literal URL is accepted.

## Client 0.12.0

- `shakerscan agent --target ID [--saved-action ID]` starts the agent session on that target (the
  managed UI prints the command with the page's target and saved action).
- `shakerscan agent --allow login.use:<saved-login-id>` and `shakerscan hunt start --saved-login`.
- `shakerscan hunt list --handoff-id`.
- Recovery commands name their instance with `--url`; `targets unauthorize` finds a URL with a
  path; IPv6 literal URLs are accepted.

## Known limits

- Web product detection (`web.identify`) has its own allowance of 121 requests and 180 s on top of
  the Scan's limits. The UI does not show this allowance yet.
- A saved login's secret shorter than six characters is not masked in later pages (it would match
  ordinary text), and a target that echoes it in another encoding (hex, reversed) is not recognised;
  the login's own answer is still reduced to its status.
- The login request's body, with the saved login's values, is kept in the private HTTP archive:
  masked views omit it, a raw archive export includes it.
- A saved login works only when the form page and the POST path match (a page `/login` that posts
  to `/session` cannot be used). No CSRF field is filled automatically. Saved logins apply to web
  and API Hunts only.
- Body tests name top-level fields only (no nested JSON paths), and every field carries an inert
  placeholder, so a field that must hold a fresh token is not filled.
- The SQL injection proof covers a query parameter or a body field; a vulnerable path segment or
  header stays a candidate. The proof uses what the action's hold has left after sqlmap (at most
  14 requests and 60 seconds); a run that spent the whole hold records `proof_unfunded`.
- `web.browser_crawl` stays anonymous in a Hunt, and an `xss.verify` the pinned browser proves (a
  URL-fragment-only or DOM parameter) refuses a session.
- Liveness is checked from the API's network position: a target only a remote worker can reach
  shows as unreachable even when its Scans succeed. UDP services are not checked, and a service that
  neither speaks HTTP nor sends a banner first (for example Redis) shows as Reachable, not Live.
- CDN edges are recognised from Cloudflare's published ranges; other CDNs are named only from their
  response headers, so a server that sends a CDN's header (`Server: cloudflare`, `CF-Ray`) is labelled
  as assessed through that CDN although its full port scope still runs.
- A large apex can add up to 10,000 subdomain targets, and a Scan's DNS step can hold for up to 30
  minutes on a slow resolver; names it could not check still become targets. UDP silence is inconclusive. WireGuard is listed as not identifiable, and
  PostgreSQL is identified without a version.
