# ShakerScan 2.3.5

The agent kit works against a connected remote instance, and the targets page follows the
workspace capability manifest. Upgrade in place from 2.3.4; 0.8.18 remains the oldest directly
certified upgrade base. No change to the deterministic proof boundary.

## Changes

### One way to call the API from an agent session (#132)

- `shakerscan api METHOD PATH [JSON]` (`scripts/api_cli.py`, a launcher subcommand shipped by the
  installer) knows the base URL (`--api-url`, `SHAKERSCAN_API_BASE`, `SHAKERSCAN_API_URL`, default
  loopback), reads a credential from `SHAKERSCAN_API_TOKEN_FILE` or `SHAKERSCAN_API_TOKEN`, sends
  it only over HTTPS, prints the JSON answer, and on an error prints the instance's own detail.
- The agent kit (AGENTS.md, the `.claude` commands and agents, the shakerscan, content-discovery,
  js-analyze and ai-security-session skills) calls the API only through it, so the same
  instructions work against a local engine and against a remote, authenticating instance such
  as ShakerScan Enterprise. `scripts/scan_cli.py` sends the same bearer token the Hunt CLI does.
  The session-start hook has a managed-instance path (no Docker, no queue route). AGENTS.md
  explains a connected remote instance.

### The client carries the kit (#133)

- Client 0.3.0 (`client/`, published separately as `client-v0.3.0`): `shakerscan agent
  [claude|codex|opencode]` materializes the kit into a workspace against the connected
  instance; `shakerscan api` and `shakerscan scan` are the runtime CLIs against it.

### Targets page (#131)

- The "Authorize for active testing (once)" button follows the `target_authorization` workspace
  capability: a managed deployment that records the authorization itself when active testing
  starts declares it unavailable, and the page says so instead of showing the button. Standalone
  deployments are unchanged.

## Upgrade

Upgrade in place from 2.3.4. No migration.
