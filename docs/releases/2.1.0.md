# ShakerScan 2.1.0

**Published 2026-09-04.** The Model Intake image split on the 2.0 platform. The installer contract grows from four
published images to five; no schema or capability-authority change; upgrade in place.

## Changes

- Model Intake ships as its own image, `shakerscan/shakerscan-model-intake`: the scanner runtime plus
  the artifact-scanning toolchain (semgrep, modelscan, fickling, safetensors, pip-audit, trivy,
  osv-scanner and their databases). The scanner and API images no longer carry that toolchain and
  scan clean without vulnerability waivers; the two build-tool waivers now apply only to the Model
  Intake image, where the pip-audit environment that vendors them legitimately lives.
- Model Intake scans run on a dedicated, always-on `model-intake-worker` that consumes its own
  `model_intake_jobs` queue, isolated from Web DAST slots the way the agent-tool worker already is.
  A Web DAST worker never picks up Model Intake work. The sandbox runs the same Model Intake image.
- Release engineering: every push to `main` now builds the full image set once (`build-on-main`), the
  stable-channel promotion records the RELEASES.md ledger row itself, the certified receipt records the
  measured DAST recall, the public install smoke picks free ports, and the CodeQL workflow is named
  `CodeQL analysis` so its run is unambiguous.

## Upgrade

- Re-run the installer. Existing installs gain one image (`shakerscan-model-intake`) and one service
  (`model-intake-worker`); migrations and stored data are unchanged from 2.0.1. See
  [`docs/upgrade-and-rollback.md`](../upgrade-and-rollback.md).
