# ShakerScan 2.5.0

Hunt stops refusing work the operator already authorized, a connected device is examined like
any other target, and the web UI works at every address that reaches the engine. Every change
here was found by driving the product from a second machine over a LAN, and each was verified
live on a clean source build before merging. Upgrade in place from 2.4.1. No change to the
deterministic proof boundary.

## Changes

### Hunt resolves what it can, and says what it resolved (#193)

- Asking for state-changing HTTP, network discovery, out-of-band interactions, identity-header
  forgery or direct-origin requests now enables `active_testing` rather than refusing with a
  422 that asked the caller to restate a decision already in the same request.
- A budget dimension whose authority is off resolves to 0. It used to resolve to 0 silently
  when the field was omitted and hard-refuse when it was written down, so the same request had
  two outcomes depending on whether a number was explicit. Funding a dimension still never
  grants its authority.
- `policy_adjustments` on the Hunt reports every authority the server implied and every
  dimension it zeroed. It also reports a privileged request that was stored as passive, which
  was previously invisible: the run said it was active, did no active work, and read as a Hunt
  that found nothing rather than as a refusal.
- `direct_origin_addresses` follows the deployment's own target policy instead of a hardcoded
  private-range list, so the field is usable on a LAN install. Link-local, multicast,
  unspecified and broadcast addresses stay refused under every policy, and hostnames are still
  refused.
- A `network` Hunt resolves against the same targets table and context pack as `web`, so it
  carries the HTTP capabilities: 3 capabilities became 21. Skills raised from 4 to 12 and
  direct-origin addresses from 8 to 32; both are context bounds, not authority.
- The authorization gate itself is unchanged and still refuses.

### A connected device is authorized and examined like any other target (#197, #199)

- `POST /targets/{id}/authorization` records a standing authorization for a device. It answered
  404 before, because it read only the web targets table, so a device was the one asset whose
  permission could not be recorded once and reused. A device scan now reuses it instead of
  demanding `confirm_authorized` on every submission.
- `device.http.probe` accepts an operator-named `origin_port`. A device locator cannot carry a
  port, so requiring a discovery scan first made a known service unreachable and unsayable.
- A device Hunt carries the HTTP capabilities: 6 became 28. Execution routes by the
  capability's own placement rather than by target kind, the HTTP binding resolves either
  inventory, and the worker digests a device run by the same id the control plane used.
- Device safety applies to every capability that reaches a device, not only the device-placed
  ones. The health circuit breaker, the request pacing and the per-device daily fragility
  budget now govern an ordinary HTTP, network or browser capability as well, settled through
  the worker's terminal transaction so the device's own counters advance.
- Browser capabilities accept a bound service origin, so a device on a non-default port is
  reachable in a browser.

### The web UI works at every address that reaches the engine (#195, #198, #199)

- The CORS allowlist is built from one configured address, so the same engine opened by public
  IP or through a forwarded port lost its CORS header on every read and answered 403 to every
  write. An Origin is now also admitted when it is the same address literal the API was reached
  on, at this deployment's own UI or API port.
- The UI follows the address it was opened at, when both that address and the configured API
  host are address literals. It previously dialled the configured host whatever address the
  page came from, so the browser either could not route to it or refused it as a
  private-network request from a public page.
- Both halves are needed: the server was willing after the first change, but the client was
  still asking the wrong host.
- Only address literals are followed, on either side. A name may legitimately be a gateway in
  front of a different API host, and following names is the shape a rebound DNS name relies on.
  Names stay with `SHAKERSCAN_CORS_ALLOW_ORIGINS`.

### Operations

- Signed SBOMs published with expanded runtime coverage (#186).
- A clean reinstall script for macOS and Linux that refuses unsafe paths and reports Docker
  cleanup failures honestly (#188, #196).
