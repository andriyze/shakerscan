# ShakerScan 2.11.2

**Status:** in development; it follows 2.11.1. The client for this release is `shakerscan` 0.11.2.

A patch release: retest, replay and coverage correctness fixes; Hunt verification, Hunt tools,
the Hunt worker's scheduling and the MCP adapter; and client 0.11.2, which completes a person's
decision with one security-key touch in the person's own terminal. No schema changes.

## Changes in behaviour from 0.11.1 (read before upgrading)

- **Exit status 3 instead of 2, and no question without a terminal.** `approve`, `approve
  --all-pending`, `approve --watch`, `deny`, `agent --allow`, `hunt start --allow` and the
  knowledge and secrets decisions exit with status 3 (refused, nothing ran) where 0.11.1 exited 2,
  and they refuse, where 0.11.1 asked, whenever their output is piped or captured (`shakerscan
  approve ... | tee approve.log`, `> file`, `--json | jq`): run them with the output on your
  terminal. A script that checks for status 2 checks for 3. `HUNT=$(shakerscan hunt start ...
  --allow budget.raise:2x | jq -r .hunt_id)`, which asked on stderr in 0.11.1, now exits 3: run
  `shakerscan agent --allow ...` (or `shakerscan approve` for a pending request) on its own first,
  or keep the JSON on the terminal. With the switch on or off, `approve` refuses inside an agent that `shakerscan agent`
  started, even in its window: run it in a terminal of your own.
- **The key's touch instead of the code.** With a key that holds one of your credentials plugged
  in, `approve` asks for a touch where 0.11.1 asked for the TOTP code; `--method totp` keeps the
  code. A gateway of an earlier release asks the key's PIN as well: upgrading the client before
  the gateway trades the 6-digit code for the key's PIN and a touch there (the client says it is
  the key's PIN and how many tries are left), so keep `--method totp` until the gateway is
  updated if you prefer the code.
- **Single sign-on, a key registered under My account, client 0.11.1 still installed:** 0.11.1
  run without `--method` picks that key and asks for its PIN (a key with no PIN fails); upgrade
  to 0.11.2 for the touch, or, where the gateway does not require the touch, keep `--method sso`
  with 0.11.1 (where it does, 0.11.1 takes only `--method security_key` with a key that has a
  PIN).
- **If you ran `pipx inject shakerscan fido2`** for 0.11.1: the upgrade installs exactly
  python-fido2 2.2.1. Do not upgrade with `pipx upgrade --include-injected`, which can raise it
  past the client's pin with only a pip warning; `pipx runpip shakerscan install fido2==2.2.1`
  puts it back.

## Security

- **A finding of a signed-in Scan, or a Hunt claim whose evidence was sent signed in, is never
  retested anonymously.** An authenticated Scan keeps only references to its credential profiles, so a
  retest of its findings had no identity and sent the proof's request anonymously. Where the
  application serves a guest page with HTTP 200, a verified SQL injection, NoSQL injection or
  browser XSS still exploitable for the signed-in user read as "likely fixed", and a linked Hunt
  investigation candidate was marked refuted. The same held for Scans an earlier release signed in
  with managed credential profiles, a form or OAuth login or a sign-in scenario (rows a database
  upgraded from 0.8.18 or later can still hold), and for a Hunt agent's own candidate whose
  evidence was sent with `http_request` as a signed-in principal (`as_principal`), whose
  automatic retest ran anonymously. A finding of a Scan that ran signed in and left no identity a retest can send is
  now not offered a retest, whatever its type: the finding page says why
  (`retest_needs_signed_in_identity`), `POST /findings/{id}/retest` refuses it with that reason,
  a bulk retest skips it, and no automatic retest is queued for it after the Scan (so none counts
  towards its automatic attempts). An agent candidate records the principals its evidence was
  sent as (`evidence_principals`) and is not queued for a retest. A retest already queued by an
  earlier release sends nothing and is inconclusive, with the reason, in every tier: the proof's
  own check, the older check ladder and the AI-driven tier. Known limit: such a finding is
  checked again only by an authenticated Scan with the same profile, and such a candidate by
  running the Hunt again; a Scan signed in with a raw header or cookies is retested with them, as
  before.
- **A bare query token stays out of replay metadata.** A captured URL whose query is a bare
  token (`/items?<token>`, as share and signed links use) had the token removed from the replayed
  URL but kept as the name of the withheld parameter: in the capture's `captured_withheld` and
  `captured_query_parameters_withheld`, the replay plan and the receipt a Hunt's
  `collections.replay_safe` and `collections.replay_active` answer with. 2.11.1 said this was
  masked; only the URL was. The withheld parameter is now listed as `<redacted>` in
  `captured_query_parameters_withheld` and as `query:<redacted>` in `captured_withheld`, and the
  replay plan masks a token-like name in every withheld label whatever produced it. A query name
  with no value of its own (`?<token>`, or `?<base64>==`, which reads as the name with the value
  `=`) is now judged by its shape: 16 or more characters of the base64 or base64url alphabet that
  are not words (as `includeDeletedItems` and `access_token` are) count as a token, whatever
  digits they happen to hold. Random 12- and 16-byte tokens (`secrets.token_urlsafe`, standard
  base64), which often hold fewer than three digits, an AWS access key id and standard base64
  are therefore withheld from the replayed URL as well (many were sent to the target), and HAR
  and Postman request lists mask such a name too. A bare parameter withheld for a credential word
  its text contains (`?Zq8+otpW/3kLm9Xa`) is listed under its name only when the name is words
  (`?access_token`), otherwise as `<redacted>`. Known limits: a bare token shorter than 16
  characters is withheld only when it contains a credential word, and a bare long number is
  withheld as if it were a token. Receipts stored by 2.11.0 and 2.11.1 are unchanged and may
  still hold such a name.

## Finding accuracy

- **Proof attempts that never reached a verdict leave their family partial.** A browser XSS or
  SQL injection proof batch whose attempts failed (the browser could not start, a navigation
  failed, a request was refused) settled partial with every candidate counted as attempted, and
  its family read complete with a reliable grade, although nothing proved or ruled out the
  candidates it was given (a reflection only the browser proof can promote was dropped). Such a
  family is now partial with the reason `proof_attempts_unresolved`, the proof escalation names
  how many candidates it left unresolved (`unresolved_candidates`), and they earn no
  active-verification credit in the assurance score. A failed attempt that an extension or retry
  settles is resolved; one the extension does not re-run stays unresolved. So does a candidate
  the batch was given but stopped before, because the Scan was cancelled or what was left of its
  budget could not fund that attempt's share: such a candidate left no record and the family read
  complete. It is now recorded as `candidate_deferred` with the reason `proof_cancelled` or
  `proof_share_unfunded`. Rebuilt reports of earlier Scans with failed attempts read partial
  too; a candidate an earlier Scan stopped before has no record to rebuild from.
- **A broken or slow page no longer reads as a fixed browser XSS.** The browser retest answered
  "likely fixed" when the page itself answered 200 but did not run as it did when the finding was
  proved: its own script answered 503, 404 or 429, the data call its sink makes failed, or a
  script or the payload's own image arrived after the 1.5-second settle. The 2.11.1 notes said
  "likely fixed when ... every request was answered"; that held for the page alone. The retest
  now watches the page's same-origin requests. While some are still open it waits for them, up
  to the proof's 20-second page timeout (a payload that runs meanwhile is still vulnerable). It
  is inconclusive, with the reason, when a same-origin script or frame answered with an error,
  when a script, frame or data request was refused by the service (408, 429, 5xx), failed on the
  network or was cut by the retest's 50-request cap, or when a request is still open at the
  timeout. The page's data requests (fetch, XHR, EventSource) are judged against the proof's own
  page, which a browser XSS finding now keeps (`browser_proof.page_requests`): one the proof saw
  answered must be answered again, and one that failed or never answered for the proof too (a
  guest's `/api/me` answering 401, a long poll) does not count. An open event stream counts as
  answered. A missing image, style or font, an image the cap cut, a data request the page
  cancels itself, and another site's request (which the retest blocks, as the proof does) do not
  count. Known limits: a 200 maintenance page served in place of the application is not yet told
  apart from a fix; an image or style still loading at the timeout makes the retest
  inconclusive; and for a finding recorded before this release, which keeps no proof page
  requests, a data request answering 404 or still open at the timeout (a long poll) makes it
  inconclusive, while one answering 401 or 403 counts only when the retest carries a session.
- **A weak server key no longer hides an untrusted chain.** For a server certificate with an
  RSA key under 2048 bits (or EC under 224), the verifier refuses the key (OpenSSL code 66)
  before it builds the chain, and 2.11.1 then reported only the weak-key finding: a weak
  certificate from a private CA or with a missing intermediate lost its "TLS certificate chain is
  not trusted" finding. On code 66 the inspection now runs one more handshake with every
  strength check off (`@SECLEVEL=0`: key sizes and signature digests across the whole chain) to
  judge whether the chain reaches a trusted root, recorded as `certificate_chain_trust` with the
  verifier's own reason. The untrusted finding is folded into the weak-key one only when that
  chain is trusted and no issuing certificate the server sent has a weak key or signature
  (judged from the chain it sent; a self-signed root's own signature does not count). When the
  chain is not trusted, has such a weak link, or could not be judged (observations recorded
  before this release included), both findings stand, and the untrusted one names the chain's
  own failure or the weak issuing certificate, with the key as a second line. The extra
  handshake stays within each origin and address's four handshakes; it is skipped, and the chain
  left not judged, when the default negotiation already used the fourth.
- **sqlmap requests answered with a redirect count once.** sqlmap logs a request the target
  answers 30x twice under its one number, and the wire count read every log block, so each such
  request was charged twice. A Hunt `sqli.verify` against a sign-in form that redirects failed
  with a false "wire limiter reported traffic above the hard ceiling" once it passed about 450
  real requests (900 charged), and was charged its whole hold; Scan batches, the paced
  sign-in probe set and staged SQL injection rates read the same doubled count on such
  endpoints. The count is now of distinct request numbers (`--ignore-redirects` stays pinned, so
  no redirect is followed under the same number). This removes the known limit the 2.11.1 notes
  gave for `sqli.verify`: the cause was the redirects, not the slow endpoint.

## Hunt verification and tools

- **Candidates on a network target are verified on the service they name.** A network target
  names a host, not an HTTP service, and `candidate.verify` built its proof from that host: it
  failed before sending anything (`adapter_fault:ExperimentContractError`) and was still charged
  as a verification that ran (24 requests, 180 s, a verification and an active action). The
  proof now runs on the HTTP service the candidate's locus names (`origin`, or an absolute
  `url`) on the target's own host (the same service however its default port or IPv6 address is
  written), and the verified finding, its evidence and its verification record are located on
  that service, so a later retest reads a URL it can request. A candidate on a network target
  that names no such service, two services, or another host, is refused at no cost with
  `verification_service_unresolved`. A suspected finding on a network target is verified on its
  own URL's service, and `experiment.workflow` against a network target answers 422
  `invalid_workflow` instead of failing. A network Hunt's budget pace counts the verifier's
  HTTP requests as a web Hunt's does.
- **A verification the workflow contract refuses is not charged.** A candidate whose route the
  proof workflow cannot use (a scheme-relative `//other-host/x`) was refused before any request
  (`invalid_workflow`, `target_traffic_sent: false`) and still charged as a verification that ran
  (24 requests, 180 s, a verification and an active action). It is now refused at no cost, as a
  credential refusal at the same point already was, and the action records the violation.
- **`artifact.inspect` and `javascript.analyze` read from the service the call names.** Neither
  took an `origin`, so both always read from the Hunt's registered URL: on a network target, which
  names a host and no HTTP service, every read was refused as outside the target binding (and
  charged a request), while `http.request` to the same service worked. Both now take `origin`,
  checked as `http.request`'s is: the target's own host only, another port only with active
  testing (and then counted as an active action), at admission and again at dispatch; another
  host only as a destination a person authorized for the Hunt, as for `http.request`. A read on
  a network target without `origin` is refused at no cost (`artifact_origin_required`, recorded
  as a refused attempt) and says to name the service. Retained steps keep the origin.
- **A Hunt browser XSS proof on a page that writes in the background can end negative.** The
  proof is read-only and refuses every write. A Hunt marked a proof that came back not proven as
  partial (`browser_request_blocked:state_changing_method`) whenever the page itself sent a write,
  such as socket.io long polling or telemetry, so a single-page application that does so could
  never get a complete negative from `xss.verify`. The proof now records whether a refused write
  carried its payload (`payload_write_blocked`): its marker in the write's URL or body as text or
  in a common encoding a page applies (percent-encoding, base64 or base64url, hexadecimal,
  UTF-16, gzip or deflate), and a body it cannot read or that is over 1 MiB counts as carrying
  it. Only such a write, or a proof that does not say, keeps the result partial; a page that
  encrypts or otherwise transforms the payload before writing it is not told apart from its own
  writes. Writes are still refused, and a Scan's proof is unchanged.
- **A Hunt `sqli.verify` must name the input it tests.** Given a path with no parameter
  (`/search`), sqlmap answers its own "try URI injections in the target URL itself?" with yes and
  injects into the path, so such a call spent its whole hold testing the path and never the page's
  parameter. A call that names neither a query parameter (`/reports?filter=x`) nor a path segment
  marked with `*` (`/products/1*`, sqlmap's explicit marker) is now refused before anything is
  reserved (`sqli_injection_point_missing`, recorded as a refused attempt), with how to name the
  input; a queued one is refused by the worker before sqlmap starts. The refusal also says that
  with a query parameter named sqlmap still tests the request's cookies, while a `*` marker has
  only the marked segment tested. Finished Hunts no longer propose `sqli.verify` steps for reuse,
  since a retained step carries no query.
- **A Hunt `sqli.verify` reserves enough to reach a verdict.** It reserves 1,800 requests /
  1,200 s on every named profile (900 requests / 540 s in 2.11.1). One input with no injection
  was measured to cost up to 516 requests, about 570 s at sqlmap's pace of about a request a
  second (on an endpoint that echoes the parameter), so the hold is twice that; a 540 s hold
  stopped such a call at 490 requests without a verdict. A device target and an unprofiled Hunt
  keep the registry hold, and a Hunt that cannot fund the hold asks for a budget raise.
- **A long Hunt action no longer holds the agent's terminal step** (MCP adapter and client
  0.11.2). A client that sends MCP progress tokens, such as OpenCode, was kept waiting for up to
  900 s per call, and it starts nothing else while a call of its step is open, so the Hunt did
  nothing else while a verifier ran its whole wall. Such a client is now held at most
  `SHAKERSCAN_MCP_ACTION_WAIT_SECONDS` (default 120, was 900); a longer action answers
  `outcome: "running"` with its key, the agent works on and collects it with the same key and
  input, and `shakerscan_hunt_get` lists the running actions not yet collected
  (`mcp_uncollected_actions`). Nothing runs twice. An action that ends within that wait settles
  in the call; one that runs longer (`ports.discover`, `web.browser_crawl`, `candidate.verify`,
  `browser.login_check`, `templates.scan`, `service.nse_check`, `sqli.verify`, `xss.verify`)
  may answer running. Each running action keeps its wall reservation until it settles: on `fast`
  (3,600 s), two `sqli.verify` calls in flight (1,200 s each) hold 2,400 s, and a call that needs
  more wall than is left asks for a budget raise until one settles, each settling to the wall it
  ran. Collecting an action the engine still reports running waits at most 10 s for it, not the
  whole 120 s, and `shakerscan_hunt_get` also lists every action still running on the server
  (`in_flight_actions`, with its `idempotency_key_sha256`), including one an earlier agent
  session started.
- **Short Hunt calls no longer wait behind long actions.** The agent-tool worker runs three
  actions at once, and once long actions answered running, an agent could keep three in flight
  (two `sqli.verify` and an `xss.verify`): they took every slot for up to 20 minutes, and each
  short call made meanwhile (`http.request`, `artifact.inspect`, a browser step) failed in the
  queue, because the engine waited for it only its own timeout plus 30 s from when it was queued.
  Long actions, a worker action whose wall, as the registry gives it or as the call reserves it,
  exceeds 60 s (`sqli.verify`, `xss.verify`, `templates.scan`, `ports.discover`,
  `service.fingerprint`, `service.nse_check`, `subdomains.discover`, `web.crawl`,
  `web.content_discover`, `web.browser_crawl`, `browser.login_check`), now take at most two of
  the three slots, so a short call waits only for short work, each at most 60 s, or for an SSH
  command, which runs on its session's worker and takes a slot. A Hunt with two in flight has a
  third refused with HTTP 429 `long_actions_in_flight`, reserving and recording nothing, so the
  same key is sent again once one settles (the MCP adapter answers `retry_later`). The engine now
  counts a queued call's own time from when a worker starts it, so a call that waited for a slot
  keeps all of it, and a long action queued while other Hunts' hold both long slots runs its whole
  wall once one frees; a call no worker starts within its reservation's lease (at least 90 s) is
  released without running and charged nothing. Once eight long actions wait on one worker
  (across Hunts), it leases nothing more, short calls included, until one of them starts.

## Fixes

- **A Scan whose request collection is named by its id no longer fails.** A collection named by
  `id` without a saved selection seeds discovery with its safe routes and replays nothing
  (`discovery_only`). Its first continuation round still asked for a budget for the collection's
  replay step, which the plan never has, and the Scan failed ("action budget allocation contains
  unknown actions: inputs.collection_00"). Such a Scan now continues as any other. The UI, which
  names saved selections, was not affected. To replay a collection's requests, name its saved
  selection (`selection_id`).

## Client 0.11.2

- **`shakerscan approve --test`**: one touch of your security key on an Enterprise connection,
  checked by the gateway against the keys registered to you as every touch is; nothing is
  decided. Run it once after registering a key, before your administrator requires the touch.
  It asks only at an interactive terminal (exit 3 elsewhere); a gateway without the test says so
  before anything is asked of a key.
- **One safety budget per agent session**, where the gateway requires the touch: `shakerscan
  agent --allow` shows, before its one touch, the safety budget every Hunt of that session
  shares. A Hunt start past what is left is the person's decision: in an agent's shell the line
  names that same start as the person's command (`shakerscan api POST /hunts ...`) and says not to
  send it again; the MCP adapter says the same. In the person's own terminal the touch starts it.
- **Decisions only the browser confirms.** Where the gateway answers that a decision is made in
  the browser only (a device SSH plan's confirmation, an authorization investigation's approval),
  the client asks no key, says to make it on the Hunt page and exits 3.
- **A decision only a person makes, by one touch of a security key.** An Enterprise gateway's
  administrator can require a security-key touch for decisions such as raising a Hunt's budget or
  authorizing a target for active testing when they come from a terminal. Every command of the
  client then completes such a request in the person's own terminal: it shows the decision whole
  (every limit a raise sets, safety ceilings first; the whole host), checks that the gateway's
  challenge is for exactly that request, asks for one touch (user presence; no PIN), and sends the
  same request again once with the one-time grant. Anywhere else (an agent's tool call, a pipe, a
  script, inside `shakerscan agent`) it never prompts and never asks a key anything: it prints the
  decision and the command the person runs, and exits with status 3. Ctrl-C at the touch cancels
  it (status 130). The MCP adapter answers `outcome: person_decision_required` with the command.
- **What the person touches for is what the key signs.** The client asks the gateway first (a
  person with no key registered, or a decision the gateway cannot name in full, is told so before
  anything is asked of a key), then shows only the decision as the challenge states it. Over SSH
  it says the key is on the computer you connect from and names the command to run there. With
  no key plugged in, it waits for one to be inserted (up to a minute, within the challenge's life)
  instead of failing. A refused start (a Hunt start, scan, retest or network scan of a target
  nobody authorized) says that nothing was started and names the target's authorization
  (`shakerscan targets authorize <target-id>`), never the start itself; the refusal line, the MCP
  adapter and the Hunt skill tell the agent not to send it again until the person says the
  target is authorized, then once, with the same idempotency key.
- **`shakerscan targets authorize|unauthorize <url-or-id>`** (a URL, a target's or connected
  device's id, or `host://<address>`) and **`shakerscan hunt budget raise <hunt> --limit
  NAME=N|NAME=+N`** make the usual decisions directly. Where the gateway requires a touch, in an
  agent's shell they print one line (the decision and the person's command) and exit 3 (`targets
  authorize` before it registers anything); a touch that fails exits 1, as `shakerscan api` and
  `shakerscan scan` do. Where no touch is required they are sent as they are, from any shell,
  and the engine records the connection's token first and that no touch proved the decision
  ("alice's token laptop, no security-key touch (shakerscan targets authorize)"; a raise's reason
  says the same, and the command says why). `hunt budget raise` is the command named for a raise
  only when every limit name is lower-case letters and underscores; any other is named as the
  request itself through `shakerscan api`. `targets authorize` refuses a placeholder (`TARGET-ID`) and a value ending in punctuation
  copied from a sentence before anything is sent. The one line an agent gets ends with the
  person's command, with nothing after it.
- **`shakerscan approve`** names no account by default (the gateway names the person the
  connection acts for), uses the security key without `--method` whenever a plugged-in key holds
  one of the person's credentials (below), says key errors in plain
  words, says what a touch decides ("Touch your security key to allow ...") and that it was a
  touch, and in a watch that asks a touch
  per decision keeps the request pending and the watch open when a touch fails or is cancelled,
  and ends with the reason when retrying cannot help (no key registered, the person or account no
  longer able to decide). Its lines for decisions made through your other connections say what was
  decided, in the gateway's words. On an older gateway that needs a sign-in name (it refuses an
  approval without one, and its `GET /_enterprise/me` does not report `person_decision_proof`),
  it asks for the name once, as 0.11.1 does; nothing it reads is a route that gateway refuses.
  It refuses to run inside an agent that `shakerscan agent` started, even in a terminal (a change
  from 0.11.1, switch on or off: run it in a terminal of your own).
- **One terminal rule for every command that asks the person.** `approve`, `approve
  --all-pending`, `approve --watch`, `deny`, `agent --allow`, the knowledge and secrets decisions
  and a person's decision ask only when their input and their output are a terminal, and write
  their prompts there (`hunt start --allow` on stderr when that is a terminal too). Otherwise they
  exit with status 3 (refused, nothing ran; 0.11.1 exited 2, and asked whenever its input was a
  terminal, even with its output captured) before they read the instance, show anything or ask a
  key anything, so a harness that captures an agent's command's output never makes the person's
  key blink, whatever terminal it gives the command's input or errors.
- **The security key first, also with the switch off: one touch.** Without `--method`, `approve`
  (and `--watch`, `agent --allow`, the knowledge and secrets decisions) use a plugged-in key that
  holds one of the person's credentials whenever the gateway offers a key, with the user
  verification the gateway asks: a touch alone (no PIN) for the approvals, and for every decision
  where its administrator requires a touch; the key's PIN as well for a knowledge or secrets
  decision where it does not. A gateway of an
  earlier release asks the key's PIN too; before that PIN prompt the client says it is the key's
  own PIN, not the authenticator app's code, and how many PIN tries the key has left (each wrong
  PIN costs one; eight block the key's PIN). The 6-digit code only when no key can answer (none
  plugged in, none of the person's, or no PIN set where such a gateway asks for one), and for a
  single sign-on account the browser sign-in then; `--method totp` still chooses the code. Without
  `--account`, the touch prompt names the person it approves as ("Touch your security key to
  allow, as alice ..."), as the code's prompt does ("TOTP code for alice"), instead of a line of
  its own on every run. 0.11.1 asked for the code whenever one was enrolled. Against
  a gateway that does not name the approver, the client asks for the sign-in name before it
  begins an approval, instead of sending an empty one that gateway refuses and records.
- After a touch the client says "touch accepted ...; sending the request again..." and then what
  the instance answered (applied, or refused because something changed meanwhile), never "done"
  before the request is sent. A key that cannot arrive over mosh or another remote shell is named
  when the wait for it ends, not at every prompt. A saved long request body is removed after a
  week.
- **`shakerscan scan --active-testing`** drops its own "Type 'yes'" only when the touch follows
  (the target registered for the URL is not authorized yet, and the scan carries no credential or
  receipt of its own); a target already authorized is scanned with no touch, so it is asked
  there, as in 0.11.1.
- **`shakerscan doctor`** says whether the gateway requires the touch and whether one could happen
  on this computer (on an Enterprise connection only; nothing of it against an open-source engine).
- **The Hunt skill** tells agents never to amend a Hunt's budget themselves: the person approves
  the Hunt's `budget.raise` request or runs `shakerscan hunt budget raise`.

- **Also:** the silent check of a plugged-in key
  is made only for the gateway's own relying party; a key that holds a credential is used without
  asking which; WSL without the key passed through and containers are recognized like SSH (no
  minute-long wait for a key that cannot arrive); `targets authorize` records the person the
  connection acts for; `approve` says whom it approves as; `doctor` reports no key plugged in as
  information, not a failure; the watch names the command for a refused decision (for a refused
  Hunt start, to ask the agent for its command, since the gateway keeps no request body); a
  refused submission is sent again "with the same Idempotency-Key, if it had one". On Linux a plugged-in key this
  user cannot open (no FIDO udev rules) is said at once, not waited for as if unplugged. A key
  with a PIN that the silent check finds nothing on is left to the assertion when the gateway
  asks for the PIN (a browser-made passkey can need it for every use); where the gateway asks for
  a touch alone and no other key or code can answer, that key is asked with its PIN once, said
  first (Ctrl-C cancels). Before any touch, a
  refusal (no key registered, a decision the gateway cannot name) names the decision. A secret's
  reactivation or expiry names `shakerscan secrets reactivate|expiry`, and a request body longer
  than 1,024 characters is saved to an owner-only file the command names with `@` (`shakerscan
  api` reads a body from `@FILE`, only from the directory the client saves those in, so no other
  file a person is talked into naming becomes a request's body).
- **CI:** the built wheel is installed and started on Python 3.10 and 3.11 before publishing
  (the Python 3.12 build job accepted syntax those interpreters refuse), and installed without
  the lock on Linux x86-64 and Apple Silicon macOS with Python 3.10 and 3.12 to 3.15, as `pipx`
  installs it (3.15, a pre-release on the runners, is checked but never holds up publishing); the package's own tests (`client/tests`) run before it is built.
- **Before tagging:** one real install of the built wheel on an Intel Mac (`pipx install` of the
  candidate wheel: no Rust toolchain asked for) and one on an Apple Silicon Mac.

## Dependencies

- **python-fido2 is a runtime dependency of the client on macOS and 64-bit Linux** (x86-64,
  ARM64; BSD-2-Clause; with cryptography, cffi, pycparser and, on Python 3.10,
  typing-extensions): the platforms `cryptography` publishes wheels for, so the client still
  installs there without a compiler. Windows (no terminal touch yet), 32-bit and other Linux
  architectures and the BSDs install the client without python-fido2, as before (`pipx inject
  shakerscan fido2` adds it where a wheel or a Rust toolchain exists). The package declares
  exactly `fido2==2.2.1` (a new python-fido2 release arrives only with a client release checked
  with it) and `cryptography>=50.0.2,<52` (up to python-fido2's own bound, so cryptography's
  fixes keep arriving), or `>=48.0.1,<49` on an Intel Mac (49 and later publish no Intel macOS
  wheel). A plain `pipx` or `uv tool` install resolves the newest matching releases
  from the package index without hashes. Before publishing, the built wheel is checked with the
  hash-locked set (`client/requirements/runtime.lock`: python-fido2 2.2.1, cryptography 50.0.2, or
  48.0.1 on an Intel Mac; `pip install --require-hashes -r client/requirements/runtime.lock`
  installs exactly that) and with no lock, as `pipx` resolves it, on Linux x86-64 and Apple
  Silicon macOS with Python 3.10, 3.12, 3.13, 3.14 and 3.15; an Intel Mac's set through the lock
  only. The hash-locked set is what those checks install: an install by `pipx` or `uv tool` is
  pinned by version (python-fido2 exactly), not by hash, and resolves `cryptography`, `cffi` and
  `pycparser` within the declared ranges. On an Intel Mac, cryptography 48.0.x receives no fixes
  after its own line: a known limitation a later client release revisits. The first
  `uvx shakerscan mcp` downloads `cryptography` and `cffi` as well; run it once by hand on a slow
  link.
- **The Homebrew formula does not install python-fido2.** A Homebrew install of the client has no
  security-key support and says so at install and in `brew info shakerscan` (its caveats), in
  `shakerscan doctor` and when a touch is asked for; on a gateway that requires the touch, install
  with `pipx` or `uv tool`.

## Documentation

- **"Lockout-safe" corrected to "paced, bounded".** The 2.11.1 notes ("tested at a lockout-safe
  pace") and the Scan page's coverage reason overstated how sign-in testing behaves. On the
  credential profile's own sign-in endpoint the verifiers are paced (at most 20 requests a minute,
  combined across a Scan's parallel parts) and bounded (up to 4,352 requests per Scan part:
  3,784 sqlmap, 256 Dalfox, 112 SQL injection proof, 96 NoSQL injection, 48 for each request
  verifier and 8 browser XSS proof). The probes carry placeholder values, so they never lock out
  the profile's own account, but a throttle or lockout keyed to the scanner's address (3, 5 or 10
  failed sign-ins) can still trip within seconds and then refuse the scanner's own sign-in from
  that address. Active templates (for example `default-login`), other sign-in forms and Scans
  without a credential profile are not paced. The coverage reason now says "paced and bounded"
  with these numbers.
