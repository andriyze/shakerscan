# ShakerScan 2.11.0

**Status:** in development on the `release/2.11.0` integration branch.

## Upgrade notes

- **The first start of 2.11 installs the new database schemas and count summaries.** Existing
  findings receive their stored severity order in small, resumable batches after the API starts
  serving. Until that finishes, lists use the equivalent computed order; cursors continue across
  the transition. Large databases can take longer to initialize their count summaries. Let the
  launcher finish before using the instance.
- **List indexes are built after the API is serving.** The indexes behind the bounded findings,
  targets and scans lists are created in the background, one at a time, without blocking writes
  (about 15 seconds at 500,000 findings). Until they exist, large lists answer more slowly.
- **Statement time limits now apply.** Database statements of the API (30 s) and workers (60 s)
  are bounded as configured; before 2.11 a pooled connection could lose the limit. A request that
  reaches the limit fails instead of holding the database.
- **Heavy reads are admitted, not queued.** When the API is already serving its share of heavy reads
  (large lists, the dashboard, exposure), another one is answered `429` with `Retry-After`; the UI waits
  and retries. Lists accept a `cursor`, `limit`, `sort`, `fields` and `count`; the
  older offset form still answers for one minor line and is deprecated.
- **Before an upgrade the launcher now also checks** that the install directory has room for the
  backup (`SHAKERSCAN_INSTALL_DIR_MIN_FREE_GB`, default 2), and that the running PostgreSQL and
  Redis are saving their data to their volumes. Either problem stops the upgrade with nothing
  changed and the running release still running. In a terminal it offers a complete
  `shakerscan backup` first (`SHAKERSCAN_UPGRADE_BACKUP=full` or `database` decides without
  asking); the automatic database dump is still taken otherwise.
- **A start never creates an empty database over a lost one.** When an install that has run before
  has no database volume, `start` stops and points to `backups/`. Start empty on purpose with
  `SHAKERSCAN_ALLOW_NEW_DATABASE=1 shakerscan start`.
- **Images.** `shakerscan images` lists every ShakerScan image and why it is kept;
  `shakerscan images prune` removes the ones nothing keeps. `SHAKERSCAN_KEEP_RELEASES` (default 2)
  sets how many releases stay for rollback, this one included. The release kept for rollback is the
  one that was actually running before the upgrade, even after a rollback with an older launcher.
  Installs on one host now protect each other's images, running or stopped.
- **Redis lost.** `shakerscan redis` shows Redis's health and persistence; `shakerscan redis reset`
  recreates it empty (keeping a copy) when its data is lost or it cannot start. Waiting Scans are
  queued again automatically.
- **No backup of a new database.** A first start and `shakerscan reset` no longer take a full
  backup of the empty database.
- **Broker-only fleets.** `shakerscan fleet init --workers 0` is accepted, with a warning: nodes
  join with no scan workers until the fleet is scaled.
- **Model Intake enabled later needs an API restart** for its automatic review to start
  (`shakerscan restart`).

## Recon

- **Corporate surface.** Scan reports list mail portals, identity providers, VPN gateways, edge
  appliances, CI servers and administration consoles the HTTP evidence names, under
  `discovery.corporate_surface`, as unconfirmed leads. An exactly reported version feeds the
  service view's advisory candidates; known-exploited matches remain candidates.
- **Content discovery with active authority** reads the common list and then a corporate list
  (mail, identity, VPN and console paths) in the same reservation.
- **Active recon family (`recon_active`).** Select it explicitly (it is in no preset) with active
  testing and the target's authorization: DNS name enumeration and virtual-host discovery on the
  target's own address, both only when the target is the apex domain itself (or its `www` name)
  and subdomain discovery is enabled, and parameter discovery on observed routes. A target below
  someone else's domain (`acme.vendor.example`) never has names guessed under that domain, and
  virtual-host discovery does not run on a CDN or shared hosting edge. Routes whose names are
  actions (log out, delete...) or carry token-like segments are not probed for parameters. Bundled authored lists, wildcard, catch-all and
  random-parameter controls, metered and cancellable. Results are leads; enumerated names are
  recorded as discovered targets for their own authorized Scans.
- **Discovered names keep their provenance.** A name a discovery run adds records which sources
  named it, whether only a certificate did (historical issuance, not current ownership), its DNS
  status, and that no service was checked. Runs report names that were already targets, and a
  completed run with a failed source is marked partial.

## Known limitations

- **Interrupted examination stays partial.** Cancellation and authorization withdrawal keep
  settled findings and available checkpoints; they do not establish the outcome of unfinished
  probes. A cancelled Scan is distinct from a completed Scan.
- **The dashboard can be up to 15 seconds old.** Its counts are cached per API process.
- **An install not yet registered is not protected from another install's cleanup.** Installs
  register themselves when they first start with a 2.11 or later launcher; an install that has not
  (other than the default `~/.shakerscan`), or one under another user account, is not visible to
  this install's image cleanup and pulls its images again if they were removed.
- **Redis reset and running Scans.** A Scan that was running when Redis was reset is marked with an
  unknown outcome and is not restarted automatically; start it again from the Scans page.
- **Rollback.** Rolling back to 2.10.x keeps the 2.11 database additions (the stored severity order,
  the count tables and their triggers, new indexes); 2.10.x ignores them. A rollback launcher
  older than 2.11 does not read `.release-images.previous.2` and later records.
- **Active recon is Scan-only.** Hunts do not yet have the `recon_active` capabilities.
