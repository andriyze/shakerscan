# ShakerScan 2.11.4

**Status:** integration candidate on `release/2.11.4`; it follows 2.11.3.
The client for this release is `shakerscan` 0.11.2 (unchanged).

A patch release: three fixes to the AI settings routes, the Parallel scan option where a
deployment allows parallel scans, and test fixtures that no longer depend on the calendar. No
schema changes; a rollback restores the pre-upgrade database dump, as for every release
(`docs/upgrade-and-rollback.md`).

## Security

- **The AI connection test never sends the saved provider key to another address.**
  `POST /settings/ai/test` takes the provider URL from the request and, when the request carried no
  key, used the saved one, so a request naming any URL sent the saved key there as a Bearer token
  (and made the API connect to that address). A test of a URL other than the saved AI URL now needs
  its own `ai_api_key` and is refused with HTTP 400 without one. A test of the saved URL still uses
  the saved key.
- **"Keep settings after restart" is removed; AI settings are never written to `.env`.** The toggle
  on Settings → AI wrote the settings, including `AI_API_KEY` in plain text, to the install's `.env`
  (mounted read-write into the API container and copied into backups). The settings are kept in the
  settings store (Redis) across restarts without it, so the toggle, the `persist_to_env` field of
  `PUT /settings/ai` (a request that still sends it is refused with HTTP 422), the API's write
  access to `.env` and `LOCAL_ENV_FILE` are gone.
- **The automatic false-positive close needs at least 0.7 confidence.** `PUT /settings/ai` refuses
  an `auto_fp_min_confidence` below 0.7 with HTTP 422, and a lower value saved earlier or set in
  `AUTO_FP_MIN_CONFIDENCE` is treated as 0.7. Before, the server accepted any value down to 0.0,
  where every false-positive retest verdict closed its finding.

**Action for operators who turned on "Keep settings after restart":** delete `AI_API_KEY` (and the
other `AI_*`, `AUTO_RETEST_*`, `AUTO_FP_*` and `VERIFICATION_MIN_SEVERITY` lines the toggle added)
from the install's `.env`; the values saved on the Settings page stay in effect. If the install was
started with `--lan`, also rotate the provider key: a `--lan` install has no authentication, so
anyone who could reach it on the network could have obtained the key through the connection test.

## Interface

- **New Scan offers the Parallel topology wherever the deployment allows parallel scans.** The
  "Parallel — experimental" option appeared only when the workspace's capability policy enabled
  worker administration (`worker_admin`). A managed deployment can allow parallel scans without
  granting worker administration, so the option now also appears when the policy enables the
  `parallel_scan` capability. A standalone engine has no capability policy and shows the option as
  before.

## Tests

- **Credential-grant fixtures no longer expire with the calendar.** The PostgreSQL credential-grant
  tests created profiles that expired 30 days after a fixed date; the store compares expiry with
  the database clock, so once that date passed every fixture profile read as expired and the
  tests failed. The Hunt credential-attachment unit tests had the same pattern. The fixture expiry
  now follows the real clock (30 days ahead); every assertion is unchanged and the expiry path is
  still exercised.
