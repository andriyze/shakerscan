# ShakerScan 2.3.7

A self-hosted install can add and scan its own network. Found by installing 2.3.6 from the
public installer on a clean Ubuntu 24.04 host and driving the real UI: adding `192.168.1.50`,
the first thing an operator tries, failed in five separate ways. Upgrade in place from 2.3.6;
0.8.18 remains the oldest directly certified upgrade base. No change to the deterministic proof
boundary.

## Changes

### Adding a private target (#162)

- A target is created *and* the request fails no longer happens. The insert committed before
  authorization could refuse it, so the row existed and the dialog showed an error. Creation and
  authorization are now one transaction.
- Private ranges are admitted by default. A scanner installed on the network it scans refused
  RFC1918, loopback and unique-local targets, which also closed a loop: the standing
  authorization was refused, and the active scan that needs it was then refused for want of a
  receipt the operator could not create. Hosted deployments opt back in with
  `SHAKERSCAN_PRIVATE_NETWORK_TARGETS=refuse`; both Compose files now pass the variable to the
  api, worker and agent-tool-worker services.
- The cohort selector reaches authorization. It was never passed on, so scope was always
  evaluated as production. One resolver now derives a target's environment everywhere
  (creation, later authorization, Hunt seeding, broker dispatch); a reused row keeps its own
  environment rather than adopting the new request's.
- The UI shows the server's reason instead of a generic "Failed to create target", on the page
  and in `createTarget()`.
- The targets page can see that a target is authorized. The grouped listing the page reads never
  selected the flag, so "Authorize for active testing" was offered again after a real, recorded
  authorization. Both listings now build the flag from one predicate that carries the canonical
  reader's conditions (standing tiers, unblocked scope, current host).
- Connected devices is no longer a dead end on a fresh install: readiness names the exact command
  that starts the device worker.

### Worker capacity (#162)

- "9 running · max 5" is gone. The launcher and the API read memory from different places and
  both had a cliff at 16 GB. The curve is continuous on both sides, and no host size loses
  capacity; on Linux the launcher's automatic cap is 20 (`SHAKERSCAN_AUTO_WORKER_MAX`).
- The displayed worker floor is no longer published as the concurrency cap workers obey. Display
  and policy are separate numbers.

### Destination policy, tightened where it was loose (#162)

- The Lab label admitted `169.254.169.254`. Link-local, multicast, unspecified and broadcast
  addresses are decided before any environment label, so no label admits them. An IPv4-mapped
  IPv6 spelling of one of them is classified as the address it names.
- DNS answers are admitted before they are frozen, not because they were frozen. The admission
  resolver classifies each answer under the deployment policy for the target's environment and
  freezes only what it admits; a mixed answer keeps its admissible addresses.
- Retained deliberately: a public hostname resolving to a private address at runtime is DNS
  rebinding, not an operator scanning their LAN. Declaring `192.168.1.50` works; a hostname that
  quietly resolves to `127.0.0.1` still fails.

### CI (#159)

- The required checks run in the merge queue, and a release candidate is dispatched after the
  main build rather than rebuilding the same images.
