# ShakerScan 2.14.1

**Status:** integration candidate on `release/2.14.1`; it follows 2.14.0.
The client for this release is `shakerscan` 0.14.0 (unchanged).

A patch release for installs with many targets, findings and Hunts: the dashboard no longer shows
"Exposure unavailable" on a large install, and the API answers page loads sooner, above all on a
host whose CPUs are busy scanning. No schema changes, no new settings, and no change to what a Scan
finds; a rollback restores the pre-upgrade database dump, as for every release
(`docs/upgrade-and-rollback.md`).

## Fixes

- **The dashboard shows its security posture on a large install.** The dashboard's exposure read
  (`GET /exposure/assets`, one page of a cohort) ranks every asset and summarizes proof over every
  active finding, so its cost grows with the findings, not with the page. It ran under the 5 s
  budget of a short interactive read; past that PostgreSQL cancelled it, the API answered 504, and
  Security posture, Coverage and freshness and Top actions read "Exposure unavailable for this
  cohort" for two minutes or more. Every shape of `/exposure/assets` is now a heavy read: a 30 s
  budget, and a `429` with `Retry-After` when too many heavy reads run at once, which the web UI
  waits out.
- **A failed poll is retried after 5 s.** A polled card (the dashboard's exposure cards among them)
  waited two intervals after one failed read, so a single refused or cancelled answer left the card
  empty for 30 s to 2 minutes. A failed read is now retried once after 5 s (or the poll interval
  when that is shorter); further failures back off as before, and a server's `Retry-After` still
  sets the shortest wait.

- **The per-Scan attribution off switch announced in 2.14.0 was ignored; it now works.** A Scan
  submitted with `options.traffic_attribution: false` lost that value when it was stored and still
  sent `X-ShakerScan-Run` on its requests. The value is now stored, survives a rescan from the stored
  options, and the Scan sends no run header.

## Performance

- **`/health` no longer hashes the deployed source on every read.** The build fingerprint (a hash
  of about 800 source files) was computed up to three times per `/health` read and again for
  `/workers`, `/queue/stats` and the dashboard. The web UI reads `/health` on every page, so each
  page view spent about 150 ms of the API's single event loop, and every other request waited. The
  fingerprint is now kept for 30 s; it changes only when the deployed source changes.
- **Docker reads no longer block other requests.** `GET /workers`, the dashboard and Scan
  submission read the worker containers from the Docker socket inside the API's event loop
  (60-90 ms on an idle host, longer while scan containers start). They now run in a worker thread,
  so other requests are served meanwhile. The answers are unchanged.
- **Target coverage reads skip endpoints that have no attempt.** The per-target coverage (the
  dashboard's coverage card, the grouped Targets page and its group rollups) probed every live
  endpoint for its latest continuous-coverage attempt, although most installs have few or none. It
  now probes only endpoints that have one: on an install with about 290,000 endpoints and no
  attempts, one coverage statement went from about 530 ms to about 85 ms. The result is the same;
  when most endpoints have attempts (60 % in the measurement) the read is up to about 8 %
  slower.

## Known limits

- The per-Scan attribution switch is honored by the engine's own workers; a Scan placed on a remote
  worker node (multi-node broker placement) still sends the run header.
- A heavy read refused with `429` past its wait shows the card's error until the next successful
  poll; the 5 s retry makes that short but not zero on a host that stays saturated.
