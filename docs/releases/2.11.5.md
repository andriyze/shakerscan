# ShakerScan 2.11.5

**Status:** cancelled; never published. Its changes, and the fixes to the known limits below, ship
in 2.12.0 ([`2.12.0.md`](2.12.0.md)). This note is kept as the record of the cancelled candidate.

A patch release for Hunt: a Hunt can log in and reuse its own session, the planner sees the page's
links, forms and text, and scanners and verifiers run signed in and test request bodies, with a
verified `sqli.verify` becoming a finding. No schema changes; a rollback restores the pre-upgrade database dump, as
for every release (`docs/upgrade-and-rollback.md`).

## Hunt

- **A Hunt's own login is reusable.** A response capture of a header now reads any response that
  carries it, a redirect included: a form login that answers 302/303 with its session cookie was
  refused before (`http_workflow_capture_incomplete`), and the whole request was marked failed, so
  it could not be cited as evidence either. A capture of `Set-Cookie` holds every cookie the
  response set as `name=value` pairs (attributes dropped, deleted cookies left out), ready for a
  later request's `Cookie` header: bind it with `request_bindings`
  (`{"source_action_id": ..., "capture_name": ..., "header": "Cookie"}`). The value stays in the
  worker, sealed on the Hunt's action like every capture; the planner gets a reference, and every
  echo of the cookie in a response is withheld. A request bound to a session cookie keeps its
  response readable; one bound to another capture, to a credential field, or to a cookie value
  under eight characters is still reduced to its status, as before.
- **A capture the response does not carry no longer fails the request.** A failed login is a
  result: the request is recorded as completed, and the observation lists the missing capture in
  `captures_missing`. The other captures of the same request are kept.
- **The answer to a request that captures values shows the response's cookie names and security
  attributes** (`set_cookie_metadata`: `secure`, `httponly`, `samesite`), never their values.
- **The planner sees the page.** The body sample of an HTTP answer is cut from the first byte, and
  many applications open every page with kilobytes of inline CSS. An HTML answer in a Hunt now also
  carries `html`: the page's title, its links (`href`/`src`/`action`, same-origin first as paths,
  at most 40), its forms (method, action, field names and types; a hidden field's value only
  through the masking, which withholds a secret-named or credential-shaped one behind a reference;
  never a password field's value) and its visible text without `<style>`/`<script>` (at most 1,200
  characters). The body sample itself is unchanged.
- **`artifact.inspect` reads a signed-in page.** It takes `session_ref`, `as_principal`, or
  `request_bindings` with a captured session cookie (a `Set-Cookie` capture whose values are at
  least eight characters; other captures stay with `http.request`), under the same rules as
  `http.request`: a
  session or principal needs the Hunt's approval and credential allowance, a cookie binding needs
  active testing and is metered as an active action. A read with an identity does not follow a
  redirect to another origin.
- **Smaller capability answers over MCP.** The compact view of a Hunt capability answer drops the
  copy of the observations in `result.receipt.observations` (the same list as
  `action_result.observations`), as it already did for `result.observations`. The full view is
  unchanged.
- The Hunt skill has a short "log in, then reuse the session" recipe.
- **Scanners and verifiers run signed in.** In a Hunt, `web.crawl`, `web.content_discover`,
  `templates.scan`, `xss.verify` and `sqli.verify` take `as_principal` (a credential selected at
  Hunt start) or `session_ref` (a session of the Hunt) and send that identity on every request, as an
  authenticated Scan does. They used to refuse every principal with `principal_anonymous_only`
  although their schemas offered `as_principal`. The rules are those of `http.request`: the
  credential must allow the capability, the call needs the Hunt's approval receipt at the credential
  tier, and the worker reloads the approval and the session's authority before it decrypts
  anything; a call it can no longer authorize is released with nothing sent. `web.browser_crawl`
  stays anonymous in a Hunt (the headless browser does not reliably send the session on the
  requests the application makes), and its Hunt schema no longer offers `as_principal`; an
  `xss.verify` the pinned browser proves (a URL-fragment or `deep_domxss` parameter) refuses a
  session for the same reason.
- **Signed-in scanners use the Hunt's own login.** The same five capabilities also take
  `request_bindings` with the session cookie a login of the Hunt captured
  (`[{"source_action_id": ..., "capture_name": ..., "header": "Cookie"}]`, an `http.request`
  `Set-Cookie` capture), under the rules `artifact.inspect` applies to it: active testing, the
  Hunt's approval receipt, one active action, and only a cookie whose values have at least eight
  characters. The worker reads the capture at dispatch (a capture of another Hunt or target, or an
  expired one, is released with nothing sent); the planner gets a reference, not the cookie, and
  scanner output is redacted of it (see the known limits below for two exceptions). A finding or
  candidate proved this way records `captured_session` as its evidence principal.
- **`sqli.verify` and `xss.verify` test request bodies.** Besides a query parameter (or a `*`
  path marker for `sqli.verify`), a call may name `method` (POST, PUT or PATCH), `body_field_names`
  (every top-level field the endpoint expects), the `injection_field` the claim is about and
  optionally `content_type` (form or JSON). The body is sent with every field set to an inert
  placeholder and the tool's payloads go into the fields, as for a Scan body candidate. A body test
  needs the Hunt's state-changing permission (`state_changing_http_not_allowed` raises a permission
  request otherwise). Its requests are counted in the verifier's own hold, not in the Hunt's
  state-changing request limit, which bounds the planner's own writes: a body SQL injection test
  needs several hundred requests, far above that limit.
- **A verified `sqli.verify` becomes a finding.** When sqlmap reports a vulnerable parameter the
  call named, the same action runs the Scan's deterministic SQL injection proof (a repeated
  payload/control differential) against the same request, signed in as the call was, inside the
  action's own hold. A proof that holds becomes a verified finding ("Verified SQL injection",
  critical, CWE-89), as in a Scan; sqlmap's own report alone stays a candidate.
- **Signed-in evidence is recorded for retests.** A finding a signed-in verifier proved, and a Hunt
  candidate whose evidence was gathered as a principal (credentials the cited action used, its
  archived calls, or the principal a scanner ran as), record `evidence_principals`. A retest cannot
  send a Hunt principal, so such a finding or candidate is not offered one and a queued retest sends
  nothing and is inconclusive, instead of reading a guest page as "fixed".

**Known limits.** Body inputs name top-level fields only (no nested JSON paths), and every field
carries the placeholder (a field that must hold a fresh token, such as a CSRF token, is not filled).
The SQL injection proof covers a query parameter or a body field; a vulnerable path segment or
header stays a candidate. The proof uses what the action's hold has left after sqlmap (at most 14
requests and 60 seconds); a run that spent the whole hold records `proof_unfunded`.

**Known limits of signed-in Hunts.** These are to be fixed in a later release:

- The SQL injection proof keeps a short excerpt of the response around the database error. On an
  error page that echoes the request's headers, that excerpt can show part of the signed-in
  identity (a session cookie or an `Authorization` value) to the planner, in the Hunt record and in
  the finding's evidence. This applies to every signed-in identity (a captured login, a session or
  a selected credential).
- The page outline shortens and re-cases some form attributes (a form's `method`, a field's `type`
  and `name`) before masking. A secret the page puts in one of those attributes can therefore show
  in part.
- When an input carries the `type` attribute twice, the outline reads the last one, while browsers
  use the first. A password field written that way can show its value in the outline, unless its
  name or shape marks it as a secret.
- A captured cookie is not bound to the origin and scheme that set it. It is sent to any origin of
  the target the call names, including plain `http://` for a cookie a login set over HTTPS.
- Every captured cookie value of eight characters or more is withheld wherever it appears for the
  rest of the Hunt. A target can choose cookie values that hide other text from the planner.
