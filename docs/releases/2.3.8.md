# ShakerScan 2.3.8

A scan's report tells the truth about what it examined, keeps every finding it observed, and says
what to do next. Found by scanning real sites and fixtures on the rebuilt 2.3.7 fleet and reading
the result as an operator would: a thorough scan of a production site graded A* over an origin it
never examined, a static crawl that hit its output cap threw its records away, ten missing-header
findings persisted as one row, and the page said "authentication challenge" for a redirect.
Upgrade in place from 2.3.7; 0.8.18 remains the oldest directly certified upgrade base. No change to
the deterministic proof boundary.

## Changes

### What a scan examines, and what it says about it (#170)

- A bound origin that answers every request with a redirect to another origin is reported as
  not examined, with the redirect named and the serving origin offered as the next step. It was
  graded A* with "authentication challenge" as the explanation.
- Discovery spends the budget the operator authorized. The crawl, content-discovery and browser
  reservations were fixed constants sized for the smallest profile; a thorough scan spent 3% of
  its ceiling. Each producer keeps its share of the ceiling and scales with the profile; the wall
  is the binding dimension.
- A static crawl that produces more output than the retained cap ends `partial/output_truncated`
  with its records kept. It ended `failed` and discarded everything it had read; the cap now
  follows the request reservation.
- Content discovery measures absence instead of inferring it: a few high-entropy paths that cannot
  exist are probed inside the same reservation as the negative control, and a "hit" that is
  indistinguishable from one of them is dropped with the measurement recorded. Whether a redirect
  kept the requested path is judged by the producer on the raw pair, before redaction.
- `robots.txt` and `llms.txt` are mined for paths a crawl cannot reach; markup answers are refused
  and same-origin references only are admitted.
- A query parameter or body field named by the target is an opaque string, not an identifier:
  `_rsc`, `_csrf`, `user[email]` and `$filter` no longer fail the manifest. One endpoint a manifest
  cannot express is counted and dropped; it no longer ends the whole scan. Sensitive-path and
  secret-value rejections still fail the build outright.
- A verifier with no candidate settles `not_applicable`, and so does the proof step that depends
  on it. It was blocked as `dependency_failed`, which marked every family, shard and grade
  unreliable on any target without a parameterised route. A family whose verifiers all had
  nothing to do reads `complete/no_candidates`.
- DNS posture survives a forwarder that answers only the common types: a query the system
  resolver times out on is retried over DNS-over-HTTPS for a public name on public addresses
  (`SHAKERSCAN_DNS_DOH_RESOLVERS`; internal names never leave the network). DKIM selectors are
  asked for; the fan-out is bounded so records are not lost to contention; a partial result states
  `timed_out` or `adapter_failed`, not a bounded-output truncation.
- TLS versions and per-protocol ciphers the probe measured reach the report again.

### Findings (#170)

- Every finding a run observed is persisted. A CWE-less template match keyed its identity on the
  tool name, so ten missing-header findings on one route collapsed to a single row whose title
  flipped from scan to scan. The identity now uses the template and matcher, then the title.
- Freshness is separate from status: a finding carries when it was first and last observed, the
  findings page filters by `not_seen_within_days` and marks stale rows, and a scan page separates
  what this run observed from what earlier scans found.

### Policy and authorization (#170)

- `active_testing: true` without a preset resolves to `standard_active` (recon, passive templates,
  XSS, SQLi). It resolved to `passive`, so an active submission ran nothing active while the page
  read "Active allowed". An explicit `preset: passive` keeps the permission without the work.
- A target has one definition of a standing authorization, so a legacy receipt without an action
  name can no longer deadlock the target between "authorized" and "needs authorization".
- Rebuild tolerance: the launcher's status reports whether the running UI matches the checkout.

### Scan report page (#170)

- The conclusion reads top-down: what this run concluded, whether the target is releasable and
  why (the release decision with its rationale or blocking count), how far to trust it, and what
  to do next. Next steps are derived from what limited the run and link to a pre-filled New Scan.
- The facts row keeps observed risk and examination strength distinct and adds what this run found
  and what is carried over unresolved from earlier scans. Scope is one line; posture and coverage
  limits fold into one list with a count. The Testing tile names the active families that ran, or
  warns that active testing was allowed and none was selected.
- A parallel scan's page shows live activity during the discovery phase; it was blank until the
  first shard started.
