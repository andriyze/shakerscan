# ShakerScan 2.11.3

**Status:** integration candidate on `release/2.11.3`; it follows 2.11.2.
The client for this release is `shakerscan` 0.11.2 (unchanged).

A patch release: a scan never reaches the deployment's own addresses, the scanner's new look,
a managed workspace's sidebar and Hunt start, and two wording fixes. No schema changes; a
rollback restores the pre-upgrade database dump, as for every release
(`docs/upgrade-and-rollback.md`).

## Security

- **A Scan, a Hunt or a device scan never reaches the deployment's own addresses.** Loopback
  (`127.0.0.0/8`, `::1`, the name `localhost`) and every network listed in
  `SHAKERSCAN_DEVICE_DENY_CIDRS` are refused as a destination whatever
  `SHAKERSCAN_PRIVATE_NETWORK_TARGETS` says (`allow` included) and whatever the target's
  environment (Staging, Lab, Development, Preview and Test included). Before, the list was read only
  by the network-scan worker, and under `allow`, or with a Lab-class environment, a web Scan or a
  Hunt admitted loopback and every private range, so it could reach the deployment's own
  containers (the database, the queue, a gateway in front of the engine). Every spelling of an
  address is judged (an IPv4-mapped, NAT64, 6to4 or Teredo form of a listed address is refused
  too). The check applies:
  - when a target's scope is evaluated and when a Scan or Hunt resolves its target and freezes the
    addresses it may connect to (a name with a mixed answer keeps only the addresses outside the
    list);
  - again before execution connects: a frozen address that the list names is refused even if it
    was admitted earlier, for example before the list was changed;
  - to a Hunt's operator-confirmed direct origin;
  - to a device scan and a service check, both at admission and in the network worker.

  The refusal says that the address is one of the deployment's own and is never scanned; it does
  not suggest a Lab label or the private-network setting, which do not change it.
- **Device admission reads the list and resolves names under every setting.** A device scan, a
  network scan of a target (`POST /targets/{id}/network-scans`) and a service check are answered
  with HTTP 422 before anything is queued when the device's address, or every address its name
  resolves to, is in the list or is loopback. Before, admission applied only the private-network
  setting, and resolved nothing under `allow` or a Lab-class environment, so such an address was
  queued (holding a scan slot) until the network worker refused it. The 422 names
  `SHAKERSCAN_DEVICE_DENY_CIDRS` as the setting.
- **The list no longer depends on the cloud-metadata switch.** With
  `SHAKERSCAN_DEVICE_ALLOW_METADATA_TARGETS` on, the network worker used to skip
  `SHAKERSCAN_DEVICE_DENY_CIDRS` altogether. It now applies the list and loopback whatever that
  switch says; the switch still governs only the built-in cloud-metadata addresses.
- **A malformed list stops the API and the workers at startup**, naming the setting, instead of
  failing each destination check later.

What the list holds is the deployment's choice. An open-source install sets none by default, so
only loopback is added to what it refused before: a target on the install's own Compose network
reached by its service name (for example `http://juice-shop:3000`) is still scanned. The
Enterprise gateway sets the list to the container networks, loopback and link-local, and to every
private range when private networks are refused. Ordinary private targets (a LAN address under
`allow`, or under a Lab-class environment on a refusing install without them in the list) are
admitted as before.

**Changed behaviour:** a scan of `http://localhost:…` or `http://127.0.0.1:…` is refused in every
environment and under every setting, where 2.11.2 admitted it under `allow` (the open-source
default) or with a Lab-class environment. Inside the engine's containers that address is the
container itself, never the application on the host; scan the application by its address or name
instead (for example `http://host.docker.internal:3000`).

## Interface

- **The S mark and page-first tab titles.** The browser tab, the sidebar and the mobile bar show
  the website's S mark; tabs read "Findings · ShakerScan" (and "Findings · ShakerScan
  Enterprise" in a managed Enterprise workspace). The sidebar footer links shakerscan.com next to
  GitHub, and the section switch is labelled "All sections".
- **A managed workspace has no section switch.** Under the Enterprise gateway the sidebar shows
  every page the gateway's navigation list allows, so Evidence is listed under Records without a
  switch. The open-source sidebar is unchanged. (A managed workspace of the hosted platform, which
  allows Timeline, lists Timeline the same way.)
- **Hunts start from the terminal in a managed workspace.** Under the Enterprise gateway the Hunts
  page, a target's menu, the discovered-ports table, saved target actions and the Coverage page
  say "Start Hunts from your terminal: `shakerscan agent`" where the open-source edition offers
  "New Hunt", "Start Hunt" or "Open Hunt", and the browser launcher does not open. Existing Hunts
  open as before.

## Fixes

- **The Scan page names a proof the target did not serve in words.** A coverage gap whose reason
  is `target_unavailable` read "Xss Browser Prove Batch: Partial — Target Unavailable"; it now
  gives the reason's description ("The target did not serve the page a proof tests: …"), as the
  coverage summary already did. Every known reason code in that list reads the same way.
- **A browser XSS proof the target did not serve is no verdict in its own record too.** When the
  page under test answered 401/403 or a redirect to sign-in, 408, 429 or 502-504, or did not
  answer, the attempt was already partial with the reason (`target_unavailable`,
  `authentication_required`, `target_refused`), but its `xss_browser_proof` observation still read
  `proof_state` and `finding_verdict` "not_proven". Both now read "inconclusive", in a Scan's proof
  and in a Hunt's `xss.verify`, so no reader takes the attempt for a negative. A page that was
  served and did not run the payload still reads "not_proven".
