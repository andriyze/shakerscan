# ShakerScan 2.14.0

**Status:** integration candidate on `release/2.14.0`; it follows 2.13.0.
The client for this release is `shakerscan` 0.14.0 (`api --idempotency-key`, `scan --only-family`).

2.14.0 makes Scans gentler and identifiable on production targets, keeps parallel thorough Scans
from starving their workers, gives Hunts one shared lead board and the reads that feed it, fixes
eleven defects an operator reported against 2.11.1 and 2.13.0, and stops a signed-in Scan's
archive export from showing the credential the target echoed back.

**Read before upgrading: every request now names ShakerScan.** Scans, retests and Hunts send an
`X-ShakerScan-Run` header and a `ShakerScan` User-Agent token by default. A target's logs, WAF and
monitoring will see them. See [Traffic attribution](#traffic-attribution-on-by-default) to turn it
off for one Scan or for the whole install.

**Upgrade.** Upgrade in place from 2.13.0 (or any 2.13 release). The first start:

- drops the tables of the removed legacy Hunt engines (`agent_hunt_runs`, `device_agent_runs`,
  `device_agent_actions`); columns elsewhere that pointed at a legacy run keep their value without
  the link;
- widens the lead board's `source` check to accept leads the server itself proposes from verified
  findings and matched advisories (`proof_followup`, `advisory_intel`);
- adds `hypothesis_id` to `hunt_coverage_angle_events`.

Nothing else existing is rewritten. A rollback restores the pre-upgrade database dump, as for every
release (`docs/upgrade-and-rollback.md`); the dropped legacy tables come back only from that dump.

**Breaking changes.**

- `GET /findings` refuses an unknown `status`, `source_type` or `verification_verdict` with 422
  naming the parameter, the value and the accepted values. It used to answer `total: 0`. A script
  that filtered on `status=open` must use `status=active`.
- `knowledge.record` refuses the kinds `hypothesis` and `next_step` (422
  `kind_moved_to_lead_board`): a lead lives only on the lead board (`hypothesis.propose`).
- The legacy Hunt engine and the Research runtime are removed with their routes: `/research/*`,
  `/agent/hunt/session/{run_id}` and its cancel, `/agent/hunt/runs`,
  `/device-agent/session/{run_id}` and its cancel, `/device-agent/runs`, and `./scanner.sh
  research`. `/hunts` is the only investigation runtime.

## Traffic attribution (on by default)

- **Every request a Scan, retest or Hunt sends carries `X-ShakerScan-Run: scan:<id>` or
  `hunt:<id>`.** The value is the engine's own record id, never a token or a target value. The
  engine's own HTTP clients also add `ShakerScan` to their User-Agent; external tools keep their own
  User-Agent and send the header. Covered: in-process HTTP, retest replay, nuclei, katana, ffuf,
  dalfox, httpx and sqlmap.
- **Turning it off.** One Scan sends none with `options.traffic_attribution: false` (an authorized
  engagement that must not announce itself). `SHAKERSCAN_TRAFFIC_ATTRIBUTION=off` on the API and
  workers turns it off for the install; `SHAKERSCAN_TRAFFIC_USER_AGENT_TOKEN` changes the token.
- **`GET /targets/{id}/traffic`** lists each run that touched a target: first and last request,
  request count, error answers (5xx, 429, transport errors) and the target addresses reached. It
  reads the existing request archive; nothing new is stored. `docs/traffic-attribution-and-pacing.md`
  explains how a security team identifies ShakerScan traffic.

## Scans

- **A Scan backs off a target that degrades.** Before each external tool attempt the worker reads
  the origin's answers of the last five minutes from the Scan's own archive. 20% bad answers (5xx
  except 501, 429, transport errors) or a median latency four times the Scan's baseline halves the
  rate; 50% bad or 30% throttled quarters it; 80% bad pauses it for up to half the attempt's time
  (at most five minutes). A target that does not recover ends that attempt `target_degraded` and
  its family is reported partial. Pacing never fails a whole Scan; each decision is recorded in the
  Scan's `execution_context.target_pacing`.
- **Parallel thorough Scans no longer lose their Nuclei batches.** Many thorough Scans started
  together each launched a template batch at once; the workers' event loops starved, actions missed
  their budget-hold renewals, and recovery failed the Scans at `templates.active_batch` with
  "stored Scan action result is invalid". Three changes:
  - a template process takes one of the host's heavy scanner slots before it starts, two per CPU by
    default (`SHAKERSCAN_HEAVY_SCANNER_SLOTS=N` in `.env` sets another number). Further batches wait
    for a slot for up to 30 minutes, keeping their heartbeat and honouring cancellation. No worker
    and no active Scan is cut;
  - a running scanner checks for cancellation once a second, off the event loop, with one Redis
    client (it polled every 50 ms with blocking calls);
  - an action whose budget hold recovery took over is a lost lease with an unknown outcome, not an
    invalid result.

  Ten thorough active Scans at once on a 4-CPU host gave the same results as 2.13.0: all ten
  completed, the same action outcomes, no lost leases and no check cut off by the Scan's time
  limit.
- **An off-host redirect or a host answering 503 everywhere no longer fails the whole Scan** with
  "Runtime destination failed scope re-check". The Location of a redirect the client did not follow
  is no longer counted as a destination; a request actually sent out of scope still blocks.
- **`include_families` adds to the preset; `--only-family` selects exactly.** Without
  `policy.preset`, the list is added to the implied preset (passive, or standard active with active
  testing); `preset: "custom"` makes it the exact selection. Resolution is unchanged; the request
  and preview schemas and the scan docs now say so. `shakerscan scan --only-family NAME` sends
  `custom` with exactly those families.
- **Certificate Transparency results survive a crt.sh row with a null field.** Such a row used to
  fail the whole source with "argument of type 'NoneType' is not iterable" for the largest roots; it
  is now read as empty text and the other certificates still count.

## Hunt

- **One lead board.** A Hunt works the target's shared lead board with leases
  (`hypothesis.propose`, `hypothesis.claim`, `hypothesis.transition`), through the same claim and
  transition rules Arsenal uses. The checkpoint frontier is ranked by the deterministic scheduler
  from server records, with the score breakdown. A verified finding opens follow-up leads for its
  vulnerability class, and advisories matched to observed services (known exploited first) become
  leads at Hunt start. Coverage angles can name the lead they test, and continuation offers
  claimable leads.
- **New reads:** query kinds `attempts` (what any Hunt already ran on the target), `activity` (what
  changed for this Hunt since a cursor, with a bounded wait; a wait without a cursor waits from
  now), `traffic` (calls already archived for the target across Scans and Hunts) and
  `coverage_gaps` (auth boundaries by coverage state, untested first), and
  `GET /targets/{id}/knowledge/yield` (spend and verified findings per capability, how leads
  ended per source).
- **Refusals say what to change.** A tool call with a wrong argument names what the tool accepts; a
  claim, a knowledge record or a finish that is refused names the reason and the next step (for
  example the actions still running before a Hunt can finish).
- **A Hunt nobody drives ends after 72 idle hours.** A live Hunt with no activity (no action
  started or finished, no write to the Hunt) for `SHAKERSCAN_HUNT_IDLE_EXPIRY_HOURS` (default 72)
  is ended as a cancellation ends it, with `stop_reason: idle_expired`. A Hunt with an action still
  reserved or running is left until that action ends. What it learned stays in the target's leads,
  candidates and evidence.

Measured on eight intentionally vulnerable applications, three repetitions of each build with two
Hunt sessions each and the same model: no application did worse with 2.14.0 beyond the spread of
the runs; on two applications 2.14.0 found clearly more in every run (one went from 7% to 18% of
its known vulnerabilities proven in the second session, the other from 9% to 23% of them raised as
candidates), and the lead board was used in the second session on seven applications instead of
two. Overall recall moved little (proven 5% to 6%, candidates 10–12% to 12–13%), within the spread.

## Targets and findings

- **An archived target is never reported as authorized; adding it again restores it.** Adding a
  target that had been archived answered `already_exists` with the archived row, which stayed
  archived; authorizing it then answered 200 while every reader saw no authorization. `POST
  /targets` on an archived target now restores it as `PATCH is_active=true` does (services archived
  with it come back, schedules stay paused) and reports `status: restored`; authorizing a target
  that is still archived answers 409 and says how to restore it.
- **Host assets and web targets agree.** `GET /targets` rows carry `inventory_kind` and `asset_id`,
  and the response points to `/targets/inventory` for host assets. Archiving a host's last web app
  archives the host the inventory created for it (a host a person declared, or one with other
  services, stays), and restoring the web app brings the host back. Readers show an archived host's
  own URL instead of its retired form.
- **Several targets in one list request.** `GET /findings`, `/scans`, `/hunts`, `/timeline`,
  `/exposure/services` and `/exposure/changes` accept several `target_id` values (repeated or
  comma-separated, at most 500). One id filters as before.
- **The change feed reports new services and newly proven findings** (`new_services`,
  `newly_proven` in `GET /exposure/changes`).
- **Record deletion says what its approval needs.** The deletion preview returns the exact
  `approval_request`; an approval that cannot execute its preview is refused at creation, naming
  each mismatch and storing no receipt; execute's 409 names every mismatch.

## Evidence

- **Archive exports withhold the credentials a signed-in Scan or a Hunt used.** A masked export
  (`GET /scans/{id}/http-transactions`, `GET /hunts/{id}/http-transactions`, JSON and HAR) withheld
  secrets by key name and shape only, so a credential the target echoed back (a login page
  reflecting the submitted password, a table an injection tool read back) stayed in clear in a
  signed-in Scan's export. The export now withholds every secret of the credential profile versions
  the Scan or Hunt was admitted with or used, in every encoding the scrubber knows (raw,
  JSON-escaped, percent- and plus-encoded, inside a Basic credential). The user name is not
  withheld; the raw view stays the separate, deployment-gated choice.

## Images and dependencies

- Playwright 1.65.2 (package and base image); the proof browser finds its driver where 1.65 keeps
  it, so a cancelled retest still ends promptly.
- The Model Intake signer runs on Python 3.15 (asyncpg 0.32.0, pydantic 2.14.3).
- Go 1.27.4 for the scanner's tools and 1.26.11 for Model Intake's; dnspython 2.9.2, soupsieve
  4.1.2, mcp 1.30.0 in the Model Intake Semgrep tool, containerd 2.3.7 in its Trivy build: each
  clears a HIGH advisory the image gate refused.
- The pre-v2 Hunt engine, the Research runtime and about 8,400 lines of code nothing referenced
  are removed.

## Client 0.14.0

- **`shakerscan api --idempotency-key KEY`** sends a retry key on a write, so a Scan batch that
  outlived a client timeout can be retried without queuing every Scan again.
- **`shakerscan scan --only-family NAME`** selects exactly those families (`--include-family`
  stays additive).
- Refusals from the server are printed with their message, the violated rule and what to attach.

## Known limits

- Playwright browser checks (browser sign-in, DOM XSS proof) do not send the attribution header
  yet; the headless crawl does. A remote broker-placed worker sends it even for a Scan that turned
  it off.
- In-process checks keep their existing active-phase throttle; adaptive pacing applies to external
  tool attempts.
- With many thorough Scans at once, queued template batches lengthen Scans; a very large burst can
  still reach a Scan's own time limit.
- Existing `hypothesis` and `next_step` knowledge rows are kept and are no longer read as leads.
- The observation record of a finding seen before the 2.13.0 upgrade holds its first and its last
  Scan; Scans in between left no record.
