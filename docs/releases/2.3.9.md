# ShakerScan 2.3.9

Allowing active testing now runs active tests. In 2.3.8 a submission with `active_testing: true`
and no preset resolved to the passive family set, so an operator or agent who allowed active
testing got a passive scan under a page that read "Active allowed"; the 2.3.8 release note
described the intended behavior, not the shipped one. This release ships the behavior the note
described, and closes the four new and two carried findings of the latest-commit audit. Upgrade in
place from 2.3.8; 0.8.18 remains the oldest directly certified upgrade base. No change to the
deterministic proof boundary.

## Changes

### Active permission selects the standard active set (#173)

- A request with `active_testing: true` and no `preset` resolves to `standard_active` (recon,
  passive templates, XSS, SQLi). Permission without work is still available by naming
  `"preset": "passive"`. The scan page's Testing tile names the active families that ran, or warns
  that active testing was allowed and none was selected.
- Correction to the 2.3.8 note: its "Policy and authorization" section claimed this default; 2.3.8
  resolved to `passive` without an explicit preset.

### DNS-over-HTTPS fallback validates the answer, and can be configured (#173)

- An HTTP 200 is not a DNS answer. A reply is accepted only when its rcode is NOERROR or
  NXDOMAIN, it is not truncated, its question is the one asked, and every answer record belongs to
  the asked name or a CNAME target the answer introduces. SERVFAIL, REFUSED, truncation or an
  answer for another owner are refused, the next resolver is tried, and a run with no valid answer
  keeps the primary timeout as its stated reason. 2.3.8 accepted any 200 and could report a failed
  lookup as "no CAA, no DNSSEC".
- `SHAKERSCAN_DNS_DOH_RESOLVERS` now reaches the api, worker and agent-tool-worker services in
  both Compose files and the broker worker, passed as `${VAR-default}` so an explicit blank
  disables the fallback. In 2.3.8 the documented setting reached no container.

### Scan report: history claims bounded by the data (#173)

- "Carried over" counts active findings this run neither wrote, last saw nor reported. 2.3.8
  subtracted list lengths across different populations, which counted resolved and false-positive
  rows as unresolved and attributed a finding to earlier scans when a later scan had merely
  re-observed it. The card shows loading and unavailable states instead of a claim while the
  target's history has not loaded.
- The release line names an earlier-scan origin only for blockers the release decision itself marks
  as carried from the target's unresolved set; otherwise it says "on this target" and carries the
  decision's rationale.

### Findings and verification (#173)

- An installation from before the 2.3.8 identity change keeps its triage across it. A CWE-less
  finding already held under the old collapsed identity is reconciled on save when the legacy row's
  title matches: its history and disposition move to the new key instead of a duplicate opening
  beside it. A legacy row for a different check is left alone, so one accepted-risk or
  false-positive disposition never spreads to every split.
- A proof step whose verify siblings split between nothing-to-do and real work runs over the
  sibling that worked. It was settled not applicable without the executor being called.
