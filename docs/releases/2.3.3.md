# ShakerScan 2.3.3

A maintenance release for self-hosted and gateway-fronted deployments. It lets the MCP adapter
and the product CLI authenticate to an API that sits behind an authenticating gateway, gives
deployments that do not mount the Docker socket a real worker count, and corrects how an
incomplete negative Hunt DOM XSS attempt is reported. Upgrade in place from 2.3.2; 0.8.18
remains the oldest directly certified upgrade base. No change to the deterministic proof
boundary.

## Changes

### Agents and scripts behind an authenticating gateway

- `scripts/shakerscan_mcp.py` reads `SHAKERSCAN_API_TOKEN` (printable ASCII, at most 4096
  characters) and sends it as a bearer token on every request to the configured API. A token
  with a plain-`http://` origin is refused before any request is made; the token is never
  printed. Together with `SHAKERSCAN_MCP_ALLOW_REMOTE_API=true` this is how an assistant on a
  workstation drives a remote, authenticated ShakerScan (for example a self-hosted Enterprise
  gateway that issues service tokens).
- `scripts/v2_cli.py` (the product CLI behind `./scanner.sh hunt ...` and the other product
  commands) sends the same bearer token on JSON and download requests, under the same
  https-only rule; loopback use without a token is unchanged.
- `docs/mcp.md` documents the remote, authenticated form.

### Worker inventory without the Docker socket

- `GET /workers` no longer answers `count: -1` with "Docker socket not available" on a
  deployment that does not mount the socket. Every worker already refreshes a build report to
  `shakerscan:worker_build` every 30 seconds; those fresh reports now give the web DAST pool its
  count, its current/stale/pending split and its readiness, exactly the shape the socket-backed
  path produces, so the dashboard shows the real number of workers instead of "Unknown". A
  worker that stops reporting ages out of the freshness window as a removed container would.
- Container scaling still needs the socket: the answer carries `scaling_available: false` with
  the reason, instead of an inventory error. When Redis itself cannot answer, the previous
  "unknown" answer is kept. Deployments with the socket are unchanged.

### Hunt: incomplete negative DOM XSS attempts

- A verified same-origin DOM XSS browser proof stays `success` even when the pinned browser
  blocked unrelated requests (2.3.2 behaviour). A `not_proven` attempt is no longer reported as
  complete when the blocked requests say otherwise: request-budget exhaustion or a refused
  state-changing request make the Hunt `xss.verify` result `partial`, a cancellation makes it
  `cancelled`, and only cross-origin blocks leave it `success / not_proven`. The generic Scan
  browser prover and finding materialization are unchanged.

## Upgrade

Upgrade in place from 2.3.2. No migration; existing approval receipts, target authorizations and
service tokens are unaffected. The stable installer channel advances only after publication and
public smoke.
