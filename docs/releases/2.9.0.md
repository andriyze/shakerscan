# ShakerScan 2.9.0

**Status:** in development on the `release/2.9.0` integration branch. Not a candidate; these notes
grow with each change that lands on the branch.

## Upgrade notes

- **Hunts can no longer edit target instructions by default.** Editing a target's instructions is
  now its own Hunt permission, `instruction_changes`, separate from the metadata permission
  (`metadata_changes`). It is off for every target after the upgrade, including targets whose Hunt
  permissions were saved with metadata changes on. Saved metadata choices are kept as they were and
  still govern renaming targets, creating targets and recording advisory knowledge
  (`purpose: knowledge`). A Hunt that tries to create, update or delete instructions without the new
  permission gets a 403 with `reason_code: instruction_changes_not_delegated` that names
  `targets.skill.propose`.
- **Instructions a Hunt wrote under the earlier rules are now advisory.** Target instructions whose
  last writer was a Hunt acting under metadata delegation (`instruction_authority:
  target_metadata_delegation`) are no longer operator guidance. Their text is kept and Hunts still
  receive it, but separately, as *agent-written, unconfirmed* notes that grant no permission and
  never widen scope. At startup every such record, and every saved action a Hunt saved before this
  release, is marked `origin: agent_unconfirmed` (the text itself is unchanged; the marking runs on
  every start and is a no-op once done). An operator makes the text operator instructions again by
  saving it: in the UI ("Save as operator instructions"), with `PUT`/`POST /targets/{id}/skill`,
  with `POST /targets/{id}/skill/confirm` (the revision and the digest of the text that was read),
  or with `c` in `shakerscan knowledge review`. Saving a saved action again
  (`PUT /targets/{id}/actions/{action_id}`) does the same for it.
- **Saved target actions follow the instruction permission.** A Hunt's
  `targets.actions.create|update|delete` applies only where the target's `instruction_changes` is on;
  otherwise the change is filed as a saved-action proposal for operator review and the result says
  `applied: false`. Saved metadata choices (`metadata_changes`) no longer govern saved actions.
  Operator writes through `/targets/{id}/actions` are unchanged. The generic target and device
  metadata writes now refuse a `hunt_actions` key, as they already refused `target_skill`.
- **To let Hunts edit a target's instructions directly**, turn on "Let Hunt edit these
  instructions" in the target's Hunt permissions, or save `instruction_changes: true` with
  `PUT /targets/{id}/hunt-authority`. Like the other Hunt permissions it is per target, applies to
  subsequent actions including running Hunts, and lapses when the target's URL changes or the target
  is archived. A save that omits the field turns it off.

- **Rolling back to 2.8.x.** 2.8.x ignores the `origin` marks and `instruction_changes`, so Hunt-written
  instructions are again treated as operator-delegated there; upgrading again re-marks them. On 2.8.x,
  reading a target whose instructions a 2.9.0 Hunt wrote under `instruction_changes`
  (`instruction_authority: target_instruction_delegation`) fails (`GET /targets/{id}/skill` answers
  500, an update answers 404) until an operator creates the instructions again with
  `POST /targets/{id}/skill`. The proposal table and its new columns are left in place and unused.

## Instruction proposals

- A Hunt without `instruction_changes` suggests guidance with the new `targets.skill.propose`
  capability: the complete proposed text, the revision it read, a title, a reason and the ids of
  the Hunt actions or receipts, findings, candidates or scans on the target's asset that support it. A proposal applies
  nothing and needs no permission. A Hunt files at most 5; a target holds at most 20 Hunt proposals
  waiting for review (operator proposals have their own 20); a newer proposal from the same Hunt
  replaces its earlier pending one. Proposal text may not contain terminal control characters, invisible formatting characters (zero-width, direction marks, tag characters) or line separators; `shakerscan knowledge review` shows any such character inside a reviewed recipe or instruction text as a visible escape.
- Review proposals in your own terminal with `shakerscan knowledge review [target]` (also
  `./scanner.sh knowledge review`). Each pending proposal is shown with its reason, evidence and a
  diff against the current instructions, and decided with one keypress: `y` accepts, `r` rejects,
  `n` leaves it pending, `q` stops. Only a lone key decides; arrow keys, other escape sequences and
  pastes are ignored, and the command refuses to run from a pipe. `--accept ID` and `--reject ID`
  show one proposal and still ask for the key. Accept is offered only when the whole difference was
  shown, and the decision carries the digest of the text that was shown, which the server checks.
- Accepting writes the proposed text through the ordinary revision-checked instruction write, as
  the operator. If the instructions changed after the proposal was made, it is stale and cannot be
  accepted; rebasing it (`b` in the review, or
  `POST /targets/{id}/instruction-proposals/{proposal_id}/rebase`) files the same text against the
  current instructions so the new difference is reviewed first. Recording advisory knowledge does
  not make a proposal stale.
- Operator API: `GET /instruction-proposals`, `GET|POST /targets/{id}/instruction-proposals`, and
  `POST /targets/{id}/instruction-proposals/{proposal_id}/accept|reject|rebase`. Proposals are
  stored in the new `target_instruction_proposals` table, created at startup.
- Pending proposal text never reaches a Hunt's instructions, briefing or planner context.
- Saved-action proposals share the same table (`kind: saved_action`, with the operation, the action
  id and the proposed recipe), list, routes and review command. The reviewed text is the recipe as
  indented JSON with control, invisible formatting and line-separator characters escaped; accepting applies the
  recipe through the ordinary revision-checked saved-action write, as the operator, and binds to the
  digest of the text that was shown. A saved-action proposal is stale whenever the target's saved
  actions changed after it was made. A Hunt may add `reason` and `evidence_refs` to a saved-action
  write; it files at most 5 saved-action proposals, separately from instruction proposals, and a
  newer proposal for the same action replaces its earlier pending one. `GET /instruction-proposals`
  and the per-target list take `kind=instructions|saved_action` and also return
  `unconfirmed_instructions`: targets whose instructions are agent-written and unconfirmed, with
  their text, for `shakerscan knowledge review` to confirm.

## Hunt briefing

- Every Hunt start response, `GET /hunts/{id}` and the summary query now carry a bounded `briefing`
  (`hunt-briefing/v1`, about 24 KB at most): the operator instructions as snapshotted at start
  (whole, or their headings and a leading part with `more_available` and where to read the rest),
  the objective, an effective authority summary (scope, permissions, target delegation, approval
  requirements, budget limits and use), knowledge counts by kind, the number of pending instruction
  proposals, and unresolved work (open candidates; authorization investigations on the asset that are
  proposed but not run, awaiting execution, inconclusive, deferred or needing review, counted from the
  same projection the authorization workflow uses; actions in progress or awaiting permission).
  Anything shortened is listed in `briefing.trimmed`. Instructions a Hunt wrote under delegated
  permission are marked `operator_reviewed: false`.
- Agent-written, unconfirmed instructions appear in the briefing only under their own
  `unconfirmed_instructions` section (heading "Agent-written, unconfirmed", whole up to about 4 KB,
  otherwise a leading part), never in `instructions`; the context pack carries them in
  `target_skill.unconfirmed`. Hunts started before the upgrade are read the same way.
- Saved target actions in the Hunt context carry `trust`: `operator`, `operator_delegated` (saved by
  a Hunt under `instruction_changes`) or `agent_unconfirmed`; only operator and operator-delegated
  recipes are operator guidance, and none grants authority. `GET /targets/{id}/actions` and the
  target page label each saved action the same way. A recipe or instruction text written under
  `instruction_changes` keeps that label after the operator turns the permission off; turning it
  off stops further changes, and an operator save or delete is how earlier ones are withdrawn.
- A device Hunt can record investigation candidates through `POST /hunts/{id}/candidates` (it
  answered 500 before).
- The briefing's unresolved work counts authorization investigations on the asset from the records
  the authorization workflow keeps (`authorization_investigations`: proposed but not run, awaiting
  execution, inconclusive, deferred, settled, needing review), actions awaiting permission
  (`awaiting_permission_actions`), and caps the open-candidate count with an `at_least` flag. It
  replaces `inconclusive_experiments`, which counted records the workflow never writes.
- The compact MCP view of a Hunt, which leaves out the context pack, always keeps the briefing. The
  Hunt skill and MCP tool descriptions tell agents to read it first and to treat its operator
  instructions as guidance, never as authority.
