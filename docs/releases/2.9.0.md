# ShakerScan 2.9.0

**Status:** in development on the `release/2.9.0` integration branch. Not a candidate; these notes
grow with each change that lands on the branch.

## Upgrade notes

- **Hunts can no longer edit target instructions by default.** Editing a target's instructions is
  now its own Hunt permission, `instruction_changes`, separate from the metadata permission
  (`metadata_changes`). It is off for every target after the upgrade, including targets whose Hunt
  permissions were saved with metadata changes on. Saved metadata choices are kept as they were and
  still govern renaming targets, creating targets and recording advisory knowledge
  (`purpose: knowledge`). A Hunt that tries to create, update or delete instructions without the new
  permission gets a 403 with `reason_code: instruction_changes_not_delegated` that names
  `targets.skill.propose`.
- **Instructions a Hunt wrote under the earlier rules are now advisory.** Target instructions whose
  last writer was a Hunt acting under metadata delegation (`instruction_authority:
  target_metadata_delegation`) are no longer operator guidance. Their text is kept and Hunts still
  receive it, but separately, as *agent-written, unconfirmed* notes that grant no permission and
  never widen scope. At startup every such record, and every saved action a Hunt saved before this
  release, is marked `origin: agent_unconfirmed` (the text itself is unchanged; the marking runs on
  every start and is a no-op once done). An operator makes the text operator instructions again by
  saving it: in the UI ("Save as operator instructions"), with `PUT`/`POST /targets/{id}/skill`,
  with `POST /targets/{id}/skill/confirm` (the revision and the digest of the text that was read),
  or with `c` in `shakerscan knowledge review`. Saving a saved action again
  (`PUT /targets/{id}/actions/{action_id}`) does the same for it.
- **Saved target actions follow the instruction permission.** A Hunt's
  `targets.actions.create|update|delete` applies only where the target's `instruction_changes` is on;
  otherwise the change is filed as a saved-action proposal for operator review and the result says
  `applied: false`. Saved metadata choices (`metadata_changes`) no longer govern saved actions.
  Operator writes through `/targets/{id}/actions` are unchanged. The generic target and device
  metadata writes now refuse a `hunt_actions` key, as they already refused `target_skill`.
- **To let Hunts edit a target's instructions directly**, turn on "Let Hunt edit these
  instructions" in the target's Hunt permissions, or save `instruction_changes: true` with
  `PUT /targets/{id}/hunt-authority`. Like the other Hunt permissions it is per target, applies to
  subsequent actions including running Hunts, and lapses when the target's URL changes or the target
  is archived. A save that omits the field turns it off.

- **Rolling back.** 2.8.3 reads every record this release writes: an instruction authority it does
  not know reads as `none` and any `origin` other than `operator` makes the text advisory there, so
  instructions a Hunt wrote under `instruction_changes` are advisory after a rollback to 2.8.3.
  2.8.2 and earlier cannot read such a target (`GET /targets/{id}/skill` answers 500 and an update
  404) until an operator creates the instructions again with `POST /targets/{id}/skill`; roll back to
  2.8.3. 2.8.x ignores `instruction_changes`, so metadata delegation lets Hunts write instructions
  there again (saving Hunt permissions on 2.8.x drops `instruction_changes`, which then reads as off
  after upgrading again); upgrading again re-marks text Hunts wrote meanwhile. The
  proposal table and its new columns are left in place and unused. This release reads records a
  later engine writes the same way: unknown authorities as `none`, unknown origins as
  agent-written and unconfirmed.

- **Interpretations and negative results (new table, nothing rewritten).** Startup creates the
  `target_interpretations` table. Each target's advisory knowledge text (`purpose: knowledge`) is
  also kept as one `note` entry among its interpretations, written by `system:knowledge-import`:
  created at the first start, superseded by a new note whenever the knowledge text changes (on
  every write and, for changes made elsewhere, at the next start) and superseded without a
  replacement when the knowledge is deleted. The note keeps the original writer in
  `subject.written_by` (text a Hunt wrote reads as an agent interpretation) and shows control and
  invisible characters as visible escapes. The knowledge slot itself is never rewritten. No
  existing finding, hypothesis, candidate or authorization record changes at upgrade. The import
  runs after the schema is committed, still under the startup lock, in committed batches of 100
  targets, so a target row is locked for one batch at most; an interrupted start resumes where it
  stopped.
- **Retracting a knowledge note withholds that knowledge text from Hunts.** When an operator retracts
  the note (alone, or with every entry of the Hunt that wrote it), the target's knowledge slot keeps
  the text but adds its digest to `knowledge_withheld` (a set: every withheld text stays withheld,
  whichever is retracted later). Whenever the current knowledge text's digest is in the set, Hunt
  starts and Hunt reads (`context_pack.target_skill.advisory`, `targets.skill.read`, Hunt skill
  writes, and the knowledge notes holding that text in kind `interpretations`, including a note
  created when a later Hunt writes the same text again) leave it out and say it was withheld;
  `text_contains` does not match it. `GET /targets/{id}/skill` still shows the text and
  its withholding to operators. A Hunt writing the same text again does not lift it; an operator
  saving a knowledge text lifts the withholding of exactly that text.
- **A Hunt whose entries an operator retracted stops writing.** Retracting a Hunt's entries also
  records `entries_retracted` in that Hunt's notes (`GET /hunts/{id}/record`): for the rest of its
  run every write of text later Hunts or operators read is refused with 403
  `hunt_entries_retracted`: `knowledge.record`, `targets.skill.create|update|delete`,
  `targets.actions.create|update|delete`, `targets.create` and `targets.update` (target names),
  `findings.create|update` and `POST|PATCH /hunts/{id}/candidates`. Its debrief is not handed to
  later Hunts as the prior Hunt's continuation. `targets.skill.propose` and reads still work, so it
  can only suggest changes for review.
- **A dismissal ends when the finding's status leaves `false_positive`/`accepted_risk` by any
  path.** A trigger on `findings` marks the active dismissal `reopened` (`system:finding-status`)
  whether the change comes from the finding routes, a scan or verifier re-detecting the finding, or
  another engine; startup also reconciles dismissals once.
- **A Hunt no longer marks findings as false positives or accepted risks.** `findings.update` from a
  Hunt accepts only `active` and `resolved` (still only on unverified findings that Hunt created);
  `false_positive` and `accepted_risk` are an operator's triage decision. A Hunt also cannot change
  or delete a finding an operator dismissed or reopened through the new routes.
- **Rolling back to 2.8.3 with interpretations.** 2.8.3 ignores the `target_interpretations` table
  and the `knowledge.record` and `knowledge.check_experiment` actions in a Hunt's history. A
  finding an operator dismissed through the new route keeps the status and analyst verdict it was
  given (`false_positive` or `accepted_risk`; verdict `false_positive`, `duplicate` or
  `accepted_risk`), values 2.8.3 already uses; a reopened finding is `active` with verdict
  `needs_review`. The `findings` trigger and its function stay installed on 2.8.3 and keep ending
  dismissals whose finding's status changes there; upgrading again finds the table as it was left.
  On 2.8.3, `knowledge_withheld` is ignored: knowledge text an operator withheld reaches Hunts again
  until the upgrade. A target merge on 2.8.3 deletes the duplicate target's interpretations
  (including dismissal records) with the duplicate; the findings themselves move as before.

## Finding retests

- **Retests are re-checked while they run.** This removes the 2.8.2 and 2.8.3 known limitation
  "Finding retests are checked only when they are admitted, not while they run". A finding retest
  is now checked against its authorization before it starts and every 2 seconds while it runs, as
  device, AI and local web Scans have been since 2.8.2. A retest is stopped when the target's
  authorization is revoked, when an approval it runs under expires, when the target is deactivated
  or its URL or scope changes so that its authorization no longer covers it, or when the scope
  that admitted the retest no longer covers the host it replays. The tolerance is the same: a
  database that does not answer for 10 seconds stops it as `authorization_unverified`, never as a
  revoke, and a replay still running 5 seconds after the stop is cancelled.
- **What a retest is bound to.** When it is queued, a retest records the target, the target's
  current authorization and the approval receipt the request named
  (`finding_verifications.admitted_authority`, a new nullable column added at startup). This
  applies to the finding page's Retest button and `POST /findings/{id}/retest`, the bulk route
  `POST /findings/retest`, the Arsenal `finding.retest` command and the refuter and research
  paths that use it, and the automatic retests after a Scan (which also bind the Scan's approval
  receipt). A retest the worker requeues keeps its binding. A retest queued while neither receipt
  existed has nothing to revoke and is not watched, as before.
- **The replayed URL must be in scope.** A retest replays the finding's URL (`original_url`, which
  `POST /findings/{id}/retest` lets the caller override). That host must be covered by the scope
  that admits the retest: the approval receipt the request named, otherwise the target's
  authorization. This applies even when no approval is named; before, a retest of an authorized
  target could replay any host. Hosts are compared in the strict spelling the client connects to
  (IDNA 2008, canonical IP literals, no public-suffix roots), the rule every other admission
  uses; a URL whose authority contains a backslash or whitespace has no host and is refused.
  `POST /findings/{id}/retest` answers 400 `replay_url_out_of_scope`, the bulk route skips the
  finding with that reason, and automatic and candidate retests are not queued. A Scan stopped by
  its authorization queues no automatic retests. A retest whose target has no authorization and
  that names no approval has nothing to check its destination against and runs as before.
- **Redirects stay in scope.** While a watched retest runs, its requests and every redirect hop
  must go to a host the admitting scope covers. A request or hop outside it is refused, and a
  replay that had one refused records `inconclusive` with the refused hosts in
  `artifacts.refused_destinations`, never fixed (a proof from in-scope traffic stands).
  - HTTP replay steps follow redirects one checked hop at a time instead of letting curl follow
    them. A 303, and a 301 or 302 answering a POST, continue as a GET without the body; after 5
    redirects the last redirect response is returned; each hop has the step's own timeout; no
    cookies are carried between hops (as before, only the retest's own authentication headers
    are sent).
  - Every headless browser context opened during a retest (the XSS proofs and AI verification,
    and any other browser code it reaches) sends all of its traffic -- navigations, every
    redirect hop, images, fetch, beacons, WebSockets -- through a local proxy that refuses hosts
    outside the scope and closes each plain-HTTP connection after one request, so every request
    is checked. Service workers are blocked and WebRTC is disabled (its UDP would bypass any
    proxy). In-scope redirects and cookies behave as before. Proxy failures are kept on the
    retest as `artifacts.destination_guard_incidents` (host and error class).
  - The rule is by host name or IP literal, as the scope names hosts. It does not check the
    address a name resolves to, so a name that resolves elsewhere (DNS rebinding) is not caught,
    and ports are not constrained.
- **Findings without a target.** A finding retested under an approval but with no target is
  watched against that approval and the replayed host only.
- **Hunt candidate verification is unchanged.** `candidate.verify` runs one bounded workflow inside
  the Hunt and is checked when each action is dispatched, as every Hunt action is. It is not a
  finding retest and is not re-checked while it runs.
- **A stopped retest records no verdict.** It is `failed` with verdict `error`,
  `retry_class: authorization` and the stop in `artifacts.authority_stop` (reason, when it was
  observed, before or while running). `GET /retests/finding/{id}` and `GET /retests/{id}` return it
  as `authority_stop` and `stop_reason` (`authorization_withdrawn` or `authorization_unverified`).
  The finding records an attempted verification with verdict `error`, never fixed, still vulnerable
  or false positive, and a candidate is settled inconclusive. An AI Gate finding replay stopped by
  its authorization is recorded the same way instead of as likely fixed.
- **UI.** The finding page shows a stopped retest with the cause and that no verdict was recorded.
  A Scan that failed because its authorization was withdrawn now says so ("This scan was stopped
  because the target's authorization was revoked") instead of "stopped during the failed phase",
  and the Scan report banner also names a stop where the authorization could not be confirmed.
- **Queued across the upgrade.** A retest queued by 2.8.x has no binding. When it starts on 2.9.0
  it is bound to the target's current authorization and to the approval receipt its queue message
  named (or, when a requeue lost the message, the one its operation record names); its replayed
  host is checked as at admission, the binding is saved on the row, and it is watched from then
  on. If an authorization the target had when the retest was queued has gone since (revoked,
  expired, or no longer covering the target), the retest is refused before any traffic, even if
  the target was authorized again afterwards.
- **A stop that cannot be recorded.** The stop is published on the retest job first and the row is
  settled with retries; if the database stays unreachable, the stale-retest watchdog settles the
  stop later instead of requeueing the retest.
- **Upgrade workers with the API.** A worker or fleet node still on 2.8.x runs any retest it takes,
  including one 2.9.0 queued, without this watch. Upgrade every worker and fleet node together with
  the control plane, or let the retest queue drain before upgrading.
- **Rolling back to 2.8.3.** 2.8.3 ignores `admitted_authority` and runs retests as before, checked
  only when admitted. A stopped retest's record reads there as a failed retest with verdict
  `error`. 2.8.3 returns every column of a retest row, so `GET /retests/...` there also shows the
  `admitted_authority` record (target and receipt ids).

## Interpretations and negative results

- Hunts record what they learn as attributed **interpretations** with the new read-only
  capability `knowledge.record`: an `observation`, `hypothesis`, `explanation`, `next_step` or
  `note`, or a `negative_result`. Each entry records its writer (`hunt:<id>` or `operator:<id>`, set
  by the server), optional agent and model labels (attribution only), `provenance` (`observed`,
  `inferred` or `quoted_from_target`), `observed_at`, `evidence_refs`, `conditions`, an optional
  `subject` (a finding, hypothesis, candidate, authorization investigation, endpoint or another
  entry) and `supersedes`. Observations, explanations and negative results must cite at least one
  existing record on the target's asset: a Hunt action or receipt, finding, candidate, scan,
  hypothesis, authorization investigation or interpretation, and at least one of them must be
  something other than an interpretation. An entry is advisory: it is not proof,
  changes no finding, hypothesis or candidate, and grants nothing.
- Entries are appended and superseded, never rewritten. A Hunt supersedes only entries it wrote
  itself; it records a contradiction of another entry as a new entry (`subject` type
  `interpretation`), and both stay visible.
- **Negative results** have four states:
  - `experiment_completed_negative`: the exact experiment ran and showed nothing. It must cite the
    testing action (or its receipt) that ran it, finished as completed or partial (a Hunt cites its
    own actions; control-plane steps such as reads of target records do not count), and name the
    exact conditions: the technique, the operation or the method and route, the principals, objects
    or inputs, and optionally roles, service, environment, deployment fingerprint, tool version,
    application state and budget. Conditions are exact literals, and every negative result shown to
    a Hunt or operator says so (`conditions_semantics`): a value such as `{a,b}` or `1..100` covers
    only that literal string, never a set or range. Values with explicit wildcard or pattern
    meaning are refused: asterisks and stars in any Unicode form, ellipses, regular-expression and
    SQL wildcard syntax, and words such as "all", "any" or "every" as a value, after Unicode
    compatibility folding and in every value of the object fields; so are values mixing Latin with
    look-alike letters from other scripts, and unknown condition fields. A method is one HTTP token
    (`M-SEARCH` is accepted; `GET|POST` and `*` are not). A route (with or without its leading
    slash), or an object given as a path, may contain such words as literal segments
    (`/api/users/all`), an exact query string and percent-encoding. Principals and roles may
    contain apostrophes and commas (`O'Brien, Pat`). Its experiment key covers every condition; it is matched only on the same
    target and kept when duplicate targets are merged. The conditions are recorded as the writer
    states them; they are not yet checked against the cited action's request, which matters
    only once identical experiments can be skipped.
  - `experiment_inconclusive`: ran but could not decide; it cites the finished testing action the
    same way. It never suppresses anything and is listed in the briefing as unfinished work.
  - `hypothesis_refuted`: evidence contradicts one hypothesis under its recorded conditions; it
    does not change that hypothesis's status or any related hypothesis. A Hunt's negative result
    cannot name a finding as its subject.
  - `finding_dismissed`: an operator's triage decision. No Hunt capability, query or MCP tool can
    record it, and the table refuses a dismissal not written by an operator.
- **Reuse is narrow.** `knowledge.check_experiment` takes exact conditions and returns the
  identical experiments already recorded on the target. `skip` is true only as described under
  "Applicability and changes" below, and it is advice: nothing blocks running the experiment again.
  Inside one Hunt, the authorization workflow still refuses to repeat a settled experiment unless a
  retest is requested.
- Hunts read entries with `POST /hunts/{id}/query` (and `shakerscan_hunt_query`) kind
  `interpretations`, filtered by `kind`, `status`, `negative_state`, `provenance`, `hunt_id` or
  `text_contains`, with a cursor. The title and body of every entry a Hunt wrote (and of imported
  knowledge not written by an operator) come back only under `untrusted_data`, whatever provenance
  it declared (the server cannot tell an agent's words
  from text it copied from the target), with a notice naming it an agent's claim or target-quoted
  data; operator-written text is returned as written. Of a retracted or superseded entry, Hunts see
  neither the text, the note, the conditions, the subject nor the labels (superseded entries are
  history only), and `text_contains` never matches them. A device Hunt
  reads its own entries and its service members'; any other Hunt reads its own target's only.
- Kind `negative_results` lists recorded negative results together with the negatives existing
  server records already establish, each labelled with its source: settled authorization
  investigations whose latest outcome is refuted (`experiment_completed_negative`) and
  inconclusive ones (`experiment_inconclusive`), with their exact conditions (route, selected object
  digest, the two sessions and the frozen target context), adjudicated refuted hypotheses and
  verifier-refuted candidates (`hypothesis_refuted`). Filter with `state` and `source`.
- A Hunt writes at most 200 entries; a Hunt's entry body is at most 4,000 characters (an
  operator's 12,000), a title 200. Text may not contain control characters other than newline and
  tab, invisible formatting characters (zero-width, direction marks, tag characters) or line
  separators, and is refused when it looks like a credential. The Hunt action ledger keeps digests
  of the title, body and conditions, not the text.
- The Hunt briefing gains an `interpretations` section: active entries by kind and negative state,
  reopened dismissals, and up to five headlines each of open next steps and inconclusive
  experiments. An operator's headline carries its title; an agent's title arrives only under
  `agent_claim` with a notice that it is data, never an instruction; titles quoted from the target
  are withheld; bodies never appear. Headlines are the first thing removed when the briefing is over its size
  limit, and the removal is listed in `briefing.trimmed`.
- Retracting an entry also retracts the entries its writer chained to it by `supersedes`, current
  or superseded; for knowledge notes the chain follows the author of each mirrored text, so
  retracting a Hunt's knowledge never retracts an operator's, and retracting one knowledge note a
  Hunt wrote retracts every version of knowledge that Hunt wrote on the target, also past operator
  versions between them. Retracting a Hunt's entries covers its
  superseded entries too. A superseded entry can be retracted on its own. Hunts see no
  `experiment_key` or conditions digest of a retracted or superseded entry, and
  `knowledge.check_experiment` lists only active entries.
- Operator API (not reachable through the Hunt planner ingress, and refused for requests that came
  through it):
  - `GET /targets/{id}/interpretations` (filters `kind`, `status`, `negative_state`, `hunt_id`) and
    `POST /targets/{id}/interpretations` (an operator's own entry);
  - `POST /targets/{id}/interpretations/{entry_id}/retract` and
    `POST /targets/{id}/hunts/{hunt_id}/interpretations/retract` (every active entry one Hunt wrote
    on the target, in one operation), each with a `note`;
  - `GET /targets/{id}/negative-results` (filters `state`, `source`);
  - `POST /targets/{id}/findings/{finding_id}/dismiss` with `reason` (`false_positive`,
    `accepted_risk` or `duplicate`) and a `note`: sets the finding's status (`false_positive`, or
    `accepted_risk`) and analyst verdict, and records the decision with the finding's tool, URL,
    severity, verification verdict and last-seen time at that moment. A finding has at most one
    active dismissal;
  - `POST /targets/{id}/findings/{finding_id}/reopen` with a `note`: the finding becomes `active`
    with verdict `needs_review`; the dismissal stays in the history as `reopened`.
  - changing a dismissed finding's status by any other path ends the dismissal the same way
    (`reopened`, by `system:finding-status`). Merging duplicate targets moves their
    interpretations, dismissals and instruction proposals to the surviving target; a duplicate's
    knowledge note becomes history (`superseded`), so the survivor keeps one.
- CLI: `shakerscan knowledge show TARGET [--kind K] [--status S]` lists entries and negative results
  (read-only). `shakerscan knowledge dismiss TARGET FINDING --reason R --note TEXT` and
  `shakerscan knowledge reopen TARGET FINDING --note TEXT` show the finding and decide with one
  lone keypress (`d` or `o`), with the same handling as `knowledge review`: arrow keys, escape
  sequences and pastes never decide, and the commands refuse to run from a pipe.
- The target page shows a read-only list of interpretations and negative results, labelled by
  writer and source; text quoted from the target is shown as a quotation.

## Applicability and changes

- Each entry now records what it depends on, observed when it is written (`dependencies`): the
  route in the endpoint inventory (from the conditions' method and route or operation, an endpoint
  subject, or the path a cited `http.request` asked for); the responses of cited plain `http.request`
  actions (status, media type, JSON key set; the body digest stays on the action and is not copied);
  the technologies, versions and server banners of the latest completed Scan of the same target that
  recorded them; the login, token, session and SSO routes when the conditions name principals or
  roles or the route is one of them; a device service named as `tcp/<port>` or `udp/<port>`; and the
  record named as subject. A dismissal depends only on its finding. A plan or note without such
  references records none.
- A **plain request** is an `http.request` whose recorded input holds only `method`, `path` (no query
  string), `origin` and `session_ref`. Anything else recorded with it (a body, which the action
  ledger keeps as `body_kind`; `as_principal`; `via_address`; `follow_redirects`; query; headers;
  captures; request bindings) makes it a different request that is never compared with a plain one.
  A request's origin is the one it names, or its Hunt's target origin. Origins are compared as
  `scheme://host[:port]` with the default port dropped and IPv6 brackets kept; an origin whose host
  ends in a dot is refused (in conditions) or not comparable (in a request), never folded.
- `applicability` is one of `applicable` (every dependency observed, none changed significantly),
  `needs_revalidation` (one changed significantly), `historical` (the record it is about, or its
  route, is gone) or `unknown` (a dependency was not observable when the entry was written, for
  example no Scan has recorded technologies, or cannot be compared now). Superseded, retracted and
  reopened entries are never applicable. Age never changes applicability. `needs_revalidation` only
  ever moves on to `historical`; neither is undone when a dependency changes back. Re-testing and
  recording a new entry that supersedes the old one is how a conclusion becomes current again.
- Significance rules, published with every change report (`significance_rules`):
  - endpoint: every inventory row of the route retired as gone is significant; the route first
    appearing in the inventory, a new auth state or parameter shape is minor;
  - response: compared with every distinct later response of the same plain request (method,
    origin, path, session), however many requests came in between (an indexed lookup by path, no
    window; repeats are distinct only by their request input and response, so identical repeats count
    once; more than 1,000 distinct later responses counts as a change); a different status code,
    media type or JSON key set is significant; a different body digest is significant for a negative
    result (the same status and keys can carry another tenant's data) and minor otherwise; digests of
    different formats (plain SHA-256 and the installation-keyed digests) are incomparable and leave
    the entry `unknown`; a body over the capture limit (32 KiB) is digested only as a prefix
    (`body_digest_scope: prefix`) and its JSON does not parse, so on either side its digest and key
    set are incomparable (the entry stays `unknown`, never unchanged, and is never reused);
  - deployment: compared with the latest later Scan of the same target that recorded technologies (a
    Scan without technologies or banners compares nothing); a version change, a versioned
    technology appearing or disappearing, or a changed server banner is significant; an unversioned
    technology appearing or disappearing is minor; a certificate renewal or address change is
    reported but changes no entry;
  - authentication surface: a login, token, session, sign-up, password or SSO route appearing or
    disappearing is significant;
  - service: no longer observed open, or a changed product or version, is significant;
  - dismissal (a finding): a higher severity, a changed URL, the finding resolved and detected again
    (`resurfaced_count` rose), or a verifier proving it `exploited` while it is dismissed as a false
    positive or duplicate is significant. A verdict agreeing with the dismissal, an error,
    inconclusive or cleared verdict, a lower severity, a different tool name, new scanner evidence for
    the same issue, a Scan or a release alone are not.
- **Reuse.** `skip` from `knowledge.check_experiment` is true only when every one of these holds:
  - the entry is an active `experiment_completed_negative` with the identical experiment key (every
    condition, the origin included);
  - it was evaluated during that call and is `applicable`; an entry the call could not evaluate
    (another evaluation holds the target or the row, or the evaluation failed) is never reused;
  - its dependencies include the Scan technologies, the route and a response;
  - its conditions are bound to a plain request one of the writing Hunt's own cited `http.request`
    actions recorded: the conditions name only origin, method, route or operation, principals,
    objects and technique; the origin (`scheme://host[:port]`, a new condition field) is the
    request's origin; the method is the same; the route as written is the requested path with each
    `{placeholder}` in a segment holding an identifier and filled by exactly one named object (every
    named object fills exactly one placeholder, and no named id stands in a literal segment); exactly
    one principal is named and it is the request's `session_ref` (`anonymous` without a session);
    and the technique's first word is `http.request`;
  - and the **same plain request** (method, path, origin, session) was **repeated by a Hunt after the
    asking Hunt started**, and every such response equals the recorded one, body digest included.
    Scans and the endpoint inventory never authorise a skip (they cannot re-observe an authorization
    decision, and a Hunt's own crawl updates the inventory); they feed applicability and
    `needs_revalidation` only.

  `applicable` does not mean safe to skip: skip advice is rare by design. Not being contradicted is
  not enough; this is about evidence, not age.

  Entries citing other capabilities, or naming inputs, roles, service, environment, deployment
  fingerprint, tool version, application state or budget, are recorded as before but never let an
  experiment be skipped. The binding (or why it failed) is shown under `dependencies.binding`, and
  the reason for every `skip: false`. The skip is advice: nothing blocks running an experiment.
- An operator's dismissal whose dependencies change significantly is reopened for review: the entry
  becomes `reopened` (by `system:applicability`, with the changes in its note) and the finding becomes
  `active` with verdict `needs_review`, for an operator to decide again. When duplicate targets are
  merged, a dismissal of a finding merged into another follows the surviving finding (the newest
  active one stays active and its decision is applied to the survivor; others become superseded
  history) instead of being deleted with the merged-away row.
- Applicability is re-evaluated from existing records when entries are read (the operator list,
  negative results, the briefing, `knowledge.changes`) and, for the identical entries, by every
  `knowledge.check_experiment`: these reads write applicability states, and reopen dismissals. One
  evaluation covers at most 300 entries of a target (least recently checked first, skipping rows
  another evaluation holds), is skipped when another evaluation of the same target is running, and is
  not repeated for a target within 15 seconds in one API process; the reuse check is never throttled.
- **What changed** (`knowledge.changes`): the new read-only Hunt capability `knowledge.changes`,
  query kind `changes` (`filter.since`, also through `shakerscan_hunt_query`), the operator route
  `GET /targets/{id}/knowledge/changes?since=` and `shakerscan knowledge changes TARGET [--since S]`
  report, from existing records only, what changed since `last_hunt` (from the start of the Hunt
  before this one, or the latest Hunt; the default), `release` (from the last Scan before the most
  recent Scan-detected deployment change), `scan:<id>`, `hunt:<id>` (both on the same target) or an
  ISO-8601 time with a time zone: endpoints added and retired, authentication routes added and
  removed, deployment changes between the Scans either side, response changes on the requests
  active entries depend on (the latest 200 requests to each path either side), device services first
  seen or no longer observed, new subdomains under an apex a person added (from discovery and the CT
  monitor; with the latest discovery runs; host names for operators, a count for a Hunt), new and
  resolved findings, Hunts since, and the entries whose applicability changed or whose dismissal was
  reopened since then, each with the dependency that changed. Lists hold at most 25 items and counts
  stop at 1,000 (stated). Reports for `last_hunt`, `release`, a Scan or a Hunt are kept for 10
  seconds per API process (`built_at`); a report for an arbitrary time is built each time. It sends
  no traffic and starts nothing; paths, technology names, versions and banners come from the target
  and are data (`quoted_from_target`). A Hunt reads only its own target (a device Hunt also its
  service members); the operator route is not reachable through the planner ingress.
- The briefing gains `changed_since_last_hunt`: counts of those changes and up to five affected
  entries (ids, states and the dependency that changed; no text), computed at most once per 30
  seconds per Hunt and API process (`computed_at`). Its lists are removed first when the briefing is
  over its size limit, with the removal listed in `briefing.trimmed`. The report and briefing caches
  hold at most 16 MB together in one process.
- Schema: `target_interpretations` gains `dependencies`, `applicability`, `applicability_reason`,
  `applicability_changed_at` and `applicability_checked_at`, and `hunt_actions` gains the partial
  index `idx_hunt_actions_http_request_path` (`http.request` actions by recorded path), built once at
  the first start of this release inside the startup transaction: on a large installation it blocks
  writes to `hunt_actions` (Hunt actions) until it is built, so plan the upgrade start accordingly. The always-run
  startup section adds them only when missing (and `db/init.sql` has the same definitions), so these
  additions take no table lock on a normal start; the earlier interpretation indexes'
  `CREATE INDEX IF NOT EXISTS` statements still take a brief SHARE lock on `target_interpretations`
  at every start. Entries written before this change record no dependencies and stay `unknown`.
  Rolling back to 2.8.3 ignores the table and the index as before; upgrading again evaluates entries
  against the records as they are then.

## Continue after the latest release

- `shakerscan knowledge continue <target>` (operator route `GET /targets/{id}/knowledge/continue`, Hunt
  capability `knowledge.continue`, Hunt query and MCP `shakerscan_hunt_query` kind `continue`) is one
  bounded, read-only report: what changed since the release (`since` defaults to `release`; also
  `release:<marker id>`, `last_hunt`, `scan:<id>`, `hunt:<id>` or a time), then the target's
  conclusions sorted into `still_applicable` (applicable, and positively observed after the release by
  the bound plain request (method, path, origin, session) repeated with every response unchanged, body
  included; a Scan confirming the deployment and route, or being written after the release, is not
  enough and leaves it a required re-test),
  `needs_revalidation` (a dependency changed), `not_reobserved_since_release` (no change detected, but
  nothing observed the conclusion again after the release, or a dependency is unknown), `historical`,
  unfinished work (inconclusive experiments, open next steps, open authorization investigations) and
  dismissals reopened for review. Entry text is not repeated; agent text stays under `untrusted_data` in
  `kind=interpretations`.
- `next_experiments` ranks candidates by fixed, published rules (`rules`): tier 1 conclusions whose
  dependencies changed (completed negatives first, authentication causes first), 2 new login, token,
  session or SSO routes, 3 conclusions not re-observed since the release, 4 new routes, 5 unfinished
  work, 6 retired routes, 7 next steps an agent proposed. Inside a tier the rule's own order, then the
  newest record, then the record id: the same records always rank the same way. Each item names its
  basis, a suggested capability and input (the bound request when the server bound one) and whether
  the Hunt's current policy covers it (`allowed`, `needs_approval`, `outside_authority` with the reason,
  including a spent budget, a capability not on the allowlist, a state-changing request without
  permission, or a Hunt that no longer runs). Required re-tests (the first and third groups) are never
  dropped: each is listed among the items or under `outside_authority`, with totals. Reuse advice from
  `knowledge.check_experiment` does not remove one. The report sends nothing, starts nothing and grants
  nothing; every action is still admitted and enforced on its own.
- A Hunt may now supersede another Hunt's observation or experiment result only with a re-test: the
  entry is due (needs revalidation, unknown, or written before the latest release), the new entry has
  the same kind and outcome and the identical conditions, and it cites the Hunt's own completed
  plain `http.request` (the binding's allowlist) that repeated a request the earlier entry recorded or
  was bound to (method, path, session and origin), after it. The
  earlier entry stays visible as superseded. An operator's entry is never superseded by a Hunt; a
  different outcome is recorded beside the earlier entry. Any other cross-writer supersede is refused.
- Conclusions are classified from a live evaluation (a stored `applicable` that is no longer so counts
  at once), in their own window of 300 (changed ones first, then the oldest; notes and plans do not
  count against it). When anything was not read (more conclusions, or authorization investigations),
  `required_retests.at_least` is true with the reasons. The best-ranked items are always listed first,
  then every remaining required re-test. Suggestions name only `http.request` or `authz.verify`.
  Authority is evaluated on every call from the current policy; the records part is cached 10 s.
- Refresh: when no Scan has recorded technologies, or the latest is older than the release, the report
  offers a passive Scan (`policy.active_testing: false`), and under a person-added apex a passive
  subdomain discovery. It is never started by the report or by a Hunt: `shakerscan knowledge continue
  <target> --refresh` shows each offer and starts it only after a keypress at the person's own terminal
  (a pipe is refused); anything that is not a passive Scan or discovery request is skipped.
- Release markers: `shakerscan knowledge release <target> [--label L] [--at TIME]` (after a keypress) and
  `POST|GET /targets/{id}/knowledge/releases` record that a target was released (see below for how
  `since=release` chooses between a marker and a Scan-detected change). A marker changes no applicability
  and grants nothing; markers are append-only. No Hunt capability or query declares one. Schema: the new
  `target_release_markers` table is created by the always-run startup section (and `db/init.sql`); a
  merged duplicate target's markers follow it.
- Authorization workflow: a settled refuted authorization investigation is now evaluated for
  applicability (`negative_results` and the continue report) from its own records, anchored at its
  attempt's completion: later transactions repeating the same request for the primary or secondary
  principal, every later Scan's technologies, the route in the endpoint inventory (it must have been in
  the inventory when the experiment ran, otherwise `unknown`) and authentication routes first seen,
  retired or revived since. Its binding is the workflow's own (proposal digest, attempt input digest).
  Nothing is stored for it. Other capabilities' results (for example `collections.replay_*` run outside
  the workflow) stay `unknown`.
- Paging is by cursor: each page lists up to `limit` ranked items (default 25, at most 100) and up
  to 100 outside authority, in the fixed sort order, strictly after the cursor of the previous page
  (`after` = `next_experiments.next_after`, on the capability, the query filter and the operator route;
  `shakerscan knowledge continue --after C` or `--all`). Entries superseded, added or moved between
  runnable and outside authority between pages never shift what is skipped; `set_digest` covers every
  candidate and its authority, and `changed_since_cursor` says when the set changed (`--all` starts
  again, at most three times). `unlisted` counts what is not shown yet. `required_retests.total` counts
  conclusions; `unique_requests` counts distinct experiments.
- Request identity is the principal the session store recorded for the request's session
  (credential profile and its version, principal slot and label), never the per-Hunt session id and never text an agent
  wrote: a later Hunt with a session of the same profile and principal makes the same request, so it
  can re-observe a conclusion or re-test it. Another profile, slot or label is another principal, and
  a rotated profile (a new profile version) is a new principal: a rotation can switch the profile to
  another account, so even a pure secret rotation is treated as a new principal (the safe direction:
  it asks for a re-test, it never hides one). Bindings and
  response dependencies record `principal`; ones recorded earlier with only `session_ref` are resolved
  through the session store when read, and stay `unknown` when it no longer knows the session.
  Experiment conditions may name the principal by that identity or by the session id the cited request
  used.
- Windows: conclusions, inconclusive experiments, next steps and reopened dismissals are read in
  separate windows, so agent next steps never displace the others; reopened dismissals are counted
  exactly. Whenever a window fills, `required_retests.at_least` is true with the reason.
- New routes: only GET and HEAD routes become runnable suggestions; a state-changing route is listed
  outside authority as "state-changing; ask the operator". A suggestion whose origin is not on the
  Hunt's target host (and not covered by a destination grant) is outside authority (advice; admission
  enforces).
- A re-test supersedes another Hunt's entry only when its response equals the recorded one: status,
  media type, key set and the complete body digest. A changed answer (the regression), a truncated or
  prefix-only body, or a missing digest is recorded beside the earlier entry instead.
- `since=release` resolves to the later of the latest declared release and the latest Scan-detected
  deployment change (`other` names the earlier one); `release:<id>` is exactly that marker. A marker
  cannot be dated in the future or before the target was added. Declaring a release is a person's
  decision: on the open-source engine `shakerscan knowledge release` needs a keypress at a real
  terminal (like `knowledge review`), which is the only check when the engine has no accounts.
- The Hunt briefing gains `continue_after_release`: the release point, counts, required re-test totals
  and the top three ranked items by rule and record id (no text), trimmed first when over the size limit.

## Instruction proposals

- A Hunt without `instruction_changes` suggests guidance with the new `targets.skill.propose`
  capability: the complete proposed text, the revision it read, a title, a reason and the ids of
  the Hunt actions or receipts, findings, candidates or scans on the target's asset that support it. A proposal applies
  nothing and needs no permission. A Hunt files at most 5; a target holds at most 20 Hunt proposals
  waiting for review (operator proposals have their own 20); a newer proposal from the same Hunt
  replaces its earlier pending one. Proposal text may not contain terminal control characters, invisible formatting characters (zero-width, direction marks, tag characters) or line separators; `shakerscan knowledge review` shows any such character inside a reviewed recipe or instruction text as a visible escape.
- Review proposals in your own terminal with `shakerscan knowledge review [target]` (also
  `./scanner.sh knowledge review`). Each pending proposal is shown with its reason, evidence and a
  diff against the current instructions, and decided with one keypress: `y` accepts, `r` rejects,
  `n` leaves it pending, `q` stops. Only a lone key decides; arrow keys, other escape sequences and
  pastes are ignored, and the command refuses to run from a pipe. `--accept ID` and `--reject ID`
  show one proposal and still ask for the key. Accept is offered only when the whole difference was
  shown, and the decision carries the digest of the text that was shown, which the server checks.
- Accepting writes the proposed text through the ordinary revision-checked instruction write, as
  the operator. If the instructions changed after the proposal was made, it is stale and cannot be
  accepted; rebasing it (`b` in the review, or
  `POST /targets/{id}/instruction-proposals/{proposal_id}/rebase`) files the same text against the
  current instructions so the new difference is reviewed first. Recording advisory knowledge does
  not make a proposal stale.
- Operator API: `GET /instruction-proposals`, `GET|POST /targets/{id}/instruction-proposals`, and
  `POST /targets/{id}/instruction-proposals/{proposal_id}/accept|reject|rebase`. Proposals are
  stored in the new `target_instruction_proposals` table, created at startup.
- Pending proposal text never reaches a Hunt's instructions, briefing or planner context.
- Saved-action proposals share the same table (`kind: saved_action`, with the operation, the action
  id and the proposed recipe), list, routes and review command. The reviewed text is the recipe as
  indented JSON with control, invisible formatting and line-separator characters escaped; accepting applies the
  recipe through the ordinary revision-checked saved-action write, as the operator, and binds to the
  digest of the text that was shown. A saved-action proposal is stale whenever the target's saved
  actions changed after it was made. A Hunt may add `reason` and `evidence_refs` to a saved-action
  write; it files at most 5 saved-action proposals, separately from instruction proposals, and a
  newer proposal for the same action replaces its earlier pending one. `GET /instruction-proposals`
  and the per-target list take `kind=instructions|saved_action` and also return
  `unconfirmed_instructions`: targets whose instructions are agent-written and unconfirmed, with
  their text, for `shakerscan knowledge review` to confirm.

## Knowledge review through ShakerScan Enterprise, and who decided

- `shakerscan knowledge allow-changes <target>` lets Hunts edit one target's instructions and saved
  actions directly (`instruction_changes`) after a keypress, at the Hunt permissions' revision it
  showed; `--off` turns it off again. It refuses to run from a pipe, like the review.
- On a connection through ShakerScan Enterprise, accepting a proposal (`y`), confirming
  agent-written instructions (`c`) and `knowledge allow-changes` also ask for your step-up (a TOTP
  code or a USB/NFC security key; `--account`, `--method`) for that one decision: the target, the
  proposal, the digest of the text that was shown and the revision. The gateway applies the
  decision after the proof; the connection's token alone cannot. This uses the terminal approval
  protocol's new `knowledge_decision` purpose (docs/hunt-permission-requests.md) and needs a
  gateway that serves it; an older gateway is named and nothing is decided. On an open-source
  engine the keypress stays the only check, as before.
- The engine records the person a trusted gateway names (`SHAKERSCAN_GATEWAY_IDENTITY_KEY`,
  `X-ShakerScan-Operator` with an HMAC assertion; `api/gateway_identity.py`) as `proposed_by`,
  `decided_by`, `recorded_by` and a discovery's `requested_by`. Without the key nothing changes.
  The two headers are removed from every request before routing, with or without a key, and the
  key is taken out of the API's process environment at startup so no child process inherits it.
  Names are UTF-8, percent-encoded in the header.
- The knowledge commands ask the server whether it is an Enterprise gateway
  (`GET /_enterprise/healthz`) instead of inferring it from the connection's token, and report a
  decision that got no answer as "outcome unknown" (check before deciding again).
- The protocol's decision also covers dismissing and reopening a finding and retracting
  interpretations (`dismiss`, `reopen`, `retract`, `retract_hunt`), for the terminal commands that
  make those decisions.
- Rolling back: an earlier engine ignores the key and the headers.

## Hunt briefing

- Every Hunt start response, `GET /hunts/{id}` and the summary query now carry a bounded `briefing`
  (`hunt-briefing/v1`, about 24 KB at most): the operator instructions as snapshotted at start
  (whole, or their headings and a leading part with `more_available` and where to read the rest),
  the objective, an effective authority summary (scope, permissions, target delegation, approval
  requirements, budget limits and use), knowledge counts by kind, the number of pending instruction
  proposals, and unresolved work (open candidates; authorization investigations on the asset that are
  proposed but not run, awaiting execution, inconclusive, deferred or needing review, counted from the
  same projection the authorization workflow uses; actions in progress or awaiting permission).
  Anything shortened is listed in `briefing.trimmed`. Instructions a Hunt wrote under delegated
  permission are marked `operator_reviewed: false`.
- Agent-written, unconfirmed instructions appear in the briefing only under their own
  `unconfirmed_instructions` section (heading "Agent-written, unconfirmed", whole up to about 4 KB,
  otherwise a leading part), never in `instructions`; the context pack carries them in
  `target_skill.unconfirmed`. Hunts started before the upgrade are read the same way.
- Saved target actions in the Hunt context carry `trust`: `operator`, `operator_delegated` (saved by
  a Hunt under `instruction_changes`) or `agent_unconfirmed`; only operator and operator-delegated
  recipes are operator guidance, and none grants authority. `GET /targets/{id}/actions` and the
  target page label each saved action the same way. A recipe or instruction text written under
  `instruction_changes` keeps that label after the operator turns the permission off; turning it
  off stops further changes, and an operator save or delete is how earlier ones are withdrawn.
- A device Hunt can record investigation candidates through `POST /hunts/{id}/candidates` (it
  answered 500 before).
- The briefing's unresolved work counts authorization investigations on the asset from the records
  the authorization workflow keeps (`authorization_investigations`: proposed but not run, awaiting
  execution, inconclusive, deferred, settled, needing review), actions awaiting permission
  (`awaiting_permission_actions`), and caps the open-candidate count with an `at_least` flag. It
  replaces `inconclusive_experiments`, which counted records the workflow never writes.
- The compact MCP view of a Hunt, which leaves out the context pack, always keeps the briefing. The
  Hunt skill and MCP tool descriptions tell agents to read it first and to treat its operator
  instructions as guidance, never as authority.

## Scan time limit and cancellation

- **The Scan's `max_duration_seconds` is enforced by the worker.** Before this release no part of
  the V2 action path read it. An overlong Scan ran until the stale-scan sweep found it at the limit
  plus the larger of 5 minutes and 50 % (a 900 s Scan at about 23 minutes) and marked it `failed`
  with no findings, because a V2 worker writes no checkpoint for the sweep to recover. Now:
  - Work stops at the Scan's start plus `max_duration_seconds`, less a reserve for the report (5 % of
    the limit, at least 15 s and at most 120 s, never more than a quarter of the limit).
  - An action still running then is stopped through the same signal its adapter already checks for
    an authorization stop. What it observed is kept and it settles `partial` with reason
    `scan_time_limit`. One that has not stopped 15 s later is cancelled and settles `failed` with
    that reason and its full reservation.
  - An action that has not started settles `timed_out` with reason `scan_time_limit` and nothing
    charged. No further continuation round is compiled; a round refused this way is reported as a
    time-limit stop too (`time_limit_stop.continuation_rounds_not_run`).
  - The report is still finalized. The Scan ends `completed` with every finding confirmed before the
    stop; its coverage is `partial` with reason `scan_time_limit` (a worse status, such as `failed`
    when a required action failed, is kept), `scan_metadata.partial` is true, the grade is marked
    unreliable, and `scan_metadata.time_limit_stop` lists the stopped and the not-started actions.
  - A shard stops at whichever ends first: its parent Scan's limit from the parent's start, or its
    own limit from its own start.
  - A fleet node (broker) keeps the same limit, measured from when it starts the Scan, because it
    has no database to read the Scan's start from. Rounds the control plane compiles after the
    limit settle at once, without traffic, until the finalizer runs.
  - The stale-scan sweep is unchanged and remains the backstop for a worker that stops responding.
    A worker that is handed the Scan's job again resets its start, so the limit then runs from
    that delivery.
- **A cancelled Scan keeps the findings of its settled actions.** Cancellation still stops execution:
  no action starts after it, and the running action is stopped. The worker then finalizes the settled
  receipts with the same report builder, which sends no traffic. When the cancelled round had no
  finalizer planned, the finalize-only revision the Scan would have run is compiled for the report
  and not stored, because a cancelled Scan's plan is frozen. The Scan stays `cancelled`; its result
  has coverage `cancelled`, `scan_metadata.cancelled: true`, and the finalization action recorded as
  `cancelled` (`canonical_action_execution.finalized_after_cancellation: true`), and the confirmed
  findings are saved. A report built over a compiled finalize-only revision says
  `canonical_action_execution.plan_revision_stored: false`: that revision is not among the Scan's
  stored revisions. Before, a cancelled Scan saved no findings.
  - The action that was running is stopped. If its adapter returns what it had observed, it settles
    `cancelled` and those observations count; if the cancellation had already ended its lease, it
    settles `failed` and contributes nothing.
  - Not covered yet: a cancellation that arrives while the report itself is being finalized keeps
    no findings; a cancelled parallel Scan's shards keep none; a Scan cancelled on a fleet node
    (broker) still fails without findings; an ASM exploit batch records a cancellation as an
    error, as before.
- The new reason `scan_time_limit` is labelled in the API explanation, the Scan activity log and the
  UI coverage reasons.
- The known limitation that an AI target scan stopped for authorization does not keep its findings
  is unchanged: AI scans run as one piece of work, not as Scan actions.

## GraphQL

- **GraphQL endpoints are now found, and introspection and IDEs reported, in `sensitive_exposure`.**
  Before this release no V2 capability sent a GraphQL request; a Scan of DVGA reported no GraphQL
  finding. The read-only exposure batch now also sends, once per Scan:
  - `GET <path>?query=query{__schema{queryType{name fields(includeDeprecated:true){name}}types{name}}}`
    to `/graphql`,
    `/api/graphql`, `/v1/graphql`, `/graphql/v1` and `/gql`, and to every discovered route whose last
    path segment is `graphql` or `gql`. A GET carries only a query operation, and this document
    selects only the `__schema` meta field. The request asks for JSON and sets
    `Apollo-Require-Preflight` so servers with Apollo's CSRF prevention answer it.
  - `GET /graphiql`, `/graphql/console` and `/playground` with `Accept: text/html`.
  - A finding needs a 200 answer whose `__schema.queryType.name` is a GraphQL name that also appears
    in `__schema.types` (**GraphQL introspection enabled**, low, CWE-200), or a page that loads the
    GraphiQL or GraphQL Playground bundle and renders it (**GraphQL IDE served publicly**, low,
    CWE-200). Introspection is proven only by the answer to that request (a static schema file is
    not), and an IDE only at an IDE path (a documentation page showing the setup code is not). Both
    are reported on the endpoint path and pass the existing soft-404 control: a host that answers
    every path with the same body proves nothing.
  - Contracts `graphql_introspection_exposure/v1` and `graphql_ide_exposure/v1`; parser
    `exposure-probe/v4`. The first exposure slice holds 8 more requests.
- **New active family `graphql` (`graphql.verify_batch`).** It is not in a preset; select it with
  `include_families`. It needs active testing and sends GETs only, never a state-changing request.
  For each conventional location (first slice) and each discovered GraphQL route, at most 6 GETs:
  - `query{__typename}`, then a document no schema defines (`query{__typenamezq}`), which a GraphQL
    server must reject. Only an endpoint that answers the first and rejects the second is checked
    further.
  - The introspection document. When it answers with the complete list of root fields (deprecated
    ones included), a root field name is misspelt into a name the root type does not have.
    Otherwise (introspection off, or an incomplete list) the query asks for eight names reserved by
    GraphQL for introspection, each close to a common root field (`__user`, `__me`, `__search`,
    ...); no schema may define such a field. Either way validation rejects the query before any
    resolver runs. **GraphQL field suggestions enabled** (low, CWE-200) needs the error to name, as
    a suggestion, a real root field (with introspection) or an ordinary field name (without).
  - 100 aliases of `__typename` in one query: **GraphQL alias limit absent** (low, CWE-770) needs
    all 100 answered with no error.
  - `__typename` repeated 100 times: **GraphQL duplicate field limit absent** (low, CWE-770) needs
    an answer with no error.
  - Contracts `graphql_field_suggestions/v1`, `graphql_alias_limit_absent/v1` and
    `graphql_duplicate_field_limit_absent/v1`. Per-endpoint checkpoints let a resumed batch skip
    finished endpoints. The conventional locations are checked once, by the first slice, even when
    a later slice discovered one of them.
- Not covered by the Scan: array batching (it needs a POST), query depth (a nested query can be
  expensive), and anything that selects or mutates an application field (injection through
  GraphQL arguments, mutations).
- ADR 0001 lists the fixed GraphQL reads among the passive exposure checks.

## Response text shown to Hunt and agents

Every capability that returns target response text to a planner or agent masks the whole text
before cutting it. This covers HTTP requests and experiments, `artifact.inspect`,
`javascript.analyze`, device HTTP, interactive endpoint tests and authorization replays. A value
split by a cut is withheld whole. A ranged response withholds its body; use `artifact.inspect` to
read a window together with what surrounds it.

Known limit: a URL password is withheld wherever it is written, including one with an unencoded
`#`, `?` or quote (`postgres://app:Pa#ss?w0rd@db`). There is one exception. A password that
contains the URL's own opening quote followed by `,` `:` `]` `}` or `)` is shown, for example
`'ftp://u:Pq>+_2]|4':'*<Zk@h'` or `"http://u:Pq",Zk@h"`. Text like that cannot be told apart from
two separate strings, such as a URL with a port followed by an email address in compact JSON, and
masking it would rewrite that ordinary JSON. Passwords of this shape are rare: they need an
unencoded quote immediately followed by JSON or JS punctuation.

## Rolling back to 2.8.x after these changes

- A queued or scheduled Scan whose policy selects the `graphql` family fails 2.8.x validation as an
  unknown family. Remove the family from schedules before rolling back.
- A Scan in flight whose plan holds `graphql.verify_batch` actions or `scan_time_limit` receipts
  cannot be resumed by a 2.8.x worker; let it finish or cancel it first.
- GraphQL findings written by 2.9.0 keep their rows, but 2.8.x does not know their proof
  contracts (`graphql_*`), so they read as not deterministically proven there.
