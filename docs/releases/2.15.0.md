# ShakerScan 2.15.0

**Status:** integration candidate on `release/2.15.0`; it follows 2.14.1.
The client for this release is `shakerscan` 0.15.0 (`shakerscan mcp install|uninstall|status`,
`shakerscan catalog`, `shakerscan scan status|coverage|result|list|cancel`; it vendors the MCP
adapter, so it also carries the new grouped MCP tools).

2.15.0 makes a Hunt drive its own coverage: the engine maps a web target, sweeps every endpoint and
input with the server's own verifiers, tries default-credentials on the logins it finds, and holds
a finish while coverage is open and time and budget remain. It adds a `server_injection` Scan
family (off unless a Scan names it), lets an agent discover and drive Scans, findings, retests,
schedules and exports over MCP without ever sending a person's decision, and removes false
positives found by default external posture Scans on internet hosts.

**Read before upgrading: Scans and Hunts may send more requests.**

- A Scan's state-changing request ceiling now equals its request ceiling: fast 500 to 5,000,
  balanced 2,000 to 20,000, thorough 6,000 to 60,000, deep 15,000 to 150,000; the advanced-limit
  maximum goes from 100,000 to 1,000,000. Only a Scan allowed to send state-changing requests is
  affected. The request ceilings themselves are unchanged.
- A Hunt's ceilings rise for authority a person already grants separately: state-changing requests
  4/20/80 become 200/1,000/5,000 (fast/balanced/thorough), TCP ports 100/1,200/10,000 become
  2,000/20,000/200,000, and UDP ports, device fragility points and out-of-band interactions rise
  with them. The policy switches and approvals that turn these on are unchanged.
- An active web Hunt now runs discovery and a sweep of its own (see [Hunt](#hunt)), and tries a
  small list of default-credentials on the logins it finds. `SHAKERSCAN_HUNT_DEFAULT_CREDENTIALS=false`
  in `.env` turns the default-credential check off for the install.
- An installed signed advisory bundle generated before 2026-11-27 is refused in favour of the
  bundled snapshot, which this release refreshes.

**Upgrade.** Upgrade in place from 2.14.1 (or any 2.14 release). The first start:

- adds the table `hunt_default_credential_attempts` (each attempt's Hunt, action, a digest of the
  login, its host, the built-in pair reference and the verdict; no password is stored);
- recomputes the root of every target whose stored root spans registrants, now including five
  per-customer cloud hosting namespaces the Public Suffix List does not carry yet. A target the
  Certificate Transparency monitor added under such a root, whose new root is not the root of a
  target a person or a Scan added, is archived, never deleted: inactive, Continuous ASM off,
  schedules paused, `metadata_json.archived_reason: ct_monitor_other_registrant`. History is kept
  and a person can restore it;
- moves the target exposure classifier to version 2, so cached exposure classes are computed
  again as they are read.

Nothing else existing is rewritten. A rollback restores the database dump taken before the upgrade,
as for every release (`docs/upgrade-and-rollback.md`).

**Breaking changes.**

- Finishing a web Hunt while coverage is open and wall time and HTTP budget remain answers 409 with
  what is open. `POST /hunts/{id}/finish` with `force: true` and a `force_reason` finishes anyway;
  the debrief records the coverage at finish and the reason. A budget-exhausted Hunt, one whose
  wall time is nearly spent, and a failed coverage read never hold a finish.
- `shakerscan api` run by an agent (`SHAKERSCAN_AGENT_NAME` set), or without a terminal on both
  input and output, refuses a person's decision with exit 3 and sends nothing (a person's own
  script sets `SHAKERSCAN_PERSON_SCRIPT=1`); the message names the command the person runs. See
  [Agents and MCP](#agents-and-mcp).

## Hunt

- **The engine maps the target.** At the start of a web or API Hunt with testing authority, the
  engine runs, as the Hunt's own recorded capability calls (same scope, destination checks,
  pacing, budget and approvals as a planner's calls): an anonymous crawl, content discovery, a
  signed-in crawl per selected principal when the Hunt may use them, the passive template pack
  when allowed, and one read-only GET per conventional API description, hint file, GraphQL
  endpoint and well-known path of common self-hosted products. Answers are judged against a
  negative control. A step the Hunt may not run is skipped and named.
- **The engine sweeps what is mapped.** It reads every mapped endpoint, records forms, robots.txt
  and sitemap routes and routes named in inline scripts, learns inputs from 400 and 422 answers,
  and runs `request.verify` on every input, signed-in checks first. It follows the Hunt until the
  planner finishes and tests the routes and inputs the planner's own requests reveal. A recognised
  product's own templates run from the pinned bundle (read-only always; state-changing ones only
  with write permission). GraphQL query arguments are read by introspection and proved as
  injection inputs; mutations and fields named for deleting or resetting are never sent.
- **The engine never requests a route whose path names a destructive operation** (reset, drop,
  delete, logout, shutdown and similar), whatever the method. A sweep call that would is skipped and
  counted.
- **Open coverage.** `GET /hunts/{hunt_id}/coverage` and query kind `coverage` list each known
  endpoint with the test classes nothing in the Hunt has run on it and the check that closes each.
  A compact `open_coverage` rides on every capability answer and on the checkpoint. It is a
  worklist, never a finding.
- **New capability `request.verify`** proves one vulnerability class on one exact request, with a
  repeat using fresh random values and a negative control that must stay silent. Checks: SQL, NoSQL,
  LDAP, template and command injection, path traversal, XXE, in-band SSRF, open redirect, CRLF,
  host header, CORS, security headers, directory listing, GraphQL, file upload, rate limit, CSRF,
  JWT, anonymous management APIs of self-hosted products, exposures, and mass assignment at sign-up.
  The rate limit check reports a run of unthrottled wrong passwords as an observation, never a
  finding: twelve attempts do not show that no limit or lockout exists.
  It needs active testing; writes and uploads need state-changing permission.
- **`candidate.verify` proves injection candidates** (`ssti`, `path_traversal`,
  `command_injection`, `ssrf`, `sqli`, `nosqli`, `injection`) with the Scan's own differential
  proofs, and default-credential candidates (below).
- **Default credentials.** On logins a Hunt finds, a bounded check of public default and common
  pairs: active testing only, a login on the Hunt's own host, at most 20 attempts per login and 12
  logins per Hunt, 2 s between attempts, an hourly limit across Hunts, and a stop on a lockout or
  rate limit answer. A form login is posted from its own page: the attempt reads the page first
  (one extra request) and sends its hidden anti-CSRF field and submit button. A route that answers
  401 with a Basic challenge gets the same pairs as an HTTP Basic header. The proof sends the
  accepted pair again plus a control with the same user name and a random password; it is verified
  only when the pair signs in and the control is refused. A verified candidate becomes a CWE-1392
  finding.
- **Roles.** An active Hunt selects the target's registered principals; the briefing names their
  roles and which proof fits which comparison. `authz.verify` gains mode `planted_object` (another
  user reads a private field a principal planted on a shared collection) and accepts logins the
  Hunt captured itself (`primary_bindings`, `secondary_bindings`) only when the server's records
  show two different accounts.
- **Accounts on the target only with consent.** The engine signs up accounts (at most two) only
  with `policy.allow_account_creation` on `POST /hunts` (off by default) or after a person grants
  the `account-creation` permission request it raises when it finds a sign-up route.
  `request.verify` mass assignment, which signs up three accounts, also needs the flag.
- **Start a Hunt from findings.** `POST /hunts` accepts `seed_finding_ids` (at most 20 findings on
  the Hunt's target). The briefing opens with them, target text inside `untrusted_data`, never raw
  evidence or credentials. An id the Hunt cannot read answers 422 `seed_finding_unavailable`. The
  finding page's Hunt button and `shakerscan hunt start --seed-finding` use it.
- **One request rate per target origin.** Everything a Hunt sends to an origin (HTTP calls,
  verifier replays, workflow steps and the external tools through the pinned proxy) shares one
  rate, the fastest rate any Hunt tool is held to (10 requests a second). Senders wait; nothing is
  dropped. Agent-tool calls start without queue delay (the short lane is probed every 100 ms).
- **A target that asks to wait is waited for, and one that stops answering is held.** A 429 or a
  503 with `Retry-After`, a ban (the same sender's same request refused twice after it was served), five unanswered
  requests in a row, and a 423 on one method and path (refused for 15 minutes) hold that origin
  for the Hunt's HTTP calls and for every external scanner relayed through the pinned proxy,
  in Scans as well.
- **`http.request` refuses a path that resolves outside the bound origin.** A request path or
  `form_page` whose first segment names a scheme (`/http://...`) is refused with a `scope:` error
  before anything is sent, as the browser capability already did. A security advisory covers
  earlier releases.
- **Planners see more.** 16,000 characters of an `http.request` answer (was 2,000), the whole
  `artifact.inspect` window asked for, JavaScript bundles up to 4 MiB. Crawls hold their whole
  reviewed time box. Receipts carry `action_id` and a failed call's short, redacted error;
  `artifact.inspect` says when it did not search a body and why.

## Scans

- **New family `server_injection`** (active testing, risk high, in no preset; it runs only when a
  Scan names it). One differential verifier proves server-side template injection, path traversal,
  command injection (POSIX shell and `cmd.exe`), XXE, and in-band request forgery to the
  application's own loopback address. A class is reported only when a probe hits twice with
  different random values and a control without the syntax stays silent. Command probes only print
  or sleep one second; path traversal goes only through reading requests; XXE uses local entities
  only. A proven finding is retested by the check that proved it.
- **SQL injection proof:** a numeric boolean pair and a delay screen of one request for MySQL,
  PostgreSQL and SQL Server before the timing confirmation; no OR payload outside the existing
  sign-in bypass pair, and never on the credential profile's sign-in endpoint.
- **Open redirect:** a parameter that answered the plain destination gets three destinations that
  pass a careless allow-list. **JWT** (signed-in `authz_surface`, bearer profile): an altered
  signature, `alg: none`, and a short list of well-known HMAC secrets, never changing a claim; it
  runs only when the bearer is what authenticates the route.
- Four more secret-bearing deployment files are probed on `thorough` and `deep`. The reflected XSS
  tool is skipped where input reflects only into JSON. An OpenAPI document with an empty server URL
  resolves to its own directory.
- **A remote fleet worker honours `options.traffic_attribution: false`.** This closes the known
  limit of 2.14.1.

## External posture and discovery

- A documentation placeholder in an env block (`NAME=<token> command`, `${VAR}`, `your-...`,
  `xxxx`) is never a proven secret.
- A CORS grant is proven only on a 2xx answer with content. On a redirect, an empty body or a
  single sign-on interstitial it is a low candidate with `unreadable_reason`.
- Content discovery paths no longer become path-segment SQL injection candidates; routes a crawler,
  browser, spec or replay observed still do.
- crt.sh is retried on 404, 408 and 425 too, with up to four attempts over about 50 s.
- `//.env` and `/.env` are one finding.
- A wildcard-DNS match is dropped only when discovery guessed the name. A name a passive source
  (Certificate Transparency, any subfinder feed) reported, and a `www` name, are kept and marked
  `wildcard_match`, after names with their own DNS answer.
- A host on a public wildcard-DNS service that encodes an address in the name is classed by that
  address: a private, loopback or link-local address is internal.
- The Certificate Transparency monitor takes a name only under the root's registrable domain, and
  never takes its roots from its own targets.
- Archive masking no longer withholds ordinary HTML, CSS and JavaScript (font names, `function`,
  `submit`) as secrets; credentials, tokens and keys are still withheld.
- `GET /targets/{id}` reports `authorized_for_active_testing`, computed as every gate computes it:
  a web app covered by its host's authorization is authorized, an archived target is not. The
  lists use the same rule.

## Agents and MCP

- **An agent never sends a person's decision.** The routes are listed in one place: Hunt permission
  decisions, grant revocations and budget raises, target authorization, Arsenal approvals, data
  deletion, secret reveal, finding dismissals and exceptions, Model Intake approvals, fleet join
  tokens, and AI and automation settings. The agent kit hands the person the command. On an
  install without authentication this is a guard rail, not a security boundary.
- **Catalog.** `shakerscan_catalog` (MCP) and `shakerscan catalog` list the tools, CLI commands,
  REST routes, Hunt capabilities and permission kinds, every person decision and how to request
  it, and whether the install has authentication.
- **Grouped tools,** each behind an `action` argument: `shakerscan_scans`, `shakerscan_finding`,
  `shakerscan_hunts`, `shakerscan_target`, `shakerscan_schedules`, `shakerscan_exports`,
  `shakerscan_asm`, `shakerscan_credentials` (metadata only), `shakerscan_access_control` and
  `shakerscan_devices`. Every write is checked against the person-decision list before it is sent;
  triage records only `needs_review`, `true_positive` and `retest_needed`. Target text comes back
  under `untrusted_data`.
- Every MCP tool and argument is described; `shakerscan_hunt_ssh_exec` is marked destructive.
  `shakerscan_hunt_finish` takes `force` and `force_reason`; `shakerscan_hunt_query` takes
  `kind=coverage`.

## Client 0.15.0

- **`shakerscan mcp install|uninstall|status`** registers the ShakerScan MCP server once in
  OpenCode, Claude Code, Codex, Cursor or VS Code. `--http <address>` reads a deployment's
  discovery document and registers the MCP servers it offers; the token is read from
  `SHAKERSCAN_TOKEN` and never written to the agent's configuration.
- `shakerscan catalog`, `shakerscan scan status|coverage|result|list|cancel`, `evidence export`
  from any host, `hunt start --seed-finding`, and `hunt finish --force-reason`.

## Advisories

- Two optional advisory sources, both off until an operator enables them in Settings ("Advisory
  intelligence sources") or with `PUT /settings/automation` (`intel_curated_briefings`,
  `intel_vendor_declared_ranges`); `GET /settings/automation` reports them under
  `intelligence_sources`. Enabling one fetches nothing; it lets data already in the verified
  snapshot be used. With curated briefings on, a briefed candidate ranks after known-exploited ones
  and opens a Hunt lead; the Services view shows a "Briefed" chip. With vendor-declared ranges on,
  a CVE not yet analysed by NVD can match through the range its publisher declared.
- The bundled advisory snapshot is refreshed from NVD, CISA KEV and EPSS data of 2026-11-27.

## Dependencies and images

- Redis 8.10.3 and, for the fleet gateway, Caddy 2.11.9.
- The Model Intake signer image upgrades `libpam` at build time (CVE-2025-6020).
- paramiko 5.1.0 in the scanner; ml-dtypes 0.7.0 and numpy 2.5.5 in the Model Intake safetensors
  tool (the locks now match their inputs). The Public Suffix List snapshot is refreshed.

## Known limits

- `server_injection` request forgery is in-band only; a blind fetch, a fetch of another internal
  host, and an application that answers its loopback name with another site are not found. XXE and
  the JWT checks were proved on local fixtures, not on a live target.
- `candidate.verify`'s injection proof is a GET with one query parameter as the anonymous client.
- The sweep sends a captured login only to `request.verify`; `sqli.verify` and `xss.verify` still
  take a managed principal. For opaque session cookies, telling two accounts apart relies on the
  account name in the sign-in request.
- A login request that carried a captured page value is not replayed by the default-credential
  proof, except a form posted from its own page.
- Wildcard DNS suppression compares DNS answers only; it sends no HTTP to discovered names.
