## Executive verdict

The nine commits added to `new` after the previous audit materially improve the AI-native migration. They are not cosmetic changes. Canonical Hunt network execution, target-bound approval, TLS inspection, device SSH confirmation, budget reconciliation, legacy Hunt quarantine, and streaming Katana endpoint manifests are now significantly stronger.

The architecture is nevertheless still transitional rather than complete:

- The public product has one Scan, but the monolithic worker/scanner still executes legacy `quick`, `standard`, `deep`, `full`, `aggressive`, and `smart` identities.
- Canonical Hunt is the preferred write path and legacy Hunt writes are quarantined, but device actions still delegate into legacy device execution code.
- Request Collections V2 can import, index, select, and safely replay in Hunt, but deterministic Scan still needs an exact worker-side replay path instead of reducing selected requests to endpoint seeds.
- Streaming Katana output and endpoint manifests now exist in production code, but the exact parent-worker acceptance case—producer emits hundreds of endpoints, hangs, process reaches the deadline, parent recovers the durable manifest, and fan-out completes with partial coverage—still needs an end-to-end test.
- Multi-dimensional budget reservation and reconciliation exist, but stale reservation recovery and a single durable reservation lifecycle shared by Scan and Hunt are not yet fully demonstrated.

The branch should currently be described as an **AI-native V2 migration with several production runtime paths already converted**, not as the completed deletion of the legacy architecture.

## What changed in the latest `new` commits

### 1. Request selector hardening

Commit `e53a5d157dc563da72a66e0fce8fefb78ec74bf1` rejects catastrophic or heavily backtracking selector expressions before they run across large collection indexes. API and Hunt selection now use the selector's prevalidated matcher instead of recompiling arbitrary expressions.

**Assessment:** implemented and worth retaining.

### 2. Executable capability filtering and real TLS inspection

Commit `4a8db5aee2cf97165222b129d2bb2917eb18f0a7` narrows Hunt capability exposure by target kind, requires target-bound approval for credential use, adds a pinned SNI-preserving TLS handshake, and stops representing TLS inspection as an HTTP `HEAD` request.

**Assessment:** closes an important prior audit finding.

### 3. Canonical Nmap, Naabu, and Subfinder execution

Commit `fe2ba025012efb009b6c5d8dd03096f83a147a00` routes canonical network capabilities through typed adapters. The API prepares a target binding and policy, the worker independently rebuilds server-owned argv, and budget reconciliation uses measured or conservatively retained usage.

**Assessment:** canonical network execution is substantially implemented. Legacy `run_tool` remains for compatibility and other tool families still need to converge on the same executor lifecycle.

### 4. Explicit network-discovery policy and authentication normalization

Commit `9fa288df1fbdf38942e552d20aab15c8021a8db9` requires active testing and a target-bound approval receipt for network discovery. It also preserves bounded authentication fields for both principals and treats `exhaustive` as a compatibility alias for `thorough`.

**Assessment:** implemented. These contracts must remain authoritative during the Scan refactor.

### 5. Streaming endpoint manifests

Commit `5d40aaf0f47d4d24607f4fbb051f733f36006b03` converts the live Katana path to streaming execution, applies soft/flush/hard deadlines, distinguishes cancellation from timeout, and builds an endpoint manifest while output arrives.

**Assessment:** major improvement. Remaining work is durable periodic sink integration and worker/parent recovery acceptance under a real process deadline.

### 6. Canonical device SSH confirmation

Commit `6089ebe555df7ba20c0ad0904b777fd616355435` restores device SSH through the canonical Hunt surface with credential references, immutable plan digest, exact command confirmation, expiry, and fragility accounting.

**Assessment:** strong safety model. Execution still passes through legacy device-agent machinery, so engine unification is incomplete.

### 7. Legacy Hunt quarantine

Commit `e93c6b08561737d52b2b99b7b5edc3ecb323bbed` blocks new legacy web/device Hunt writes with `410 Gone` by default while keeping history and emergency cancellation readable. An explicit temporary environment override remains.

**Assessment:** correct migration control. The next step is deleting the duplicate planner/session storage after compatibility retention requirements are met.

### 8. Documentation alignment

Commit `d09d5f5d05dcb1e3a329641a730ea338142ef089` updates documentation and tests to describe the canonical Hunt path honestly.

**Assessment:** implemented.

### 9. JWT probe correction

Commit `ccc4b8829d4edc3871afaf5128c974da814149cc` fixes direct algorithm-confusion JWT probe construction. It is useful security-scanner work but is not itself part of the Scan/Hunt architecture migration.

## Remaining P0 work

### P0.1 — Make the worker consume `ScanExecutionPlan`

Current canonical requests still expose `execution_scan_type` to the old worker adapter. The next migration must:

1. Persist the canonical plan as the execution authority.
2. Queue only the plan, target binding, selected inputs, and authorization references for V2 requests.
3. Teach the worker to derive deterministic stages from policy and budget rather than a mode name.
4. Keep legacy input translation at the API boundary only.
5. Remove `execution_scan_type` after all V2 callers and workers use the plan.
6. Add a test that fails if a canonical V2 job payload contains any legacy scan identity.

### P0.2 — Wire exact request replay into deterministic Scan

The new replay plan must be connected as follows:

1. API stores only collection IDs and selectors in the queued job.
2. Worker decrypts and resolves the selected collection immediately before execution.
3. Worker creates `ReplayPlan` using the scan's target binding and authorization.
4. Each request runs through the existing pinned HTTP transport/credential boundary.
5. Redirects remain disabled unless a bounded same-origin policy explicitly enables them.
6. Actual request usage is reconciled into the shared ledger.
7. Each replay creates a typed receipt referencing request ID, plan digest, status, timing, response evidence, and partial/error state.
8. State-changing requests are rejected without all three authorization conditions.
9. Collection requests contribute their full method/body schema to endpoint identity and coverage.

Acceptance must prove that a POST body, content type, query parameters, managed auth, and exact request ID survive from encrypted collection to worker execution.

### P0.3 — Complete durable discovery recovery

The required acceptance scenario is:

1. Katana emits 347 valid endpoints.
2. Katana hangs.
3. The soft deadline stops new discovery work.
4. Complete lines are parsed and atomically flushed to a durable endpoint manifest.
5. The remaining process is terminated at the hard deadline if needed.
6. The worker or parent reloads the durable manifest even if the scanner process exits.
7. Fan-out continues with the 347 recovered endpoints plus the seed.
8. Final run status is completed with partial coverage and explicit producer timeout metadata.
9. Explicit user cancellation does not fan out.

Unit tests for streaming and manifests are not sufficient substitutes for this worker-level acceptance.

### P0.4 — Finish one durable budget lifecycle

Every executable Scan and Hunt capability should share:

- durable reservation ID
- requested, reserved, running, committed/released/failed states
- typed dimensions
- actual-use reconciliation
- stale reservation recovery after worker/process loss
- sanitized server-generated execution details
- receipt hash and artifact references

The datastore transition must be transactional. A sweeper should reconcile or conservatively commit stale reservations based on durable execution receipts; it must never blindly refund traffic that may have executed.

### P0.5 — Remove device execution delegation

Canonical device Hunt currently validates policy and budgets correctly but still delegates execution into old device-agent functions. Move those functions behind the same canonical capability executor used by web/API/network targets. Device differences should remain policy, placement, fragility accounting, credential adapter, and protocol adapter—not a second Hunt engine.

### P0.6 — Delete legacy Scan/Hunt identities after migration gates pass

Delete only after compatibility telemetry and migration retention requirements are satisfied:

- six-mode scanner branching
- old Smart/Full Coverage product identity
- legacy web Hunt planner/session creation
- legacy Device Hunt planner/session creation
- duplicate tool registry paths
- duplicate budget accounting paths
- device-only request collection ownership

Historical records may remain readable through compatibility views without allowing new legacy execution.

## Test and CI truth

Focused local tests were exercised for the newly introduced canonical Scan plan and exact replay primitive. The repository connection reported no status checks or workflow runs for the V2 commits at the time of this audit. Therefore:

- the focused module behavior is tested;
- the complete repository suite, image build, database integration, and live worker acceptance are not yet certified for these commits;
- no claim of release readiness should be made until branch CI and the required real-stack gates run.
