## Verdict

**Listed defects remediated and verification gates passing.** The original findings were real; the
follow-up fixes pass the durable gates recorded in `audit-evidence-2026-07.md`. Product surfaces not
exercised by this audit remain explicitly unqualified rather than being treated as implicitly safe.

The product's core promises hold up under real exercise: 28 UI routes render in a real browser with
**zero console errors and zero failed API calls**; input validation on `/scans` and `/workers` is
robust (malformed/typed/enum/bounds all rejected with 4xx); SQL injection in filters is not
exploitable (parameterized queries hold); destructive UI actions are confirmation-gated; the AI Gate
production gate, the schedule retention-sweep block, and the worker-count bounds are all enforced
**server-side**, not merely in agent instructions. The `docs/functionality-reference.md` capability
table matches the code's 234 routes exactly (0 drift).

The defects below were independently reproduced. The most serious was a browser-reachable
cross-origin data/command vector; unrestricted target reachability remains an intentional operator
capability, with the browser command boundary fixed instead of censoring destinations.

## Findings

### P0-1 — Wildcard-credentialed CORS on an unauthenticated API → any website can read data and drive the scanner from the operator's browser

- **Surface:** REST API (all endpoints). **Component:** `api/api.py` CORS middleware.
- **Root cause:** `allow_origins=["*"]` combined with `allow_credentials=True`. Starlette resolves
  that pair by **reflecting the caller's `Origin`** and returning
  `Access-Control-Allow-Credentials: true`, so any page the operator visits can make cross-origin
  calls and read the responses. The API has no auth of its own.
- **Reproduced (real browser):** a page served from `http://127.0.0.1:9999` (a foreign origin), using
  only page JavaScript against `http://localhost:8080`, succeeded at **4/4**: read `/findings`
  (17 KB exfiltrated), read `/settings/ai`, read `/targets` (262 KB), and **`POST /scans`**
  (launched a scan). Evidence: `audit-results/harness/cors_poc.mjs`,
  `audit-results/screenshots/P0__cors_exfiltration_poc.png`,
  `audit-results/api-responses/cors_poc_result.json`.
- **Header proof:** `curl -H "Origin: https://totally-evil.example.com" …/findings` →
  `access-control-allow-origin: https://totally-evil.example.com` + `allow-credentials: true`.
- **Why P0:** major security-boundary bypass (browser-driven read of all findings/targets/settings +
  scan control). Note the default `127.0.0.1` bind means no *network* exposure — but this vector is
  purely browser-driven and does not need network exposure.
- **Fix applied:** replaced the wildcard with an explicit origin allowlist (the local UI origins by
  default, extendable via `SHAKERSCAN_CORS_ALLOW_ORIGINS` / `SHAKERSCAN_CORS_ALLOW_ORIGIN_REGEX` for
  remote deployments) and set `allow_credentials=False`. The UI issues **no** credentialed requests
  (verified), so this is transparent to it while foreign origins can no longer read responses.
  Because CORS alone does not prevent a browser from sending a simple cross-origin mutation, an
  origin guard now rejects unapproved unsafe-method requests before endpoint code executes. CLI and
  agent requests without `Origin` remain accepted. Operators can explicitly allow any origin with
  `SHAKERSCAN_CORS_ALLOW_ORIGINS=*` when that is their intended deployment policy.

### P1-1 — Unrestricted destinations amplified the browser command vector (accepted capability)

- **Surface:** `POST /scans`, `POST /targets`. **Component:** `normalize_target_url` (`api/api.py`).
- **Observation:** target normalization validates the URL scheme (http/https) but intentionally does
  not censor link-local, cloud-metadata, loopback, private, or internal destinations. Metadata
  submissions were **accepted (200)** and
  only `failed` later on network reachability, not on policy. `http://postgres:5432` (an internal
  service) **completed and produced 3 findings**. Evidence: `audit-results/api-responses/negative_results.tsv`.
- **Why it mattered:** P0-1 allowed a hostile browser origin to command that reachability. The scanner
  is also intentionally capable of reaching destinations a normal browser cannot.
- **Resolution/design decision:** preserve unrestricted operator-directed HTTP/HTTPS targets. Users may
  scan local labs, private networks, Docker services, link-local services, and metadata endpoints
  without a hidden environment switch. The remediation is at the command boundary: unsafe requests
  carrying an unapproved browser `Origin` are rejected before endpoint execution, while CLI/agent
  requests without `Origin` and explicitly configured UI origins retain full capability. Operators
  remain responsible for deployment network policy and authorization.

### P2-1 — Negative `limit` / `offset` reach Postgres → HTTP 500

- **Surface:** `GET /findings` and ~12 other list endpoints. **Component:** `Query` params.
- **Root cause:** `limit: int = Query(N, le=X)` and `offset: int = 0` declare an upper bound but no
  lower bound, so `?limit=-5` / `?offset=-10` pass into SQL and raise
  `asyncpg.InvalidRowCountInLimitClauseError` / `…OffsetClauseError` → 500. (Over-max and non-numeric
  are correctly 422 already.) The client body is a clean "Internal Server Error" — **no stack trace
  leaks to the caller** — but normal user input yielding a 500 is a defect.
- **Fix applied:** added `ge=1` to every bounded `limit` and `ge=0` to every `offset` across the
  affected list endpoints, so out-of-range values now return 422.

### P2-2 — `POST /findings/bulk` rejects its own documented request body (422)

- **Surface:** REST API. **Component:** `bulk_update_findings` (`api/api.py`); AGENTS.md example.
- **Root cause:** the handler signature was `bulk_update_findings(finding_ids: list[str], status: str,
  notes: Optional[str] = None)` with no request model. Under FastAPI, a scalar `str` and a
  scalar-sequence `list[str]` bind to the **query string**, so the JSON body AGENTS.md documents
  (`{"finding_ids":[...],"status":"...","notes":"..."}`) returns **422**. Confirmed live and against
  `/openapi.json` (`status`/`notes` shown as query params). No UI caller, no test — nothing caught it.
- **Fix applied:** introduced a bounded `BulkFindingUpdateRequest` Pydantic body model so the
  documented JSON works as written. Duplicate IDs are de-duplicated, and the response reports rows
  actually changed plus requested, unique-requested, and not-found counts.

### P2-3 — UI build badge shows a stale commit

- **Surface:** UI sidebar vs `/health`. **Component:** `ui/src/components/Sidebar.tsx`;
  `docker-compose.yml` UI build arg.
- **Root cause:** the sidebar renders `NEXT_PUBLIC_APP_VERSION`, which is **baked into the UI image at
  build time**. The API deliberately derives its label from the live checkout HEAD
  (`current_scanner_version()`, whose docstring says to reflect volume-mounted code, "not the commit
  baked into SCANNER_VERSION when the image was built"). Result: UI showed `Build 99ee3a0` while API,
  workers, and `/health` correctly reported `118aa6a`. For a product whose benchmarking rule is
  "never measure on a build-stale fleet", a wrong build badge is actively misleading.
- **Fix applied:** the sidebar now shows the baked UI build, live API build, and worker-fleet build
  separately and flags skew instead of replacing one component's identity with another. Runtime
  requests are shared between desktop and mobile sidebar renderings.

### P2-4 — AI Operations Router dropped documented DAST scan intents

- **Surface:** `POST /ai/ops/route`. **Component:** `_build_ai_ops_router_plan` (`api/api.py`).
- **Root cause:** the deterministic router handled Full Coverage and selected ASM phrases but did not
  implement the product model's ordinary `scan` or exact quick/standard/deep/full/aggressive/smart
  DAST vocabulary. A dry run for “Run a quick scan” returned `intent: unknown`.
- **Fix applied:** unqualified scans now plan Quick DAST, all six named scan types preserve their exact
  type, `deep scan` stays distinct from Deep Hunt, and confirmed execution uses the same `/scans`
  path. Every queued scan remains dry-run by default and requires execution plus authorization
  confirmation. Regression coverage includes a metadata target to ensure routing does not censor the
  operator's destination.

### P3-1 — `POST /targets/dedupe` ignores a JSON-body `dry_run` (documented body param is query-only)

- **Root cause:** `dry_run` is a **query** parameter defaulting to `True`. A caller sending
  `{"dry_run": false}` in the JSON body has it **ignored** — the request fail-safes to a dry run
  (verified live: response echoed `"dry_run": true`, target count unchanged). This is the **opposite**
  of a destructive-by-default bug (it is safe-by-default), but the body param is silently a no-op, so
  an intended execute via body silently does nothing. **Documentation fix**: callers must use
  `?dry_run=false`. Left code as-is (fail-safe); documented the correct invocation.

### P3-2 — Documentation / agent-instruction drift (backend enforces; these are doc-completeness gaps)

Verified that the **backend enforces** the corresponding gates, so these are documentation defects,
not safety bypasses:
- `AGENTS.md` prose "the `/asm/improve` endpoint" omits the real prefix `POST /targets/{id}/asm/improve`. **Fixed.**
- `.claude/commands/subdomains.md` step 4 says "Poll for completion", contradicting AGENTS.md's global
  "report that discovery was started — don't wait". **Fixed** to match the global rule.
- `.claude/commands/ai-gate.md` never mentions `confirm_production`, though AGENTS.md and the **server**
  require it for `environment=production` (verified: production scan without it → 409). **Fixed** (note added).
- Two skill files both declare frontmatter `name: shakerscan` (`skills/scanner-skill.md` and
  `skills/shakerscan/SKILL.md`) — an ambiguous-resolution hazard where the legacy redirect could shadow
  the canonical safety-gated workflow. **Fixed** by renaming the legacy entry to `shakerscan-legacy`.

## Verified-good behavior (explicitly not defects)

- **28/28 UI routes**: HTTP 200, zero console errors, zero failed API calls, no blank pages, no
  horizontal overflow at 320/375/768/1024/1440 px. Error routes (bad UUID / unknown route) render a
  graceful "Failed to load … / Retry" or a clean 404 — no client-visible stack traces.
- **Destructive UI actions gated:** finding delete shows a confirm dialog; no `DELETE` fires on first
  click; Cancel aborts (verified in-browser).
- **Input validation:** malformed JSON, null/empty/wrong-type target, bad enum, wrong content-type,
  worker count 0/negative/over-max/non-integer/string, batch empty / >50 → all 4xx.
- **Injection resistance:** SQLi in `severity`/`root_domain`/`sort_by` filters → 200 empty or 422
  (sort allow-listed); path traversal in `/scans/{id}/result` → 404.
- **Server-side gates enforced:** AI Gate production (`confirm_production` → 409 without),
  schedule retention-sweep rejected, worker bounds — all enforced in the API, not just in prose.
- **Cross-surface consistency:** workers API=16 = docker=16; finding PATCH persists (Unicode notes
  round-trip) and reverts; schedule CRUD round-trips.
- **DAST ground truth:** quick scan of Juice Shop (plain HTTP) correctly reported missing CSP
  (medium) and Referrer-Policy (low), score 82/B.
- **Route contract:** 234 code routes; no duplicate or currently-shadowed routes; capability table
  matches code exactly.
